# AIOps 知识库大纲构建 Pipeline — 执行计划 v4.0

> **版本**：v4.0
> **创建日期**：2026-04-20
> **基于**：pipeline-plan v3.0（大幅简化）
> **定位**：聚焦于"知识库大纲"的多模型对抗生成流水线

---

## 一、为什么从 v3 简化到 v4

v3 设计了 5 个阶段（冷启动 → 评审 → 收敛 → 深度下钻 → 整合），其中 Stage 4/5 是对每个子模块做深度知识页生成。但我们的当前目标只是**整理一份高质量的知识库大纲**，而非产出完整的知识内容。大纲做好之后，再考虑后续的逐模块细化。

因此 v4 将 Pipeline 精简为 **3 个阶段**：

```
Stage 1: 多模型并行生成 → 收集 N 份大纲草案
Stage 2: 交叉评审与仲裁 → 发现差异、解决冲突
Stage 3: 主控合成 → 输出终版大纲
```

---

## 二、设计原则

| 原则 | 说明 |
|------|------|
| **多源对比** | 不依赖单一模型，让多家 LLM 独立生成大纲，从差异中寻找最优解 |
| **评审先行于融合** | 先让专家互相"挑刺"，充分暴露问题后再合成，而非生成后直接使用 |
| **输出即大纲** | 最终产出物就是一份结构化的知识库大纲文档，可直接用于后续内容填充 |
| **零领域知识门槛** | 执行者无需了解 AIOps，Pipeline 自带完整的行业上下文 |

## 三、工具链与模型分配

### 可用模型

| 模型 | 提供方 | 特点 |
|------|--------|------|
| Gemini 2.5 Pro | Google | 长上下文窗口，结构化输出能力强 |
| GPT-4o | OpenAI | 综合推理与逻辑分析能力强 |
| DeepSeek | 深度求索 | 工程技术细节准确，性价比高 |
| kimi-k2.6 等 | Kimi（Moonshot） | 长上下文与中文结构化评审 |

### 角色分配（不重复使用同一模型）

| 阶段 | 角色 | 模型 | 理由 |
|------|------|------|------|
| Stage 1 生成 | 生成者 A | **Gemini** | 长上下文 + 结构化大纲生成 |
| Stage 1 生成 | 生成者 B | **ChatGPT** | 不同视角的大纲生成 |
| Stage 1 生成 | 生成者 C | **DeepSeek** | 工程实践视角的大纲生成 |
| Stage 2 评审 | 评审者 | **Kimi（如 kimi-k2.6）** | 中文结构化评审 + 差异分析 |
| Stage 3 合成 | 主控合成 | **Gemini** | 长上下文窗口适合合并多份文档 |

> 如果某个 API 暂时不可用，可用其他模型替代，但尽量保持 Stage 1 的三个生成者使用不同模型。

## 五、各阶段详细设计

### Stage 1：多模型并行生成

**目标**：让 3 个不同模型独立生成大纲草案，确保视角多样性。

**统一的生成 Prompt 要点**（各模型使用同一份 Prompt）：

```
你是一位资深的 AIOps 领域架构师。请为一家企业级组织设计一份
「智能运维（AIOps）知识库目录大纲」。

要求：
1. 大纲定位：面向运维工程师、SRE、运维管理层的系统性知识框架
2. 覆盖范围：从运维基础（监控、日志、告警）到智能化（异常检测、
   根因分析、大模型运维）的完整技术链路
3. 结构深度：2-3 级目录（一级域 → 二级主题 → 关键知识点）
4. 每个一级域附：一句话说明其定位与价值
5. 标注每个一级域的 AIOps 成熟度等级：
   - L1（基础运维）：手工操作为主
   - L2（辅助分析）：数据驱动，人为主
   - L3（智能推荐）：AI 辅助决策
   - L4（高度自愈）：自动化闭环
6. 不要只罗列技术名词，要体现知识之间的逻辑关系
7. 输出格式：结构化 Markdown
```

**产出物**：
- `output/stage1_draft_a_gemini.md` — Gemini 生成的草案
- `output/stage1_draft_b_chatgpt.md` — ChatGPT 生成的草案
- `output/stage1_draft_c_deepseek.md` — DeepSeek 生成的草案

---

### Stage 2：交叉评审与仲裁

**目标**：由第四个模型（Kimi，默认 `kimi-k2.6`）对三份草案进行对比评审，找出共识、分歧和盲区。

**评审 Prompt 要点**：

```
你收到了三份由不同 AI 模型独立生成的「AIOps 知识库大纲」草案。
你的任务是进行交叉对比评审。

评审步骤：
1. **共识提取**：三份草案中共同出现的知识域，说明业界对其重要性有共识
2. **分歧标注**：某份草案有但其他草案没有的内容，分析是"有价值的独特视角"
   还是"不必要的边缘内容"
3. **盲区识别**：三份草案都遗漏的重要知识域
4. **结构对比**：哪份草案的知识组织结构更合理？为什么？
5. **深度对比**：哪份草案的二级/三级展开更充实？有哪些值得吸收的细节？
6. **仲裁建议**：对于分歧项，给出你的采纳建议及理由

输出格式：
- 共识清单（直接进入终版）
- 分歧项列表（附仲裁结论）
- 盲区补充列表
- 推荐采纳的独特点子
- 结构优化建议
```

**产出物**：
- `output/stage2_review_report.md` — 完整的交叉评审报告

---

### Stage 3：主控合成

**目标**：基于三份草案 + 评审报告，合成最终大纲。

**合成 Prompt 要点**：

```
你是 AIOps 领域首席架构师。你需要基于以下材料合成一份最终版的
「AIOps 知识库目录大纲」：

1. 三份独立生成的大纲草案
2. 一份交叉评审报告

合成原则：
1. 共识项直接采纳
2. 分歧项按评审报告的仲裁结论处理
3. 盲区必须补充
4. 有价值的独特点子吸收进来
5. 知识结构按"从底层数据 → 上层应用 → 智能化"的逻辑组织
6. 每个一级域包含：域名称、一句话说明、成熟度等级、二级/三级展开
7. 文末附"知识域依赖关系图"（文字描述）
8. 文末附"各域推荐优先级"（P0/P1/P2）

输出要求：
- 一份完整的、可直接使用的 Markdown 大纲文档
- 不要再标注"来自草案A/B/C"，产出物应该是浑然一体的
```

**产出物**：
- `output/stage3_final_outline.md` — **最终交付物**

## 七、执行方式

本 Pipeline 已通过 Python 脚本自动化，使用方式：

```bash
# 安装依赖
pip install -r requirements.txt

# 在项目根目录 .env 中填写 API Key（见下文「API 配置」）

# 执行完整 Pipeline（Stage 1-3）
python src/main.py --full

# 或单阶段执行
python src/main.py --stage 1    # 仅生成三份草案
python src/main.py --stage 2    # 仅做交叉评审（需先完成 Stage 1）
python src/main.py --stage 3    # 仅合成终版（需先完成 Stage 1+2）
```

### API 配置

采用项目根目录 `.env` 配置（可参考 `.env.example`）。

**推荐：OpenAI 兼容中转站（Gemini + ChatGPT 共用）**  
若 Gemini 与 ChatGPT 均通过同一中转（如 ChatAnywhere）调用，设置：

- `CHAT_API_KEY`：中转站 API Key  
- `CHAT_BASE_URL`：中转站 Base URL（示例：`https://api.chatanywhere.tech/v1`）  
- `GEMINI_MODEL`：中转上对应的 Gemini 模型 id（示例：`gemini-3-pro-preview`，以服务商文档为准）  
- `OPENAI_MODEL`：中转上对应的 ChatGPT / 兼容模型 id（示例：`gpt-4o`）  

此时 Stage 1 的 Gemini 草案、ChatGPT 草案与 Stage 3 的合成均通过该中转调用，仅 `model` 参数不同。

**直连（未设置 `CHAT_API_KEY` 时）**

- `GEMINI_API_KEY` + `google-generativeai`（`GEMINI_MODEL` 用 Google 官方模型名）  
- `OPENAI_API_KEY` + `OPENAI_BASE_URL`（官方或其它 OpenAI 兼容端点）

**其它**

- DeepSeek：`DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、`DEEPSEEK_MODEL`  
- Kimi（Moonshot）：`KIMI_API_KEY`、`KIMI_BASE_URL`（默认 `https://api.moonshot.cn/v1`）、`KIMI_MODEL`（如 `kimi-k2.6`）、`KIMI_TEMPERATURE`（`kimi-k2.6` 通常必须为 `1`，否则 API 返回 400）

## 九、与 v3 的核心差异

| 项目 | v3 | v4 |
|------|----|----|
| 阶段数 | 5 个 | 3 个 |
| Stage 1 | 单模型冷启动 | 多模型并行生成（3 份草案） |
| Stage 2 | 四专家评审 + 仲裁 | 单模型交叉对比评审 |
| Stage 3 | 冲突收敛 + 质量门控 | 基于评审报告直接合成 |
| Stage 4/5 | 深度下钻 + 整合 | 移除（留待后续） |
| API 调用次数 | 20+ 次 | 5 次 |
| 预计耗时 | 数天 | 10-15 分钟 |
| 人工介入 | 30 分钟配置 | 仅填写 API Key |
| 最终产出 | 大纲 + 知识卡片 | 知识库大纲文档 |

---

*变更记录：v4.0 相较 v3.0 简化为 3 阶段（并行生成 → 交叉评审 → 主控合成），移除了深度下钻与整合阶段，聚焦于大纲产出，API 调用从 20+ 次降至 5 次，预计耗时从数天缩短至 10-15 分钟。*
