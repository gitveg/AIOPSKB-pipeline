# PHM 知识库多智能体构建 Pipeline — 设计文档

## 1. 项目背景

当前 v10 大纲的第二部分（行业-设备-特性知识体系）存在结构性缺陷：
- 无部件层级，故障仅到设备级
- 设备覆盖不全面（仅 8 个行业、57 个设备条目）
- 故障诊断生命周期维度混合在设备级 10 维模板中，缺乏故障级的细粒度展开

本方案从零重新构建，设计为 **行业 → 设备 → 部件 → 故障** 四级结构，通过多智能体协作确保覆盖面和可用性。

**范围**：仅聚焦第二部分。第一、三、四部分不动。

---

## 2. 四级数据模型

### 2.1 层级结构

```
行业 (Industry) — ## 层
  └─ 设备 (Equipment) — ### 层
       ├─ 设备基本信息（类型、原理）
       ├─ 设备生命周期（5 阶段）
       └─ 部件 (Component) — #### 层
            └─ 故障 (Fault) — ##### 层
                 └─ 10 个诊断子维度
```

### 2.2 字段定义

#### Industry（行业）
| 字段 | 类型 | 说明 |
|------|------|------|
| 编号 | str | 如 "2" |
| 名称 | str | 如 "电力行业" |
| 设备列表 | list[Equipment] | 该行业下所有设备 |

#### Equipment（设备）
| 字段 | 类型 | 说明 |
|------|------|------|
| 编号 | str | 如 "2.1" |
| 名称 | str | 如 "齿轮箱" |
| 类别 | str | 设备所属子类别，如 "风电" |
| 基本信息 | EquipmentInfo | 设备类型、作用与工作原理 |
| 生命周期 | Lifecycle | 5 阶段：设计选型→安装调试→运行看护→维护检修→退役报废 |
| 部件列表 | list[Component] | 所有关键部件，全部展开 |
| 风险与标准 | str | 关键性评估 + 引用标准 |
| 智能化应用 | list[str] | AI/数字孪生/大模型应用场景 |

#### Component（部件）
| 字段 | 类型 | 说明 |
|------|------|------|
| 编号 | str | 如 "2.1.1" |
| 名称 | str | 如 "齿轮副" |
| 故障列表 | list[Fault] | 该部件的所有故障模式 |

#### Fault（故障）— 10 个诊断子维度
| # | 子维度 | 说明 | 示例 |
|---|--------|------|------|
| 1 | 故障描述 | 故障现象概述 | 齿面渐增性磨损导致传动精度下降 |
| 2 | 故障机理 | 根因分析（物理/化学机理） | 润滑不良→油膜破裂→金属直接接触→磨粒磨损 |
| 3 | 监测手段 | 用什么方法/传感器检测 | 振动（高频冲击/包络信号）、油液分析（铁谱/颗粒度） |
| 4 | 诊断手段 | 如何分析和判断 | 频谱分析、阶次分析、时域同步平均 |
| 5 | 诊断指标与特征 | 关键特征参数 | 啮合频率边带、残余信号RMS、油液金属元素浓度 |
| 6 | 健康评估方法 | 如何量化退化程度 | 磨损元素趋势建模、振动烈度趋势分析 |
| 7 | 寿命预测方法 | RUL 预估方法 | 基于振动特征退化的 RUL 预测模型 |
| 8 | 维护策略 | 预防/预测/事后等策略 | 预测性维护（PdM），基于振动趋势预警 |
| 9 | 检修方法 | 具体维修操作 | 齿轮更换 SOP、齿面修复研磨 |
| 10 | 备件与资源 | 所需备件和工具 | 齿轮备件按 RUL 预测提前储备 |

## 3. 多智能体设计

### 3.1 收集调研智能体（Collector Agent）

**职责**：尽可能全面地枚举设备种类、部件、故障类型。

**三个枚举方法**：

1. **`enumerate_equipment(industry_name, seed_names)`**
   - 输入：行业名称 + v10 已有设备名作为种子
   - 输出：`[{name, aliases, subcategory, description}]`
   - 策略：要求 LLM 穷举该行业所有需要 PHM 的关键设备，种子保证不遗漏 v10 已有条目
   - Web search 辅助：枚举前通过 MCP WebSearch 工具收集行业设备清单资料，作为补充上下文

2. **`enumerate_components(equipment_name, seed_components)`**
   - 输入：设备名称 + v10 已有关键部件名
   - 输出：`[{name, description}]`
   - 策略：列出所有可独立监控和更换的部件

3. **`enumerate_faults(equipment_name, component_name)`**
   - 输入：设备名 + 部件名
   - 输出：`[{name, description}]`
   - 策略：列出该部件的所有典型故障模式

**Web search 集成**：
- 主要方式：LLM 自身知识（覆盖面已足够广）
- 增强方式：通过 Claude Code 的 WebSearch MCP 工具预先收集参考资料，保存到 `research/` 目录，collector 读取作为补充
- 未来可扩展：接入搜索 API（Tavily/Serper）实现全自动

### 3.2 主智能体（Builder Agent）

**职责**：架构保证、结构化填充、根据反馈迭代。

**核心方法**：

1. **`enrich_faults(equipment, component, fault_skeletons) -> list[Fault]`**
   - 接收故障骨架（仅名称+描述），填充全部 10 个子维度
   - 批量处理：一次 LLM 调用填充一个部件下所有故障
   - 输出格式：结构化 JSON，由 Pydantic 校验

2. **`refine_from_feedback(current_data, evaluation_report) -> dict`**
   - 读取评估报告中的具体改进建议
   - 生成定向补充指令，调用 collector 补充缺失条目
   - 调用 enrich_faults 填充新条目的子维度

### 3.3 可用性判断智能体（Evaluator Agent）

**职责**：站在工程师视角审核知识库的实用性。

**四维评估**：

1. **查询路径测试**：生成 15-20 个真实故障场景，验证从根节点（行业）能否导航到具体故障条目
2. **覆盖完整性**：逐行业检查是否有遗漏的重要设备/部件/故障
3. **可操作性**：每个故障的 10 个子维度是否有实质内容，足以指导工程师行动
4. **交叉检索能力**：同一故障模式（如轴承磨损）在不同设备的对应部件中是否都有记录

**输出**：结构化评估报告（Markdown），含具体改进建议和优先级。

## 4. Pipeline 编排流程

### 4.1 CLI 入口

```
python scripts/pipeline.py --build          # 构建/重建知识库
python scripts/pipeline.py --evaluate       # 评估最新版本
python scripts/pipeline.py --refine         # 根据评估改进
python scripts/pipeline.py --full           # 完整流程
```

### 4.2 Build 阶段

```
对每个行业（从 v10 提取种子数据）:
  1. collector.enumerate_equipment() → 扩充设备列表
  2. 对每个设备:
     a. collector.enumerate_components() → 获取部件列表
     b. 对每个部件:
        - collector.enumerate_faults() → 获取故障骨架
        - builder.enrich_faults() → 填充 10 个子维度
  3. 写入该行业的结构化数据
合并所有行业 → 写入 outlines/Merged_PHM_TOC_v11.md
导出 data/v11_faults.json + data/v11_faults.csv
```

### 4.3 Evaluate 阶段

```
读取最新版本大纲 → evaluator.evaluate() → 写入 reviews/Evaluation_v{N}.md
```

### 4.4 Refine 阶段

```
读取最新版本 + 最新评估报告 → builder.refine_from_feedback() → 写入 v{N+1}
```

### 4.5 迭代循环

Build → Evaluate → Refine 可反复循环，直到评估通过或达到迭代上限。

## 6. v10 迁移策略

**策略：提取种子数据，重新生成。**

1. 解析 v10 第二部分，提取：行业名称、设备名称、每个设备的 `关键部件` 列表
2. 将这些作为种子传给 collector，确保 v10 已有条目不会丢失
3. collector 基于种子扩充新的设备和部件
4. builder 重新生成完整的四级结构

v10 的知识内容（监测方法、诊断手段等）不直接迁移，因为粒度不匹配（设备级 vs 故障级）。但 v10 数据作为参考上下文提供给 builder，辅助生成。
