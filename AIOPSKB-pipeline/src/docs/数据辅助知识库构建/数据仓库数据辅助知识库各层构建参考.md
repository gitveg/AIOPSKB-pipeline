# 数据仓库数据辅助知识库各层构建参考

> **版本**：v1.0
> **创建日期**：2026-06-28
> **数据基线**：PHM 数据仓库 `alg_analysis`（近 5 年，2021-06-28 ~ 2026-06-28）
> **适用范围**：指导如何利用数据仓库挖掘的设备分布数据，辅助知识库「子设备 / 子系统 / 部件 / 零件」各数据层的构建
> **定位**：**参考作用**（external anchor），非自动生成。数据提供「现实存量校验」，结构判定仍由人工 / LLM / 专家评审完成

---

## 一、文档目的

知识库采用八层结构（见 `construct_guide.md` §1.1）：

```
行业 → [子行业] → 设备 → [子设备] → 子系统 → 部件 → 零件 → 故障
```

其中 **子设备 / 子系统 / 部件 / 零件** 四层是知识库内容生成的核心，也是人工构建中最依赖经验、最易遗漏或臆造的部分。本文档回答一个问题：

> **PHM 数据仓库里能挖出什么，分别能辅助这四层的哪一步、辅助到什么程度？**

核心结论先行——**数据仓库对各层的支撑度并不均衡**：

| 知识库层 | 定义 | 数据支撑度 | 一句话结论 |
|---|---|---|---|
| **子设备** | 设备的技术路线细分（如双馈/直驱/半直驱） | 🟡 **中** | 部分行业有技术路线代码可验证；多数行业无 |
| **子系统** | 功能分解单元（传动/发电/控制） | 🟠 **弱** | 无结构树，只能从部件构成间接推断功能域 |
| **部件** | 可独立更换/检修的总成（齿轮箱/叶片） | 🟡 **中** | 低频 `devicetype` 直接提供部件候选清单 |
| **零件** | 更细粒度可拆卸件（行星齿轮/太阳轮） | 🔴 **无** | 数据仓库无零件级数据，必须靠标准/手册/LLM |

> **关键认知**：监测平台的 `devicetype` **不是纯「设备类型」**，而是**「设备级 + 部件级」混合**。用数据做参照时，必须先识别这个混合性，否则会把部件误当成设备/子设备。详见第三节。

### 3.4 单企业刷量（⚠ 反例指标）

| 数据质量 | 行业 | 未分类占比 |

| 中（5~30%） | 石化、化工、有色、火电、港口 | — |
| 差（>30%） | 钢铁、水泥、试验、汽车 | 慎用 |

## 四、核心：各层数据支撑度与方法

### 4.1 子设备层（技术路线细分）— 🟡 中等支撑

**子设备定义**（`construct_guide.md` §0.2）：设备大类下的技术路线细分，仅当设备是大类且包含多个技术路线时使用（如锅炉→煤粉炉/CFB/余热锅炉）。

**数据能做什么**：
- ✅ **验证某设备是否需要拆子设备**：当同一设备大类下存在多个**技术路线型 `devicetype`**，且各自有显著存量时，佐证需要拆分
- ✅ **存量覆盖度裁剪**：按 `construct_guide.md` §2.5「主流技术路线覆盖现场存量 95%+」原则，用数据验证选哪几个子设备

**典型案例 —— 风电**（数据完美佐证）：

| 技术路线 devicetype | 中文 | 设备数 | 企业数 | 占风电比 |
|---|---|---|---|---|
| 139553 | 双馈主传动 | 23,630 | 809 | 30.5% |
| 139554 | 直驱主传动 | 9,197 | 281 | 11.9% |
| 139552 | 半直驱主传动 | 5,065 | 164 | 6.5% |

三种技术路线覆盖风电设备 48.9%，且分布在不同企业 → **"风电机组"必须拆双馈/直驱/半直驱三个子设备**，与知识库现有架构（三机型）完全吻合。

**数据不能做什么**：
- ❌ 多数行业的 `devicetype` **没有技术路线维度**（如石化全是 `离心泵/屏蔽泵/磁力泵` 这种"泵的种类"，不是"某设备的子设备"）。这些设备**不需要拆子设备**，直接进入子系统层
- ❌ `devicename` 不含技术路线字样（如双馈风机的 devicename 只是"11号风机"），无法从命名挖掘
- ❌ 无法自动判断"哪些 devicetype 属于同一个设备大类"（如 139553/139554 都属于"风电机组"），需人工/专家映射

**操作建议**：
1. 对每个候选设备，查 TopN 清单看是否存在"技术路线型"代码聚类
2. 判定阈值：**≥3 个技术路线，各自存量 ≥1000 台（或企业数 ≥10），且 Top 技术路线累计覆盖 ≥95%** 才拆子设备
3. 不满足的直接按单一设备处理，跳过子设备层

---

### 4.2 子系统层（功能分解）— 🟠 弱支撑

**子系统定义**（`construct_guide.md` §0.2）：设备（或子设备）的功能分解单元（传动系统/发电系统/控制系统），按功能独立性划分，**始终存在**。

**数据能做什么**：
- 🟡 **间接推断功能域**：通过某设备的**部件构成**（见 4.3），人工归纳出功能子系统。数据提供"这个设备由哪些部件组成"，功能归类仍需人工
- 🟡 **跨机型统一骨架验证**：风电的部件构成（叶片/齿轮箱/发电机/主轴/塔筒/变桨轴承）印证了知识库「10 子系统统一骨架」的合理性

**典型案例 —— 风电部件构成 → 子系统映射**：

| 部件（数据挖出） | 归属子系统（人工/标准） |
|---|---|
| 叶片(7011) | 风轮系统 |
| 变桨轴承(7065/60005) | 变桨系统 |
| 齿轮箱(7002) | 传动系统 |
| 发电机(7007) | 发电系统 |
| 主轴(7006) | 传动系统 |
| 塔基/塔顶(7009/7008) | 塔架与支撑系统 |

**数据不能做什么**：
- ❌ **无结构树**：`devicemodeljson` 不是结构树，`business_device_condition_point.fullname` 是自由文本路径（段数不固定），无法程序化解析出"设备→子系统→部件"的层级
- ❌ 无法自动把部件归到功能子系统——这是知识工程，需参照标准（如 RDS-PP）和专家意见
- ❌ 多数非风电行业，部件级数据稀疏，难以支撑功能域划分

**操作建议**：
1. 子系统划分**以 `construct_guide.md` 的功能分解方法论 + 行业标准（KKS/RDS-PP）为主**，数据仅作"该设备确实有这些功能部件"的旁证
2. 可选增强：开发 `fullname` 路径解析器，从 `business_device_condition_point.fullname` 提取「设备→部件」关系（路径倒数第二段常为部件），为部件清单提供补充。这是**未来可挖掘方向**

### 4.3 部件层（总成单元）— 🟡 中等支撑

**部件定义**（`construct_guide.md` §0.2）：子系统下可独立更换/检修的总成单元（齿轮箱/联轴器/叶片）。

**数据能做什么**：
- ✅ **直接提供部件候选清单**：第三节识别出的「部件级 `devicetype`」（齿轮箱/叶片/发电机/轴承座/滚筒/减速机等）就是天然的部件候选
- ✅ **部件存量排序**：按 `device_count` 排序，优先纳入高频部件
- ✅ **过滤非部件**：用 `single_ent` 排除单企业特例，识别仪表类（压力表 7062）、区域类（机舱/机头区域）等不应作为部件的条目

**数据不能做什么**：
- ❌ **不完整**：数据仓库只录入了"被监测的部件"，大量总成（密封件、联轴器、轴承内部件）未被单独建 `devicetype`，需靠标准/手册补充
- ❌ **命名不规范**：`devicename` 是现场自由命名（"1#气缸""2#驱动"），需规范化后才能进 `components.md`
- ❌ **无部件→子系统归属**：需人工归类（见 4.2）

**操作建议**：
1. 部件清单 = **「数据挖出的部件级 devicetype（去重去特例）」 ∪ 「标准/手册补充的必备总成」**
2. 数据部分优先取 `device_count ≥ 50 且 enterprise_count ≥ 2` 的条目
3. 每个部件进入 `components.md` 前必须规范化命名、补充描述/易损标识/维护方法（这些数据仓库没有）

---

### 4.4 零件层（可拆卸件）— 🔴 无支撑

**零件定义**（`construct_guide.md` §0.2）：部件下更细粒度可拆卸件（行星齿轮/太阳轮），允许短链。

**数据现状**：数据仓库**完全没有零件级数据**。`partcount` 只有计数，无零件清单；`fullname` 最细到部件/测点。

**结论**：零件层**必须**依靠：
- 设备厂商技术手册 / 零件清单（BOM）
- 行业标准（如齿轮标准的齿形/模数定义）
- LLM 基于"部件类型"生成（如"齿轮箱"→行星齿轮/太阳轮/行星架）

数据仓库在零件层**无任何参考价值**，应在构建流程中明确标注"数据不适用"，避免团队误用。

## 五、使用流程与阈值建议

### 5.1 纳入知识库的设备阈值

Judge 评审设备清单时，对照 TopN 清单校验：

| 信号 | 阈值 | 判定 |
|---|---|---|
| 设备数 + 企业数 | 设备数 ≥100 **或** 企业数 ≥5 | ✅ 纳入（有真实存量） |
| 仅 1 家企业 | `single_ent = True` | ⚠ 标注为"单企业特例"，默认不纳入通用知识库 |
| 未分类占比高（行业级 >30%） | — | 该行业数据慎用，需配合标准/专家 |

### 5.2 各层构建时的数据使用顺序

```
阶段2 设备枚举
  └─ 用 industry_devicetype_topN.csv (in_topn=True) 做外部锚点
     └─ 过滤 single_ent=True 和部件级条目 → 得到"设备级"候选清单
     └─ Judge 评审 + 人工补充主流程设备

[按需] 子设备拆分 (仅风电等少数行业)
  └─ 检查同设备大类下是否有≥3个技术路线型devicetype
     └─ 取 Top 技术路线，验证累计覆盖≥95% → 确定子设备清单

阶段3 部件拆解 (子系统→部件→零件)
  └─ 子系统：以标准/专家为主，数据旁证部件构成
  └─ 部件：「数据部件级devicetype」∪「手册补充」→ 规范化命名
  └─ 零件：纯手册/标准/LLM（数据不适用）
```

### 5.3 Judge 评审对照清单

评审每条设备/部件时，评审方可查 TopN 清单回答：
- 该 `devicetype` 在该行业的真实存量？（`device_count`）
- 多少企业在用？（`enterprise_count`，排除单企业）
- 是否进入行业 TopN？（`in_topn`，反映主流性）
- 占该行业比例？（`pct`）

## 六、局限性与注意事项

1. **`devicetype` 不统一**：设备级与部件级混合，使用前必须先识别条目级别（第三节清单可作为初筛）
2. **数据质量参差**：钢铁/水泥/试验等行业未分类占比高（>30%），这些行业的 TopN 参照价值打折，需配合标准
3. **时间范围**：基线为近 5 年，监测平台数据持续增长，建议**季度更新**
4. **单企业污染**：务必用 `single_ent` 过滤，避免把某企业特例写进通用知识库
5. **中文补全的推断性**：无枚举代码的中文是基于 `devicename` 高频词推断的（如 7009→塔基），个别可能不准，使用时建议复核原始 `devicename`
6. **结构层无自动生成**：子设备/子系统/部件/零件的**结构判定**始终需要人工/LLM/专家，数据只提供"存量校验"和"候选清单"，不提供"结构本身"

## 七、数据更新与维护

| 项 | 建议 |
|---|---|
| 更新频率 | 季度（监测平台数据增长周期） |
| 更新方式 | 重跑 `industry_devicetype_topN.py` + `_patch_noenum.py`，覆盖 `db_export/` |
| 新行业接入 | 数据仓库出现新 `industry` 枚举时，脚本自动纳入（无需改代码） |
| 新 devicetype | 自动进入清单；若是无枚举代码，跑 `_probe_noenum.py` 反查补全 |
| 版本管理 | 每次更新在本文档记录数据基线日期 + 总设备数 |

## 八、后续可挖掘方向

1. **`fullname` 路径解析器**：从 `business_device_condition_point.fullname` 程序化提取「设备→部件」关系（路径倒数第二段常为部件），为部件层提供更完整的候选（当前只用了 `devicetype` 视角）
2. **设备大类聚类**：用 `devicename` 文本聚类 + `devicetype` 把"设备级"条目归并到知识库的"设备大类"，解决 4.1 中"无法自动判断哪些 devicetype 属于同一设备大类"的问题
3. **跨行业部件复用库**：轴承/齿轮箱/联轴器等通用部件在多行业高频出现，可按 `construct_guide.md` §12 建立"通用组件库"
4. **故障案例关联**：将 `diag_fault_case`（故障案例表）与 `devicetype` 关联，统计"某设备类型实际发生过哪些故障"，辅助故障层（阶段4）的真实性校验

## 附录 C：devicetype 知识库层级分类结果（v1.1 新增）

为把数据库 `devicetype` 对齐知识库层级定义，基于知识库**实际白名单**（从 `equipment_registry.md` 提取 697 个设备名 + 从 `components.md` 提取 1793 个部件名）+ 工程常识关键词规则，对 TopN 清单内所有 `devicetype` 做了自动分类。**待复核 0 项**。

### C.1 分类方法（双重校验）

1. **白名单匹配**（高置信）：`devicetype_cn` 精确命中设备白名单 → 设备；命中部件白名单 → 部件
2. **关键词规则**（中置信）：按"零件词→部件词→设备词→仪表/部位→功能域→杂项"顺序匹配
3. **特殊代码**：技术路线代码（139553/139554/139552）→ 子设备

### C.2 分类统计（TopN 内，174,755 台设备实例）

| 知识库层级 | 型号数 | 设备实例数 | 占比 | 数据支撑度 |
|---|---|---|---|---|
| **设备** | 100 | 98,780 | 56.5% | 🟢 强 |
| **子设备** | 3 | 37,905 | 21.7% | 🟡 中（仅风电） |
| **部件** | 50 | 29,802 | 17.1% | 🟡 中 |
| **其他**（部位/仪表/杂项） | 9 | 8,268 | 4.7% | — 应过滤 |
| **子系统** | 0 | 0 | 0% | 🔴 无 |
| **零件** | 0 | 0 | 0% | 🔴 无 |

### C.4 关键结论（修正第三节 3.3 的表述）

1. **`devicetype` 实际混合了「设备 + 子设备 + 部件 + 其他」四类**（不是最初判断的"设备级+部件级"两层）。`classify_devicetype.py` 已给每个型号打上 `kb_level` 标签。
2. **子设备层仅风电有数据支撑**（双馈/直驱/半直驱主传动，37,892 台）——其余 22 行业的 `devicetype` 没有技术路线维度，对应设备**不需要拆子设备**。
3. **子系统层、零件层在全行业均为 0**——数据仓库**完全没有**这两层信息，再次印证第四节"子系统🟠弱、零件🔴无"的判断。这两层必须靠标准/手册/LLM 构建。
4. **部件层数据集中在风电/钢铁/水泥/煤炭**——这些行业把齿轮箱、叶片、辊、锥箱、托辊等总成单独建了 `devicetype`，可作为部件清单的数据来源；石化/化工的部件级数据稀疏（泵的内部件未被单独监测），需靠手册补充。
5. **"其他"类（8,268 台）必须过滤**——塔基/塔顶/机舱（部位）、压力表（仪表）、非标/通用（杂项）既非设备也非部件，进知识库前应剔除。
