# 设备层与部件层构建经验总结

> 本文档记录电力行业知识库构建过程中，设备层和部件层暴露的问题、根因分析及经验教训。
> 适用于后续行业（石化、冶金等）构建时参考，避免重复踩坑。
> 整理日期：2026-05-13

---

## 1. 规则必须前置，不能事后补

### 问题

我们遇到的最大一类问题是"边界模糊"——凝汽器到底是汽轮机的部件还是独立设备？励磁系统到底归发电机还是独立？锅炉的辅助设备该不该挂在锅炉下面？这些问题在数据已经生成后才来争论，修改成本很高（要改components.md、删故障文件、清理引用）。

### 根因

构建开始时没有明确定义"什么是设备、什么是部件"的判定规则。LLM在无约束的情况下自由发挥，按通用理解而非行业实际来划分层级。

### 经验

**在生成第一行数据之前，判定规则必须写清楚。** 我们后来补写的"设备与部件5条判定原则"（物理独立性、采购独立性、运维独立性、功能完整性、资产登记）应该在construct_guide.md的章节0就存在，而不是修了一轮之后才补。

### 推荐做法

- 每个行业启动构建前，先完成设备枚举阶段，产出设备清单和边界决策文档
- 设备清单必须经过Judge审查通过后，才能进入部件拆解阶段
- 参照 `equipment_classification.md` 的格式，每个设备都记录判定依据

## 2. 分类维度不能混用

### 问题

`boiler/sub_equipment.md` 是最典型的反面教材。一个文件里混了结构维度（火管/水管）、循环维度（自然/强制/直流）、燃烧维度（层燃/室燃/流化床）、用途维度（电站/工业）、介质维度（蒸汽/热水），这些维度之间是交叉关系而非并列关系。LLM生成时没有约束分类维度，就自由发挥把所有可能的锅炉名词都堆进去了。

### 根因

sub_equipment（子设备）的拆分没有指定分类维度。LLM倾向于"尽量全面"，把所有能想到的分类都列出来，而不考虑维度之间的逻辑关系。

### 经验

**子设备/部件的拆分必须基于单一维度。** 火电锅炉按技术路线（煤粉炉/CFB/余热锅炉）拆就是对的，按混合维度拆就是灾难。

### 推荐做法

- 在prompt中明确指定分类维度，例如"按技术路线/燃烧方式拆分"
- 拆分后检查：任意两个子设备之间是否可能同时存在于同一台设备上（如果是，说明维度混用了）
- 互斥性是好的分类的标志（煤粉炉和CFB不会同时存在于同一台锅炉）

## 3. LLM生成的数据有系统性缺陷模式

### 问题

重复问题有很强的规律性：
- 过热器管5条完全重复——很可能是prompt被喂了两遍，或者生成后concat时重复
- 8个火电文件、3个风电文件、33个水电文件都有重复——这不是偶发错误，是生成流程本身的bug
- 重复的模式几乎都是"整块复制"（前N条和后N条完全一致），不是随机行重复

### 根因

生成pipeline中缺少自动去重和校验步骤。数据从LLM输出后直接写入文件，没有任何中间检查。

### 经验

**每层生成后必须加一个自动检查步骤。** 检查方法很简单：对数据行做 `sort -u`，对比去重前后的行数，不一致就报警。这种检查成本极低，但能避免大量数据质量问题。

### 推荐做法

- 在construct_guide.md的工作流程中，每层生成后增加"自动校验"步骤
- 校验内容至少包括：行级去重、表头完整性、必填字段非空
- 校验不通过的文件标记为"待修正"，不允许进入下一阶段
- 具体实现可参考以下检查脚本逻辑：
  ```
  total_data = 数据行数（排除表头）
  unique_data = sort -u 后的数据行数
  if total_data != unique_data → 报警，自动去重
  ```

## 4. 领域知识的准确性需要专业校验

### 问题

发电机轴承写成了滚动轴承，这个错误很致命——大型汽轮发电机全部用滑动轴承，这是行业常识。LLM为什么会犯这个错？因为通用语料中"发电机轴承"的搜索结果大量来自小型电机（柴油发电机、工业电机），这些确实用滚动轴承。LLM没有能力区分"火电1000MW汽轮发电机"和"工厂备用200kW柴油发电机"。

### 根因

LLM的通用知识无法自动适配特定行业语境。当prompt没有明确约束技术参数范围时，LLM会用最常见的理解来填充，而"最常见的"往往来自通用场景而非目标行业。

### 经验

**不能指望LLM自动适配行业语境。** 必须在prompt中明确约束技术范围。

### 推荐做法

- prompt中写明目标行业的技术参数范围，例如"适用于300~1000MW大型火电机组，轴承型式为椭圆瓦/可倾瓦滑动轴承"
- Judge智能体审查时，增加"行业适用性"检查项：生成的故障模式是否匹配目标行业的技术特征
- 对关键部件（轴承、密封、材料等），在prompt中提供明确的技术约束
- 建立行业特定的"常识校验清单"，例如：
  - 火电：发电机轴承=滑动轴承，锅炉=水管锅炉（非火管），汽轮机=冲动式/反动式（非离心式）
  - 风电：齿轮箱=行星齿轮（非圆柱齿轮），叶片=复合材料（非金属）

## 5. 垃圾数据要果断删除，不要试图修复

### 问题

风电那11个独立目录（叶片、轮毂、齿轮箱等）的数据质量极差——轮毂目录混入汽车轮毂故障，发电机目录混入柴油机故障。最初还在犹豫要不要逐条清理修复，最终决定直接删除，只保留风电机组主设备目录。

### 根因

当数据源头就错的时候（prompt没约束住行业范围），逐条修补成本极高且容易遗漏。错误的数据源头意味着整个数据集的可信度都存疑。

### 经验

**修复垃圾数据的成本远高于从正确起点重新生成。** 尤其当数据源头就错的时候，逐条修补只会越改越乱。

### 推荐做法

- 发现数据质量问题时，先判断是"少量错误"还是"系统性偏差"
- 少量错误（如个别参数不准）：直接修正
- 系统性偏差（如整个目录的语境都不对）：果断删除，从正确的prompt重新生成
- 判断标准：抽查10条数据，如果超过3条存在语境偏移，视为系统性偏差

## 6. 目录结构即知识架构，骨架定了就少动

### 问题

风电从12个目录合并为1个，冷却塔拆为湿冷塔+空冷岛——每次目录结构变动都伴随着components.md、faults/、sub_equipment.md的连锁修改。目录结构是知识库的骨架，骨架错了，后面填的内容越多越难改。

### 根因

设备枚举阶段没有充分审查就进入了部件拆解和故障生成阶段，导致后续发现设备划分有问题时，需要大量返工。

### 经验

**设备目录确定后尽量不再变动，部件层和故障层可以在其上增量迭代。**

### 推荐做法

- 阶段2（设备枚举）的审查要格外严格，使用"设备与部件5条判定原则"逐条过
- 设备清单通过审查后，冻结设备目录结构，后续只允许增量添加，不允许删除或合并
- 如果必须调整设备目录，先评估影响范围（涉及多少个faults文件），再决定是否执行
- 每次目录变动后，运行全量去重和引用完整性检查

## 7. 记录决策理由，比记录决策本身更重要

### 问题

凝汽器被从汽轮机部件中移除又加回去、励磁系统在发电机和独立设备之间反复——如果只记录"凝汽器=独立设备"这个结论，后续有人（或LLM）可能再次质疑并把它塞回汽轮机。

### 根因

没有持久化记录分类决策的依据，导致同一问题在不同时间点被重复讨论。

### 经验

**每个分类决策都要写判定依据。** 这样后续新增设备时有先例可循，不会每次都重新争论。

### 推荐做法

- 每个行业维护一份 `equipment_classification.md`，记录所有设备分类决策及其依据
- 格式参照已有的 `power/equipment_classification.md`：设备名称 + 判定依据 + 关键边界决策 + 历史问题记录
- 新增设备时，先查阅该文档确认是否有类似先例
- Judge审查时，将分类决策文档作为参考依据
