## 一、冗余（可精简）

2.6节（智能体协作流程）和章节3开头各自独立描述了「扩充→整合」两阶段流程，各配了一张流程图。内容几乎完全重叠：

- 2.6 "阶段B: 整合循环" ≈ 章节3 "阶段B: 整合精炼"
- 两张流程图传达相同信息

**建议**: 删除2.6节的流程图和具体步骤描述，仅保留一句话引用到章节3。2.6节保留智能体之间「谁发给谁」的交互关系即可。

### 2. 阶段0 过于单薄

"阶段0: 行业初始化"只有两行内容，在章节3中单独占一个标题层级，信息量不值得。

**建议**: 合并到阶段1的开头，作为阶段1的前置步骤。

**建议**: 要么扩充为真正的执行计划（含已完成/进行中/待做状态），要么降级为章节3的一个子节。

## 二、与当前 pipeline 行为不一致

### 4. JUDGE-FAULT 模板缺少 Schema 锚定

实际 judge.py 已在故障层 Judge prompt 中加入了 D1-D9 定义约束块，以及 D2 等级一致性、D3 因果完整性、D9 可操作性三个新审查维度。但 construct_guide 4.2节的 JUDGE-FAULT 模板仍然是旧版6条审查标准，缺少这三项。

**建议**: 在 JUDGE-FAULT 模板审查标准中补充：
- D2 故障等级判定是否与判定标准表一致
- D3 故障描述因果关系是否完整（现象→原因→条件的因果链）
- D9 预防措施是否具体可操作（而非泛泛描述）

### 5. COLLECT-L4 模板与 collector.py 存在差距

collector.py 的故障层 prompt 已有12条要求（含来源引用、父部件约束、D1分隔符说明、D2标准、D5/D6正反例），但 COLLECT-L4 模板只有8条要求，缺少：
- D1 多选用`;`分隔的说明
- D2 等级判定标准（轻微/一般/严重/危急的具体条件）
- D5/D6 正确/错误示例

**建议**: 补齐这三项，让模板与代码保持一致。

### 6. 故障层列数未显式说明

1.3节故障层表格示例有10列（故障名称 + D1-D9），1.4.2节也展示了10列表格，但文中从未显式写出"10列"这个词。pipeline 代码已从"9列"改为"10列"，guide 应在故障层格式规则中明确标注。

**建议**: 在1.4.2节故障层格式处加一句"故障层固定10列"。

## 三、描述不清晰或有歧义

### 7. COLLECT-L4 的条件模板语法未说明

`{{若该部件包含子部件（{子部件列表}），请聚焦于...}}` 使用了双花括号表示条件包含，但文档中从未解释这个约定。单花括号 `{变量}` 和双花括号 `{{条件}}` 的区别对读者不透明。

**建议**: 在4.1节开头加一段模板语法说明：`{变量}` 为必填替换，`{{条件块}}` 为按需包含（仅当条件满足时插入）。

### 8. "维护方法/报废方法仅叶节点填写"的表述

阶段3步骤3.2和COLLECT-L3都说"叶节点部件填写...，非叶节点填'—'"。但现在父部件也生成故障文件了，「叶节点」和「有故障的部件」不再一一对应。一个父部件既有故障文件，又有子部件——它的维护/报废方法该填什么？

**建议**: 明确规则为："维护方法和报废方法仅**最底层部件**（无子部件的部件）必填，有子部件的部件填'—'"。这与叶节点概念一致，但用「有无子部件」来判定比用「叶节点」更清晰。

### 9. 子设备触发条件模糊

步骤2.3说"若某设备是大类...标记为需要子设备拆分"，但"大类"没有量化标准。虽然0.2定义了子设备的概念（"仅当设备是大类且包含多个技术路线时使用"），但什么算"多个技术路线"缺乏判据。

**建议**: 加一条启发式规则，例如"当设备在实际现场存在≥3种不同的技术实现方式，且这些实现方式在部件结构和故障模式上有显著差异时，应拆分子设备"。

### 10. 来源引用位置不统一

COLLECT-L1/L2/L3要求"每条信息末尾用括号注明来源"，COLLECT-L4改为"每条故障信息的D3列末尾注明来源"。后者更合理（D3是文本最长的列），但前者没有明确"末尾"是指描述列的末尾还是整行末尾。

**建议**: 统一表述为"在描述列末尾用括号注明来源"。对于子行业/设备层（只有描述列），自然就是描述末尾。

## 四、缺失内容

### 11. D5 无标准阈值时的处理指引

D5要求"每个参数标注类型标签和阈值"，但实践中很多故障模式没有公开的定量阈值（尤其新设备或罕见故障）。Guide未说明这种情况怎么办。

**建议**: 在1.3节D5说明后加一句："若无公开标准阈值，可填写工程经验值并标注'（经验值）'；严禁编造阈值数据"。

### 12. 搜索无结果/LLM输出异常时的 fallback 策略

Guide描述了正常流程（搜索→收集→Judge→迭代），但未提及异常处理：
- 搜索返回0条结果时怎么办
- LLM输出非标准格式（不是表格）时怎么办
- Judge给出矛盾反馈（前后两轮要求相反）时怎么办

Pipeline代码中 base.py 已有重试机制，但Guide层面没有指导原则。

**建议**: 在章节3末尾加一个"异常处理策略"小节，简要说明搜索无结果→降低查询粒度重试、格式异常→重新生成、Judge矛盾→人工介入。

## 五、概念改进

### 13. Judge 输出格式冗余

2.4节 Judge 输出格式同时有 `completeness_issues` 和 `missing_items` 两个字段，语义高度重叠。

**建议**: 明确分工：`completeness_issues` 描述覆盖度问题（定性），`missing_items` 列出具体缺失条目名称（定量）。

### 14. "覆盖率≥95%/90%/85%" 评估方式不可操作

5.2节设定了覆盖率目标，但"Judge评估 + 行业标准对照"这种评估方式依赖Judge主观判断，不是客观度量。实际pipeline中也没有覆盖率计算逻辑。

**建议**: 要么定义可计算的覆盖率指标（如"已生成故障的部件数/总部件数"），要么改为"Judge综合评估覆盖度是否充分"的定性判断，删除硬性百分比。

### 15. equipment_classification.md 缺少质量门控检查项

步骤2.5a描述了设备分类决策文档的格式，但阶段2质量门控中只有"equipment_classification.md 已编写"这一条，缺少格式合规检查。

**建议**: 在质量门控中增加"equipment_classification.md 格式合规：每台设备有判定依据，关键边界决策已记录"。

## 六、架构改进（用户补充）

### 16. 章节4 Prompt模板应改为设计准则

**现状**: 章节4（Prompt模板）包含4套完整的 prompt 模板（COLLECT-L1/L2/L3/L4、JUDGE-COMPLETENESS/FAULT、USABILITY-TEST），与 pipeline 代码中的 collector.py、judge.py 存在两份独立维护的 prompt。

**问题**:
- Prompt 随 pipeline 迭代频繁调整，guide 中的模板很快与代码漂移（本次审查已发现 #4 和 #5 两处不一致）
- 维护两份 prompt 是纯负担，且 guide 中的版本总是滞后的
- construct_guide 的定位是「架构蓝图和设计准则」，不是「代码实现」

**建议**: 将章节4从「具体 Prompt 模板」重构为「Prompt 设计准则」，包含：
1. 各层 prompt 必须包含的设计要素（如故障层必须覆盖 D1-D9 全维度定义、来源引用、父部件约束等）
2. 各角色 prompt 的设计原则（如收集智能体 prompt 必须明确输出格式和禁止事项，Judge prompt 必须包含 Schema 锚定）
3. 删除所有具体的 prompt 全文，仅保留设计要点清单

这样 pipeline 代码是 prompt 的唯一真实来源（single source of truth），construct_guide 只定义「prompt 应该满足什么要求」而非「prompt 具体怎么写」。
