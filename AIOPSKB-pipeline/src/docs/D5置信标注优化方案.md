# D5 置信标注优化方案：提升标准值占比 + 待核实归零

> **目标**：标准值占比从 6.4% 提升至 15-25%，待核实占比从 37.8% 降至 0%
> **约束**：所有改动行业无关，后续火电/水电/核电/光伏等直接复用
> **日期**：2026-05-25
> **审阅修订**：2026-05-26（Claude，工业运维 + 多智能体视角补强）

> ⚠️ **修订说明**：原方案诊断与主干设计都正确，但在落地过程中有 4 个收敛性风险被忽略，可能导致"待核实降为 0%"的目标完成、但**经验值池被污染**、**假标准值率升高**。本次修订在不推翻原方案的前提下补强这些环节，集中体现在 **3.1.1（参数域预筛选）**、**3.5（兜底分档 + 审计）**、**3.4（Kimi unknown 出口）**、**3.7（标准号程序化反向校验）** 四处，并在第六章补一份**收敛性总结**。原作者标记为"**【原文】**"，补充/修订标记为"**【Claude补强】**"。

## 一、问题诊断

当前风电知识库 D5 子参数级统计（N=1464）：

```
标准值 only:            93 (  6.4%)
经验值 only:           817 ( 55.8%)
待核实 only:           312 ( 21.3%)
经验值 + 待核实:        242 ( 16.5%)
─────────────────────────────────
含标准值合计:            93 (  6.4%)
含经验值合计:          1059 ( 72.3%)
含待核实合计:           554 ( 37.8%)
```

37.8% 的"待核实"率由五个结构性缺口导致：

| # | 缺口 | 所在文件 | 严重度 |
|---|------|---------|--------|
| 1 | Collector prompt："不确定就标待核实"——安全优先，无最小化指引 | `collector.py` L286-289 | 高 |
| 2 | Judge 维度 12："零待核实可疑"——干净的表格反而不通过 | `judge.py` L72 | 高 |
| 3 | Kimi Phase C 选择性更新——未覆盖行里的待核实原样保留，无兜底清扫 | `standard_checker.py` L63 | 高 |
| 4 | 搜索查询：6 条仅 1 条搜标准，且限 DL/GB，无 IEC/ISO | `collector.py` L140-151 | 中 |
| 5 | 无质量门禁：validator 不拒收也不警告高"待核实"率文件 | `validate_kb.py` | 中 |

核心矛盾：**Prompt 层鼓励保守标注 → Judge 层惩罚激进标注 → Phase C 承诺消除但无强制兜底 → 残留无人负责。**

#### 3.1.1 【Claude补强】参数域预筛选 — 避免速查表噪声

**原方案问题**：18 个参数域全量注入到 Collector prompt，对一个具体部件而言（如"主轴承"）只有 3-4 个域真正相关（振动、温度、滚动轴承、油液），其余 14 个都是噪声。大段速查表会：
1. 增加约 2K token 的 prompt 长度（占用上下文）
2. **稀释 LLM 注意力**——LLM 看到"局放""安全阀""避雷器"等无关域，可能误用到当前部件
3. 增加误标——LLM 强行匹配无关标准（实测可观察到这种偏置）

**改进**：在 collector.py 中增加 `_select_relevant_domains(comp_cn, equip_cn, search_text)`，按部件名 / 设备名 / 搜索结果中出现的关键词，从 18 个域中挑选最相关的 3-5 个注入 prompt。

```python

    "齿轮磨损": ["齿轮", "啮合", "齿面", "gearbox"],
    "滚动轴承": ["轴承", "滚珠", "滚柱", "包络", "冲击脉冲", "bearing"],
    "螺栓连接": ["螺栓", "紧固", "扭矩", "预紧", "法兰"],
    "接地": ["接地", "跨步电压", "接地电阻"],

    "介电性能": ["介损", "tanδ", "介电", "电容"],
    "直流电阻": ["直流电阻", "DC resistance", "触头", "接触电阻"],
    "效率/性能": ["效率", "出力", "扬程", "流量", "功率因数"],
    "腐蚀/壁厚": ["腐蚀", "壁厚", "减薄", "氧化皮", "蠕变"],
    "水化学": ["水质", "pH", "溶解氧", "电导率", "硅酸根"],
    "安全阀": ["安全阀", "整定压力", "回座"],
}

def _select_relevant_domains(comp_cn: str, equip_cn: str, search_text: str, max_n: int = 5) -> list[str]:
    """根据部件/设备/搜索文本，从18个参数域中挑出最相关的至多5个。"""
    text = f"{comp_cn} {equip_cn} {search_text[:3000]}".lower()
    scored = []
    for domain, triggers in D5_DOMAIN_TRIGGERS.items():
        score = sum(1 for kw in triggers if kw.lower() in text)
        if score > 0:
            scored.append((score, domain))
    scored.sort(reverse=True)
    selected = [d for _, d in scored[:max_n]]
    # 兜底：若一个都没命中（少见），返回全集前5以保持 prompt 非空
    return selected if selected else list(D5_STANDARD_REFERENCE.keys())[:max_n]

### 3.2 `collector.py` — 三处改动

#### 3.2.1 D5 置信标注规则收紧（L280-293）

**当前文本：**
```
置信标注规则（每条参数末尾必须加，必须包含"置信："二字）：
- 能确认来自具体标准：（标准号-年份 条款，置信：标准值）
- 行业通用经验但无精确溯源：（置信：经验值）
- 无法确认来源：（置信：待核实）——后续将由专家审核升级或降级
...
绝对禁止在不确定时伪造标准号，不确定就标"置信：待核实"。
```

**改为：**
```
置信标注规则（每条参数末尾必须加，必须包含"置信："二字）：
- 能确认来自具体标准：（标准号-年份 条款，置信：标准值）
- 行业通用经验但无标准可引用：（置信：经验值）
- 参数数值存疑（不同文献/资料数值矛盾，无法判断哪个正确）：（置信：待核实）

标注优先级：尽量标"标准值"或"经验值"，避免依赖"待核实"。
待核实仅用于一种情况：同一参数的阈值在多个来源中数值矛盾，无法确定哪个准确。
不确定来源不是待核实的理由——找不到标准号就标经验值。
每文件待核实占比超过10%视为不合格。

禁止在不确定时伪造标准号。不确定来源就标"置信：经验值"（而非待核实）。
不确定数值就标"置信：待核实"并注明矛盾的来源。

正确示例：[物理]振动速度>7.1mm/s（适用：轴中心高≥315mm，刚性安装；ISO 10816-3:2009 表1 B/C级，置信：标准值）
正确示例：[化学]油中水分>100ppm（置信：经验值）
正确示例：[物理]磨损深度>0.2mm（某文献主张0.2mm，另一文献主张0.5mm，置信：待核实）
错误示例：[状态量]密封面磨损深度>0.4mm（置信：待核实）——来源不确定但不是数值矛盾，应标经验值
错误示例：[物理]振动速度>7.1mm/s（完全不加标注）
错误示例：[物理]振动速度>7.1mm/s（经验值）（缺少"置信："前缀）
错误示例：振动加速度传感器（这是监测手段，应填D6）
```

#### 3.3.2 对抗性审查新增维度

```

> **【Claude补强】维度 16 需要程序化前置校验配合**：让 LLM 自己核查自己引用的标准号是否真实，依然有同源偏差。更可靠的做法是**两步校验**：
> 1. **程序化校验**（详见 3.7）：在 validate_kb.py 中提取所有"标准值"参数的标准号，与 `D5_STANDARD_REFERENCE` 进行模糊匹配，发现未在白名单内的标准号 → 标记为 `unknown_standard`
> 2. **LLM 语义校验**：Judge 维度 16 处理程序化校验筛出的 unknown_standard 子集，判断是真新标准还是编造
>
> 这样 Judge 只对可疑子集深查，效率更高且漏检率更低。

#### 3.4.2 100% 给结论（含 unknown 出口）

> **【Claude补强】对原方案的修正**：强制 Kimi 对所有"待核实"参数给出"标准值/经验值"二选一的结论，会出现一种边界情况——Kimi 对该参数也完全没把握。**强行让它二选一会逼出错误标注**（误标"经验值"会污染经验值池，误标"标准值"会增加假标准值率）。

正确的设计：要求 100% 给结论，但显式允许 Kimi 在不确定时返回 `unknown`，由 orchestrator 在 Phase C 之后做兜底处理（详见 3.5 修订）。

核查规则改为：

```
- 本批次你必须对所有含"待核实"标注的D5参数给出结论
- 三种合法结论：
  · "标准值"——你能确定标准号且数值与标准一致
  · "经验值"——你确认该参数是行业经验，但无标准可引
  · "unknown"——该参数你也无把握，明确返回此标记
- fault_updates中必须包含所有含"待核实"参数的故障行，不得因"无需修改"而省略
- 切勿在自己也不确定时强行二选一
```

返回 unknown 的条目，由后续 Post-Phase-C 兜底处理（3.5）。

### 3.5 `orchestrator.py` — Post-Phase-C 兜底（分档 + 审计）

> **【Claude补强】原方案的两个问题**：
> 1. 把所有残留"待核实"直接改写为"置信：经验值"，等于把"Kimi 也搞不定的不确定参数"塞进了**经验值池**——工程师查询时无法区分"行业共识经验"和"原本应该是待核实但被强制降级的"。这会**污染经验值的可信度**。
> 2. 兜底没有审计追踪，下一轮如果想专门复查这批，没有数据基础。

**改进**：兜底引入"经验值-未核实"子标签，并写出 audit 文件。

```python
# Post-Phase-C safety net (Claude补强版)
# 原则：宁可承认不确定，也不污染经验值池
import json
from datetime import datetime

_residual = final.count("置信：待核实")
_unknown = final.count("置信：unknown")  # Kimi 显式不确定的（详见 3.4.2）
_total_fallback = _residual + _unknown

if _total_fallback > 0:
    # 写 audit trail（按部件分文件，便于后续追溯）
    audit_dir = os.path.join(REPORTS_DIR, "d5_fallback_audit")
    os.makedirs(audit_dir, exist_ok=True)
    audit_path = os.path.join(
        audit_dir,
        f"{context.get('equipment','unknown')}_{context.get('component','unknown')}.json"
    )
    audit_entry = {
        "timestamp": datetime.now().isoformat(),
        "context": {k: context.get(k) for k in ("industry","sub_industry","equipment","component")},
        "residual_pending": _residual,
        "kimi_unknown": _unknown,
        "fallback_label": "经验值-未核实",
        # 抓取所有兜底参数的上下文（前后各 40 字符），便于后续抽样复查
        "samples": _extract_fallback_samples(final, max_n=20),
        # 注：_extract_fallback_samples 需在 orchestrator.py 中实现，
        #     功能为扫描 final 文本中所有含"置信：待核实"和"置信：unknown"的行，
        #     提取前后各 40 字符作为 samples 列表（最多 max_n 条）
    }
    with open(audit_path, "w", encoding="utf-8") as f:
        json.dump(audit_entry, f, ensure_ascii=False, indent=2)

    self.log(f"    Post-Phase-C清扫: 残留{_residual}条待核实 + {_unknown}条unknown → 标记为经验值-未核实")
    self.log(f"    审计文件: {audit_path}")

    # 关键：使用"经验值-未核实"子标签，不污染纯经验值池
    final = final.replace("置信：待核实", "置信：经验值-未核实")
    final = final.replace("置信：unknown", "置信：经验值-未核实")
```

**配套修改 validate_kb.py 统计逻辑**：将"经验值-未核实"作为独立统计类别，与"经验值"分开计数。这样后续可以：
- 监控"经验值-未核实"占比作为知识库可靠性下限指标
- 高占比文件优先纳入下一轮 Kimi 复查或扩充搜索
- RAG 输出时主动告知用户"该参数未经标准核实"

**为什么不直接保留"待核实"**：D5 字段的对外语义是"已完成核查"，"待核实"会让 LLM/工程师误以为还有人工流程在跟进。改名为"经验值-未核实"明确表态：这是已经走完自动核查流程但未能溯源的数据，等同于经验值的下限可信度。

### 3.7 【Claude补强】`validate_kb.py` — 标准号反向白名单校验（后置校验）

**执行时机**：pipeline 全流程（含 Phase C 兜底）完成后，由 validate_kb.py 做离线校验。不在 pipeline 主流程内，无法回溯触发 Kimi 或修改已写盘数据。其产出为 warning 列表，供下一轮重跑时优先处理。

**目的**：与 judge 维度 16 配套，提供程序化的"假标准值"前置筛选。Judge 只对程序化筛出的可疑子集做语义判断，避免 LLM 自查自的同源偏差。

**实现**：在 `check_d5_confidence` 之后新增 `check_d5_standard_whitelist`：

```python
import re
from config import D5_STANDARD_REFERENCE

# 从映射表抽取所有合法标准号前缀（去掉年份/条款后缀）
_VALID_STANDARDS = set()
for info in D5_STANDARD_REFERENCE.values():
    for std_num, _scope in info["standards"]:
        _VALID_STANDARDS.add(std_num.upper().replace(" ", ""))

# 形如 "DL/T 5448-2014" 或 "ISO 10816-3:2009" 的标准号提取
_STANDARD_REF_PATTERN = re.compile(
    r"(?:DL/T|GB/T|GB|IEC|ISO|ASME|VDI|AGMA|IEEE|TSG|NB|HJ|JB|NAS)\s*[A-Z]?\s*\d+(?:[.-]\d+)*"
)

def check_d5_standard_whitelist(report, filepath):
    """提取所有标"标准值"的D5参数中引用的标准号，校验是否在白名单内。
    未命中的标准号 → 标记为 unknown_standard，提交Judge维度16做语义判断。"""
    headers, rows = parse_md_table(filepath)
    d5_idx = next((i for i, h in enumerate(headers) if "D5" in h or "特征参数" in h), None)
    if d5_idx is None:
        return

    unknown_refs = []  # 不在白名单的标准号
    for row in rows:
        if d5_idx >= len(row):
            continue
        d5_val = row[d5_idx]
        # 仅校验标"标准值"的子参数
        if "置信：标准值" not in d5_val:
            continue
        for std_ref in _STANDARD_REF_PATTERN.findall(d5_val):
            normalized = std_ref.upper().replace(" ", "").split("-")[0].split(":")[0]
            # 模糊匹配：normalized 是否是白名单某条的前缀
            if not any(normalized.startswith(v) or v.startswith(normalized) for v in _VALID_STANDARDS):
                unknown_refs.append(std_ref)

    if unknown_refs:
        report.results.append(CheckResult(
            level="warning", check="D5未知标准号", file=filepath,
            message=f"{len(unknown_refs)}个标准号不在白名单: {', '.join(set(unknown_refs)[:5])}",
        ))
```

**设计意图**：
- 白名单未必能穷尽合法标准（新标准、行业冷门标准），所以仅作 warning 而非 error
- 工程师/Judge 收到 warning 后人工/语义判断是真新标准还是编造
- 高占比"未知标准号"的文件优先复查
- 随着白名单维护，假标准值率会被持续压低

**为什么程序化前置很关键**：Kimi/Judge 都用 LLM，存在"我引用的标准是真的"这种自证偏差。程序化匹配是唯一不受 LLM 偏置影响的校验环节。

### 3.8 【Claude补强】经验值-未核实：终态定位与下游处理

**前提约束**：当前没有人力、没有工程师进行全量逐条核实，最多只能抽样。方案必须在此约束下自洽。

#### 3.8.1 闭环逻辑

自动化链路中，任何环节处理不了的条目，不是回到"待核实"，而是进入"经验值-未核实"——一个**已完成核查的终态**，不是等待人工的待办标记。

```
自动化全链路（无人参与即可完成）：

Collector D5          Kimi Phase C          Orchestrator 兜底        自动化终态
    │                      │                     │                      │
    │ [标准值] ──────────→ 验证通过 ──────────→ ────────────────────→ ✅ 标准值
    │                     验证失败 ──────────→ 标记为经验值-未核实 ─→ ⚠ 经验值-未核实
    │
    │ [经验值] ──────────→ 升级为标准值 ──────→ ────────────────────→ ✅ 标准值
    │                     无法升级 ──────────→ ────────────────────→ ✅ 经验值
    │
    │ [待核实] ──────────→ 升级为标准值 ──────→ ────────────────────→ ✅ 标准值
    │                     降为经验值 ────────→ ────────────────────→ ✅ 经验值
    │                     Kimi也不确定 ──────→ 标记为经验值-未核实 ─→ ⚠ 经验值-未核实
    │                     Kimi未覆盖 ────────→ 正则兜底 ───────────→ ⚠ 经验值-未核实

后置校验（validate_kb.py，pipeline 跑完后执行）：
    [白名单外标号] → 输出 warning → 人工抽样确认（非必须流程）
    高经验值-未核实占比文件 → 输出 warning → 优先纳入下一轮重跑
```

三档终态，无人参与即可完成，知识库直接可用。

#### 3.8.2 与"经验值"的本质区别

纯"经验值"：行业通用经验，工程师可放心参考。LLM/RAG 可主动推送为"建议处理方案"。

"经验值-未核实"：阈值数值大概率是对的（LLM 没编造），但溯源链断了（没标准、没可查出处、OEM 手册未公开）。你知道它大概率可用，但不敢拍胸脯。

**两者的共同点**：阈值数值有工程依据，不是凭空编造。
**两者的区别**：溯源链是否可查，决定了工程师对它的信任折扣。

**"经验值-未核实"比删除好**：没有这条，RAG 只能说"齿轮箱振动异常，建议检查"；有了这条，RAG 至少能说"参考值是 50m/s²，这个值没标准背书，但你往上走就危险了"（一个可当作基线的数字）。比没有数强，比编造的数诚实。

#### 3.8.3 三档 RAG 输出策略

三档在 JSON/CSV 存储格式上完全一致（均为 D5 字段的置信尾注），只在 RAG 回答模板上措辞差异化：

| 置信档 | RAG 输出措辞 | 信任指引 |
|--------|------------|---------|
| 标准值 | "根据 GB/T 7595-2017，油击穿电压应 ≥ 30kV" | 可放心执行 |
| 经验值 | "行业经验表明，振动速度 ≥ 7.1mm/s 应安排检修" | 可执行，保持监测 |
| 经验值-未核实 | "参考值：振动加速度 ≥ 50m/s² 建议排查，该阈值未经标准溯源，请结合现场工况确认" | 参考基线，现场验证 |

**工程师的实际使用方式**：
- 标准值 → 直接下工单
- 经验值 → 确认工况匹配后执行
- 经验值-未核实 → 当作预警基线，现场用自身经验校准 1-2 次后即可等同经验值使用

#### 3.8.4 抽样审计（非必要接口）

在全部自动化闭环之外，保留一个轻量抽样接口——不做流程依赖，仅用于工程师额外关注时的低门槛入口：

- 输出一份汇总报告：按 D2 危急度 × 故障常见度排序，列出"经验值-未核实" Top-N 条目
- 工程师有空就看，没空不影响知识库正常使用
- 不是必须流程，是额外便利

#### 3.8.5 中长期自然消解

"经验值-未核实"不会永远停留。后续通过三条零人力路径自然消解，无需逐条人工核实：

1. **标准 PDF RAG 基础设施建成后** → 程序化回溯匹配，升级为"标准值"
2. **OEM 手册入库后** → 同上
3. **下一轮全量重跑时** → Collector 搜索能力增强、速查表扩充，新生成的数据源头标注更完整，自然覆盖旧数据

这些是基础设施升级后的被动收益，不是为"经验值-未核实"专门投入的人力。

#### 3.8.6 核心态度

**承认不确定，但不丢弃信息**。

这四条是完整的：
- 比强制标"经验值"诚实——不污染纯经验值池，RAG 不会用"行业经验表明"去介绍一条无人核实过的阈值
- 比保留"待核实"干净——不承诺有人来核，不制造期待
- 比直接删除有用——给工程师一个参考基线，哪怕只能作为预警锚点
- 比逐条人工核实可行——在零人力约束下完成自动化闭环

## 六、【Claude补强】收敛性总结：四个修订点的协同关系

原方案聚焦"待核实归零"的可见目标，本次修订补强了**不可见但更关键的四个收敛性问题**。这四个修订点协同形成一道"防失真"防线：

```
                    ┌─ 速查表预筛选（3.1.1）
                    │   防止：LLM 注意力稀释 + token 浪费
   ① 标注阶段       │
   （Collector）    └─ D5_STANDARD_REFERENCE 修正（3.1）
                        防止：低质量映射诱导误标
                              │
                              ▼
                    ┌─ Kimi unknown 出口（3.4.2）
   ② 核查阶段       │   防止：Kimi 强行二选一导致错误标注
   （Kimi Phase C） │
                    └─ 标准号反向白名单（3.7）
                        防止：LLM 自证偏差，捕获假标准值
                              │
                              ▼
                    ┌─ 分档兜底（3.5）
   ③ 兜底阶段       │   防止：经验值池被污染
   （Orchestrator） │
                    └─ 审计追踪（3.5）
                        防止：兜底数据丢失，无法迭代复查
                              │
                              ▼
                    最终输出：标准值 / 经验值 / 经验值-未核实 三档
                    每档语义清晰，下游 RAG 可差异化处理
```

**核心判断**：原方案让"待核实"归零是必要的但不充分。若不引入这四个补强：
- 经验值池会被兜底数据稀释（看着 D5 数据更多有"行业经验"背书，实际多数没人审过）
- 标准值占比上升的同时假标准值率也会上升（LLM 看到速查表后随意贴标）
- 兜底没有审计，下一轮想专门复查"原本待核实"的那批，没有数据基础

补强落地后，知识库 D5 字段的对外语义才真正自洽：**每一档置信都是"已完成自动化核查后的真实置信结论"，没有任何"半成品"流入下游**。
