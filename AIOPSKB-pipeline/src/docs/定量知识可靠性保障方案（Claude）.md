# 知识库定量内容可靠性保障方案

> **维护者**: Claude + GLM
> **最后更新**: 2026-05-21
> **适用版本**: construct_guide v2.3，pipeline 现行架构

---

## 一、问题：为何定量数据是最高风险区

### 1.1 两类定量数据的本质区别

| 类型 | 来源 | 偏差后果 |
|------|------|---------|
| **A类：标准规定值** | 国家/行业/国际标准，有唯一权威依据 | 阈值错误导致误判——设备正常但报警，或已异常但漏报 |
| **B类：工程经验值** | 行业实践积累，无单一来源 | 偏差影响相对较小，但严重失真时同样危险 |

LLM 生成时不区分这两类，用相同置信度输出"振动速度>7.1mm/s"（真实 ISO 值）和"磨损深度>0.4mm"（模型合成数字）。使用者看到格式相同的条目，无法判断可信程度。

### 1.2 来源标注的设计原则

**只要求 LLM 能可靠回答的问题**。要求 LLM 引用具体文献（如"DL/T 869 第5章"），会产生虚假引用（`[1][2]` 占位或捏造标准号），比不注明来源更有危害。正确做法是让 LLM 判断一个它能回答的问题——"这个数值的可信程度是哪一类"，而不是"你从哪本书上看到的"。

### 1.3 哪些字段需要来源保障

| 字段 | 来源必要性 | 保障方式 |
|------|-----------|---------|
| D3 故障描述与机理 | **低** — 通识性工程原理，无单一来源 | 不标注（移除原有 `[1][2]` 要求） |
| D4 故障征兆 | 低 | 无需 |
| **D5 特征参数阈值** | **最高** — 定量数值直接影响判断 | 三级置信标注 + Kimi 双重核查 |
| D6 监测手段 | 低 | 无需 |
| D7 诊断方法 | 中 — 逻辑正确性比来源更重要 | Judge 对抗审查（第12条：因果充分性） |
| **D8 检修方法** | **中高** — 操作步骤安全关键 | `[规程级]`/`[经验级]` 标签 + Judge 安全审查 |
| D9 预防措施 | 低 | 无需 |

## 二、保障体系：当前 fault 层执行流程

```
Phase A：扩充（Collector × 1-2轮）
  - D5 参数：生成时打三级置信标注（标准值/经验值/待核实）
  - D8 方法：生成时打规程级别标签（规程级/经验级）
  - D3 描述：不要求来源（已移除该要求）
    ↓
Phase B：整合（Consolidation，高质量时跳过）
    ↓
Judge 对抗审查（融入现有 Judge，零额外调用）
  - 第1-9条：覆盖度、格式完整性
  - 第10-13条（对抗视角）：D5工况适用性、置信分布真实性、
    D7因果充分性、D8操作安全性
  - 发现"致命"问题 → 写入 critical_issues → orchestrator 强制重新生成
    ↓
Phase C：Kimi 标准核查（新增，每部件1次Kimi调用）
  - 消除所有"待核实"（有标准 → 升为"标准值"；无标准 → 降为"经验值"）
  - 尝试将"经验值"升级为"标准值"（Kimi 有不同于 DeepSeek 的标准覆盖）
  - 核查声称"标准值"的参数是否真实（降级 DeepSeek 的虚假引用）
    ↓
写盘：最终输出不含"待核实"
```

## 三、各方案设计原则

### 方案一：D5 三级置信标注

**核心思路**：不改列结构，在每条 D5 参数末尾追加 `（置信：标准值/经验值/待核实）`，有标准号时同时注明。

三个级别的语义：
- `标准值`：有具体标准号和条款，可查验，如 `（ISO 10816-3 表1，置信：标准值）`
- `经验值`：行业通用经验，无精确溯源，如 `（置信：经验值）`
- `待核实`：DeepSeek 不确定的临时标签，由 Phase C Kimi 核查后消除

**关键约束**：绝对禁止伪造标准号，不确定就标"待核实"，宁可保守。

**D5 参数数量**：以实际存在的可监测阈值为准，1条即可，不强制凑数。

---

### 方案二：行业标准导向搜索（暂缓）

**核心思路**：在 `collector.py` 的 fault 层搜索查询中增加"标准定向搜索"——基于 `config.py` 中维护的各子行业关联标准表（如火电-水质：`DL/T 889, GB/T 12145`），构建以标准号为锚点的搜索 query，同时从搜索结果里提取真实出现的标准号传给 LLM 作为引用候选，降低 LLM 凭记忆虚构标准号的概率。

**暂缓原因**：即使搜索带上标准号锚点，DuckDuckGo 返回的仍只是标准目录页或摘要，无法获取具体的阈值表格。LLM 最终还是靠训练数据回忆数值。标准号出现在搜索结果里能略微降低虚构引用概率，但无法解决"编造阈值"的根本问题。**真正的解决方案是标准 PDF RAG（中长期目标）**，在此之前该方案收益有限。

---

### 方案三：Verifier Agent（暂缓）

**核心思路**：在 Collector 与 Judge 之间插入一个专项数值核验 Agent，只做一件事——对已生成的 D5/D7 定量数值逐条溯源核查，返回置信判断后回写标注。

**暂缓原因**：本质是**同源验证**——用 DeepSeek 验证 DeepSeek 生成的内容，两者共享同一套训练数据，对训练数据中确实存在的标准值能正确确认，但对训练数据中模糊或缺失的值，Verifier 同样无法区分"正确但冷门"和"错误但合理"。这个角色已被**方案五（Kimi 核查）** 以更优的方式替代——Kimi 使用不同训练数据，能提供真正互补的第二视角。

---

### 方案四：Judge 对抗审查（融入 Judge，非独立 Agent）

**核心思路**：在现有 Judge 中追加 4 条对抗性审查维度（以25年工龄资深工程师视角），不新增 Agent，零额外调用。

对抗维度重点：
1. D5 工况适用性：同一参数在不同压力/材质下差异极大，是否工况错配？
2. D5 置信分布真实性：是否存在全标"标准值"零"待核实"的可疑情况？
3. D7 因果充分性：诊断条件是否充分且必要？
4. D8 操作安全性：是否存在泄压前操作、需要特种资质未标注等安全隐患？

**闭环机制**：Judge 返回的 `critical_issues` 字段（severity=致命）会被 orchestrator 捕获，强制进入下一轮重新生成，并将致命问题作为上下文传给 Collector。高分通过逻辑在致命问题前无效。

---

### 方案五：Kimi 标准核查（Phase C）

**为什么引入第二个模型**：Kimi 与 DeepSeek 训练数据不同，对中国行业标准（DL/T、GB/T）有互补覆盖。两个模型都认可的标准值，可信度远高于单模型输出；Kimi 也能核查 DeepSeek 的虚假"标准值"引用。

**执行机制**：按故障行更新 D5 列（Kimi 返回 fault_name → 新D5内容的映射），而非脆弱的参数级字符串替换。

**降级原则**：宁可降为"经验值"也不能保留虚假标准号。Kimi 不确定时，统一改为"经验值"。

---

### 方案六：来源标注重设计

**D3 来源移除**：原要求"D3末尾注明来源"产生的是无意义的 `[1][2]` 占位，机理描述本身是通识工程知识，无单一来源可引用，强制标注只产生噪声。

**D8 规程级别标签**：检修方法的权威性直接影响工程师是否可信赖执行。新增两级标签：
- `[规程级]`：操作步骤来自强制安全规程或官方维护手册（有行业强制依据）
- `[经验级]`：行业惯例或经验做法，无强制规程依据

这与 D5 置信分级的逻辑相同——问 LLM 能判断的问题（来源类别），而不是让它引用无法验证的具体文件。

## 四、AI 审查的能力边界

**可以做到**：
- 量级错误（MPa 与 kPa 混淆）
- D5 与具体设备工况的明显不匹配
- D7 诊断逻辑的因果缺陷
- D8 操作顺序的安全隐患（未泄压先操作等）
- 格式规范问题（D5/D6 混淆等）
- 识别"听起来精确但是合成数字"的模式

**无法做到**：
- 验证未被公开记录的新型故障模式
- 核对特定设备型号的 OEM 专用参数
- 替代对实际设备台账和历史故障记录的核对

**知识库的定位建议**：
- `置信：标准值` → 可直接用于 RAG 回答，引用时注明标准号
- `置信：经验值` → 可用于 RAG，在回答中注明"以下为行业经验值，请对照设备手册确认"
- `[规程级]` D8 → 工程师可参考执行；`[经验级]` → 建议结合现场经验判断
