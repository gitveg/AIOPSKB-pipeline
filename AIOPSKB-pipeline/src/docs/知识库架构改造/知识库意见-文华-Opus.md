## 意见 1：设备名称 → 设备类型；设备类型 → 设备属性

**整体判断：方向正确，但是个语义层级问题，不是改个名就完事**

文华说的是对的。现实中"设备名称"是带编号的实例（主变压器 H101），当前知识库里的"锅炉、发电机"本质是**类（class）**而非**实例（instance）**。

但要看清楚一件事：**当前知识库本身是"类型级"的知识模板，不是设备台账**。所有"主变压器"共享同一组故障模式知识，按实例来组织反而是浪费。所以这套层级是对的，**只是命名没有体现出来**。

**改名建议**：
- 现"设备名称" → "**设备类型名称**"
- 现"设备类型"（主设备/辅助设备/公用系统） → "**设备分类**" 或 "**设备角色**"（我建议用"设备角色"，"属性"太宽泛）

**一个我想确认的疑问**：知识库未来是否要对接 EAM/MES 这种实例级系统？
- 如果**会对接**：现在的命名就要改清楚，留出"设备实例（如 H101）"这一层的空间
- 如果**仅作工程师参考**：纯语义改名也行，但优先级不高

## 意见 2：部件层问题（粒度太粗 + 借鉴三 AI 评审）

**整体判断：强烈支持。粒度问题是 PHM 落地的根本性问题**

文华提了两个观察，都对：

**问题 A：设备/部件同名（"锅炉设备下还有部件叫锅炉"）**
这是 LLM 把部件层和设备层语义混了。我看了 construct_guide，已经在 0.2.1 节明确"设备 vs 部件"的判定原则了，所以这是**执行层面**的问题，不是设计问题。可以靠规则脚本快速拦截：扫描 components.md 是否包含与 equipment 同名的行，发现即报错。

**问题 B：部件粒度太粗（齿轮箱、发电机这些其实是子系统级）**

这是 PHM 行业最关键的问题，我必须展开说：

PHM 的核心原则是：**故障粒度 = 部件粒度 = 维护动作粒度**

如果"齿轮箱"是一个部件，那它的故障可能涉及 10+ 种独立失效模式（行星齿轮断齿、太阳轮点蚀、轴承内圈剥落、油泵失效、密封漏油、冷却器堵塞...），这 10+ 种故障的**根因、检测手段、检修方法、备件清单完全不同**——硬塞进一个"齿轮箱"部件下，故障层就会变成"什么都写一点，什么都写不深"。

**真正的部件粒度应该是**：齿轮箱 → 行星级齿轮组 → 行星齿轮 / 太阳轮 / 内齿圈 / 行星架。

**好消息**：construct_guide 1.1 节其实已经支持"部件多级嵌套"，问题在 pipeline 实际生成时**深度不够**——LLM 倾向于在第一层就停下。

**关于借鉴三 AI 评审扩展到部件层**：
完全支持。设备层评审有 KKS/RDS-PP 做锚点，部件层没有现成的全行业编码体系，但可以用其他维度约束。我建议评审 prompt 关注：

| 维度 | 检查点 |
|---|---|
| 命名规范 | 设备/部件不能同名（强制规则） |
| 粒度一致性 | 同一父节点下的部件粒度要一致（不能"齿轮箱+行星齿轮"并列） |
| 拆解充分性 | 叶节点是否拆到了维护动作级别（一个叶部件对应一组确定的备件和检修步骤） |
| 完备性 | 该设备的主要功能子系统是否都覆盖（机械传动、润滑、冷却、电气、控制、安全） |
| 失效独立性 | 每个叶节点部件的故障模式是否互相独立（高耦合的应合并） |

**这条优先级最高，建议先做**——粒度对了，意见 3、4 才有真正的落脚点。

## 意见 3：故障层加 5 个检维修栏

**整体判断：方向对，但要分级处理。不能全交给 LLM 生成**

文华的本质诉求是：把知识库从"**故障诊断字典**"升级为"**完整运维工作流手册**"。这个方向我认同，但 5 个新列的**性质和 LLM 可靠性不一样**：

| 新列 | 性质 | LLM 可靠性 | 建议 |
|---|---|---|---|
| 用工需求 | 经验估算（与厂家规模、班组配置强相关） | **低** | LLM 给参考值，明确标"经验估算"，留待现场修正 |
| 工机具 | 通用类目（防爆工具、扭力扳手、万用表等） | 中 | LLM 可生成通用项，具体规格留空或注明"按设备手册" |
| 备件用料 | **OEM 强相关**（具体型号、规格、品牌） | **低** | LLM 给通用名（如"柔性石墨填料环"），具体型号必须现场补 |
| 安全注意事项 | 有标准依据（HSE、特种作业规程） | **较高** | **必须加**，可以给置信标注（如引用 AQ 标准/化学品安全说明书） |
| 验收标准 | 有标准依据（ANSI/FCI、GB/T 检验规范） | **较高** | **必须加**，可以给置信标注 |

**我的核心建议**：
1. 把这 5 项做成**独立的新维度**（不是塞进 D8），便于结构化提取（生成工单时要单独取"用工需求"）
2. **不要平均用力**——安全/验收标准是有标准依据的，LLM 能生成靠谱内容；用工/备件是 OEM 强相关，LLM 只能给参考
3. 设计一个**"现场补充"标签**：标记哪些字段是 LLM 生成的、哪些是工厂实际填写的。这点很重要，否则工程师拿到一份满满"看起来很专业"的工单，结果发现备件型号都是假的——会**摧毁整个知识库的信任度**

**一个潜在的坑**：这 5 列加进去，每个故障的字段从 10 个变成 15 个，**Collector 的 token 消耗大概翻倍**，且后 5 列的质量大概率比前 10 列差很多。要做好"前 10 列是可信知识、后 5 列是补充参考"的语义分层。

## 意见 4：D1 改造 + 新增故障模式列（监测平台对接）

**整体判断：这是 4 条意见里 PHM 专业价值最高的，强烈支持**

这条意见触及了 PHM 知识库的**灵魂**。我必须详细说说为什么这条最重要。

**PHM 标准的故障层级模型**：
```
失效机制（Mechanism）—— 物理化学原理层面
    ↓
故障模式（Failure Mode）—— 监测系统直接报警的标签
    ↓
故障征兆（Symptom）—— 现场可观测现象
    ↓
故障原因（Root Cause）—— 根因分析
```

**当前知识库的状态**：
- D1 故障类别（机械/电气/绝缘/热/化学/控制/环境）= **失效机制**
- D4 故障征兆 = **故障征兆**
- D3 故障描述与机理（含根因）= **故障原因**
- **缺失：故障模式（Failure Mode）这一层**

**故障模式（不平衡/保持架/松动/轴承...）是工业监测系统的直接输出**。SCADA/CMS/DCS 系统的振动监测、油液分析、红外测温模块给出的报警标签，全都是这种故障模式级别的描述。

**没有这层，知识库就无法和监测系统对接**：
- 现场报警："主变压器主油泵 - 轴承内圈缺陷报警"
- 知识库无法用"故障模式=轴承内圈缺陷"精确匹配，只能模糊匹配 D4 征兆
- 这导致知识库**永远只能作为人工查询的字典，无法接入自动化诊断流程**

**关于"静态文件维护，不让 LLM 生成"——非常对**：

故障模式是**有限的、领域固定的枚举集**，不像 D3 描述那种开放性内容。LLM 自由生成会出现：
- 同一故障模式叫不同名字（"轴承外圈剥落" vs "外圈点蚀" vs "外圈疲劳"）
- 命名与监测系统标签对不上
- 难以做跨设备聚合分析

**正确做法**：
1. 维护一个 `failure_modes.yaml` 文件，按**部件大类**分组（旋转机械、电气设备、压力容器、阀门、变压器、热交换器、电池储能...）
2. 每个大类下列出该类设备公认的故障模式（参考 ISO 13373、ISO 17359、行业 CMS 系统标签）
3. Collector 生成故障时，**从对应大类的枚举中选择**故障模式列，而不是自由生成

**改造建议**：
- **重命名 D1**："故障类别" → "**失效机制**"（更符合 PHM 术语）
- **新增 D11/D-mode**："故障模式"，从静态 yaml 枚举中选择
- yaml 文件按部件大类（部件层评审时同步打标签）分组，由人工维护
