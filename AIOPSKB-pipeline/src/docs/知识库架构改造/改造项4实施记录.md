## 1. 改造目标

### 1.1 问题（方案 §4.1）

子设备划分过细。实证：风电机组拆了 **9 个子设备**，其中 **6 个是小众/试验性/已淘汰机型**——

| 子设备 | 标注（原 sub_equipment.md） |
|--------|----------------------------|
| 高速永磁风电机组 | 【小众技术路线，市场份额不足1%】 |
| 异步双馈混合型机组 | 【试验性技术，尚未大规模商用】 |
| 直驱电励磁同步风电机组（EESG） | 【小众技术路线，市场份额极低】 |
| 液压传动型风电机组 | 【极小众技术路线，市场份额极低】 |
| 无刷双馈风电机组 | 【技术验证阶段，尚未大规模商用】 |
| 鼠笼异步风电机组（SCIG） | 早期定速机型，新增装机近零、存量在退役 |

这些机型几乎无现场存量、无人维护，展开完整知识纯属浪费且稀释主流机型质量。

### 1.2 通用保障机制（方案 §4.2）

不是只改风电，而是建立"子设备该怎么划"的 **prompt 约束 + 评审** 通用机制。三条原则：

1. **单一维度**：只按技术路线/型号变体切分，不混功能模块（功能模块属于子系统层）。
2. **MECE**：主流路线互斥且穷尽。
3. **按存量与可维护性裁剪**：覆盖主流机型，小众/试验性机型不展开下层。

### 1.3 风电试点（方案 §4.3）+ 需求方决策

- **保留（主流）**：双馈（DFIG）、直驱（PMSG）、半直驱（中速永磁）——覆盖 95%+ 存量。
- **小众机型处理**：需求方（2026-06-15）确认——**6 个小众/试验性/已淘汰机型（含 SCIG）归档到 `_archive`**，正式目录只留 3 个主流；sub_equipment.md 裁剪为 3 行。
  - 说明：方案 §12.② 原标注"删除 vs 保留名字不展开"待确认，本次决策为"归档不列入"，与凝汽器旧数据归档同一做法（彻底从正式流程移走但留底备查）。

## 3. 代码改动明细

### 3.1 `src/pipeline/agents/collector.py`（P0 核心，sub_equipment prompt 重写）

`:245` 的 `elif layer == "sub_equipment":` 分支重写：

| 改动点 | 改造前 | 改造后 |
|--------|--------|--------|
| 列举要求 | "列出该设备下的**所有**子设备/技术路线类型" | "只列出覆盖 95%+ 现场存量的**主流**技术路线；小众/试验性/未规模化商用/已淘汰机型**不单列**（直接剔除）" |
| 新增原则 | — | 单一维度 / MECE / **按存量与可维护性裁剪** / 数量克制（2-4个） |
| 新增锚点 | — | 风电主流=DFIG/PMSG/半直驱（高速永磁/液压/EESG/无刷双馈/SCIG 不列）；锅炉主流=煤粉炉/CFB/余热锅炉 |
| 判断标准 | — | 现场存量占比 + 是否规模化商用 + 运维知识能否独立成体系 |

保留：两列输出格式 `| 子设备名称 | 描述 |`、表格前后无解释、`existing_note` 兼容。

> `_build_queries` 的 sub_equipment 搜索查询（搜"技术路线"）无需改——改的是 prompt 文案，不是搜索策略。

### 3.2 `src/pipeline/agents/judge.py`（P0 核心，新增 sub_equipment 专项审查）

在 `:36` 后、`sub_system` 专项分支（`:97`）前，插入 `if layer == "sub_equipment":` 专项 return（参照 sub_system 分支写法）。审查维度：

1. **维度单一性**：是否只按技术路线切？有无混入功能模块（把"齿轮箱""偏航系统"当子设备 = 严重问题）或容量/用途维度？互斥性自检。
2. **MECE**：主流路线互斥穷尽，有无遗漏重要技术分支。
3. **存量裁剪合理性（重点）**：是否过度细分小众/试验性/未规模化商用/已淘汰机型？市场份额极低的应剔除或合并而非单列？是否冗余？【既不冗余、又覆盖主流】为核心判据。
4. **主流覆盖**：是否覆盖主流型式（95%+ 存量）？
5. **子系统≠子设备**：子设备是技术路线变体，不得混入功能分解维度。
6. **命名一致性**：规范统一，不与上层设备同名。

返回 JSON 结构沿用 fallback：`verdict / score / missing_items / classification_issues / issues / suggestions`。`orchestrator._run_layer` 调用链通用，无需改。

### 3.3 `src/construct_guide.md`（文档同步，§2.5 补裁剪原则）

§2.5（子设备拆分）原有"维度纯度要求/维度纯度自检规则"，**新增**"按存量与可维护性裁剪（改造4）"段：

> 子设备清单只覆盖该设备的**主流技术路线（现场存量 95%+）**。市场份额极低、未规模化商用、试验性或已淘汰的机型**不单列**入正式知识库（可在归档目录备注，不展开下层知识）。判断标准：现场存量占比、是否规模化商用、运维知识能否独立成体系。通常 2-4 个主流子设备即可，宁缺毋滥。例如风电机组只列双馈(DFIG)/直驱(PMSG)/半直驱三个主流，高速永磁/液压传动/电励磁直驱(EESG)/无刷双馈/鼠笼异步(SCIG)等小众或已淘汰机型不列入。

### 3.4 三 AI 评审措辞强化（P1，对齐"不列入"决策）

| 文件 | 改动 |
|------|------|
| `src/ai_expert_review/prompts/sub_equipment_review.md:32-36` | 维度3"存量裁剪"：`市场份额极低的应合并或标注` → `市场份额极低或无现场存量的机型应剔除或合并，不得单独成行列出`；判据由"既不冗余又覆盖全" → "只覆盖主流（95%+），既不冗余又覆盖主流" |

## 5. 设计决策记录

### 5.1 为何采用"归档删除"而非"保留名字不展开"

需求方决策（2026-06-15）。优点：
- 正式目录干净，`run_component` 天然只处理 3 个主流，**无需新增"跳过小众"逻辑**。
- 与凝汽器旧数据归档同一做法，机制统一。
- 小众机型仍留底 `_archive`，日后风电若上小众机型可回查。

### 5.2 为何不改 schemas.py / loader.py / response_parser.py / 转换脚本

- `schemas.py` 全文无 sub_equipment 定义——子设备格式约束由 orchestrator `_consolidate` 的 `format_rules["sub_equipment"]` 和 validate_kb.py SCHEMA 承载，不在 schemas.py。
- `response_parser.py` 校验是 layer-agnostic 的，`ALLOWED_LEVELS` 已含 sub_equipment；新增裁剪维度只是 issues/redundant 里多出条目，不改 schema。
- `loader.py` 保持两列（name/desc），本次不扩列（不让评审依赖"存量占比"数据，靠专家常识+collector 锚点判断）。
- 转换脚本（md_to_json/json_to_csv/track_progress/rerun_d5）纯数据搬运/路径解析，不含裁剪逻辑；保持 sub_equipment.md 两列表头，`validate_kb.py:39` 表头校验不变。

### 5.3 为何不改 orchestrator 调用链

`_run_layer` 对所有 layer（含 sub_equipment）统一走"扩充→judge→整合"，sub_equipment 已自动经过 judge。`_identify_sub_equipment_needs` 的拆分门槛健康（"宁可漏判也不要过度拆分"）。`run_component` 按 sub_equipment.md 清单处理——裁剪后清单只有 3 个主流，天然不处理小众。

### 5.4 三 AI 评审为何只改措辞不改结构

`prompts/sub_equipment_review.md` 的"存量裁剪"维度本已存在，专家角色也已就绪。改造4 的增量是"裁剪强度"（标注 → 不列入），故仅对齐措辞，不新增维度/不改 JSON schema。

## 9. 结论

## 10. 附录：LLM 实跑与三 AI 评审验证（2026-06-16）

> 本节为改造4 主实施（2026-06-15）后的补充验证，用真实 LLM 跑通"collector → judge → 三 AI 评审"链路，验证各环节实际效果。

### 10.1 验证目的与方式

代码改完后尚未用真实 LLM 跑过。本次用独立试跑脚本 `src/scripts/_trial_run_sub_equipment.py`（支持 `full` 完整 `_run_layer` 流程 / `raw` 单次裸调用，可指定任意 sub/equip）实跑两个设备，验证：① 新 prompt 能否让 LLM 自动裁剪小众、产出与标准答案一致？② judge 专项审查、三 AI 评审在真实数据上是否生效、能否兜底？

### 10.2 风电试跑（有锚点）：与标准答案一致

完整 `_run_layer` 流程（扩充+judge+整合）产出 **3 个主流**：双馈(DFIG) / 直驱(PMSG) / 半直驱（中速永磁）。**与标准答案完全一致、零小众**，第1轮 judge 就 9 分高分通过。

### 10.3 循环论证发现 + 锚点调整

事后核查发现：collector prompt 的"锚点示例"里**直接写明了风电机组的标准答案**（DFIG/PMSG/半直驱，小众不列）。LLM 产出这 3 个本质是"照锚点抄"——**循环论证**，不能证明独立裁剪能力。

需求方决策（2026-06-16）：**只保留经实际验证的风电锚点，删除未验证的锅炉锚点**（原 prompt 锚点含风电+锅炉两行）。理由：已验证答案可作 few-shot 保生产质量；未验证答案当锚点会把不确定信息当标准误导 LLM。collector.py 锚点现为仅风电一行，措辞标注"仅列已实际验证的设备"。

### 10.4 锅炉试跑（无锚点）：暴露 LLM 独立裁剪短板

删锅炉锚点后试跑锅炉（火电），验证 LLM 独立能力。产出 **4 个**：火管锅炉 / 水管锅炉 / 循环流化床锅炉 / 链条炉排锅炉。**3 个严重问题**：

1. 🔴 **漏绝对主流煤粉炉**（火电 90%+ 装机）
2. 🔴 **抓错对象**——偏向工业锅炉（火管/链条是工业供热炉，非发电炉）
3. 🔴 **维度混乱**——火管/水管（结构维度）与 CFB/链条（燃烧方式维度）混维度并列

judge 第1轮判 3 分（正确拦截），但 `_run_layer` 的 **2 轮扩充上限耗尽后，最后一轮未经 judge 就放行**（机制盲点）。**结论：LLM 无锚点时独立裁剪不可靠；judge 能发现问题但受轮次约束兜不住底。**

### 10.5 三 AI 评审兜底：两位专家一致"需重做"，精准纠错

将锅炉试跑的 4 个不合格结果喂给三 AI 评审（`AI_Expert.py review --layer sub_equipment`，DeepSeek + Kimi 两轮辩论）：

| 专家 | R1 | R2 | 判定 |
|------|-----|-----|------|
| DeepSeek | 2.5 | 2.0 | 需重做 |
| Kimi | 2.0 | 2.0 | 需重做 |

两位专家**独立审查却高度趋同**（R2 趋同提前结束），精准指出全部问题（与 §10.4 人工评判完全吻合）：混维度=致命、漏煤粉锅炉=致命、水管锅炉互斥性=严重（结构共性非独立路线）、火管/链条炉=剔除（工业锅炉火电无存量）；遗漏项=煤粉锅炉（必补）+ HRSG（若覆盖联合循环）。报告留存 `src/ai_expert_review/reviews/boiler_sub_equipment/`。

### 10.6 模拟仲裁 + 闭环验证

模拟仲裁（主智能体基于双方意见，**未落地**）：双方共识全采纳；Kimi 单方"CFB 命名规范化为'循环流化床锅炉（CFB）'"采纳（低成本）；HRSG 边界——基于 thermal/boiler 现有体系已含 HRSG 子设备目录，纳入。

**模拟仲裁最终建议清单 = 煤粉锅炉 / 循环流化床锅炉（CFB）/ 余热锅炉（HRSG）—— 恰好等于 thermal/boiler 现有的 3 个正确答案。**

闭环证明：**即便 LLM 第一遍裁错，三 AI 评审 + 仲裁能纠正回正确答案。**（试跑的 4 个临时结果已清除，thermal/boiler/sub_equipment.md 已还原为原有 3 个正确答案。）

### 10.7 四道防线模型（改造4 完整质量保障）

| 防线 | 作用 | 锅炉验证表现 |
|------|------|-------------|
| collector 裁剪原则 | 第一遍尽量产对 | ❌ 无锚点时失效（产 4 个不合格）|
| judge（pipeline 内置）| 快速拦截明显问题 | 🟡 第1轮判 3 分拦住，但轮次上限后放行 |
| **三 AI 评审 + 仲裁** | **深度评审、精准纠错** | ✅ **兜底成功，纠正回正确答案** |
| 人工验证 | 锚点准入 | ✅ 风电已验证，锅炉经此轮可确认 |

**核心结论**：改造4 机制整体可靠——LLM 独立裁剪虽不稳，但三 AI 评审 + 仲裁是有效兜底。新设备子设备划分应走"LLM 初生成 → 三 AI 评审 → 仲裁 → 人工确认后转锚点"的完整流程，而非单靠 collector。
