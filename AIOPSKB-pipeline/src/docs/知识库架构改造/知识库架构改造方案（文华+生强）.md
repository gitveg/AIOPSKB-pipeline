## 改造 2：结构分解层 —— 部件层拆为「子系统 / 部件 / 零件」（生强意见2 + 文华意见2）

**这是本次改造的核心。**

### 2.1 背景

当前部件层是**任意深度的父部件/子部件树**，语义扁平：一个节点是"子系统级"还是"零件级"在表格里看不出来，导致：
- 粒度太粗（齿轮箱、发电机这种子系统级的东西被当作"部件"），故障层"什么都写一点、什么都写不深"
- 设备/部件同名（"锅炉设备下还有个部件叫锅炉"）
- 层级关系混乱，不利于编码、索引和表格展示

### 2.2 改为固定三层语义结构

部件层拆解为三个**固定语义层级**，统称 **「结构分解层」**（对外讲架构时使用的统称，不进入表格内容）：

```
子系统（Sub-system）→ 部件（Component）→ 零件（Part）
```

**标准锚点**：该三层映射 ISO 14224（工业设备可靠性数据采集标准 / PHM-RCM 领域基准）的设备分类法层级 **Sub-unit → Component/Maintainable item → Part**。评审与命名可引用此标准。

**完整层级链**（以风电为例）：

```
风电(子行业)
  └ 风电机组(设备)
      └ 双馈机组 / 直驱机组(子设备 = 技术路线变体)
          └ 传动系统(子系统)
              └ 齿轮箱(部件)
                  └ 行星齿轮 / 太阳轮 / 轴承 / 密封(零件)
```

### 2.3 关键概念厘清：子系统 ≠ 子设备（务必区分）

这是落地时最易出错的地方，必须分清两个**正交的轴**：

| 层级 | 划分维度 | 例子 |
|------|---------|------|
| **子设备** | 技术路线 / 型号变体（同一设备的不同"种类"） | 双馈机组 / 直驱机组 / 半直驱机组 |
| **子系统** | 功能分解（同一台设备由哪些功能模块组成） | 风轮系统 / 传动系统 / 偏航系统 / 液压系统 |

- 子设备在**上**（变体轴），子系统在**下**（功能轴），子系统挂在各自的子设备之下。
- **不可把功能子系统（如齿轮箱）当作技术路线变体放进子设备层。**
- 变体会影响子系统构成（直驱机组**无齿轮箱**），所以结构分解树必须按子设备分别展开，不能跨变体共用一套。

### 2.4 层级深度规则（> **注意：子设备层是按需存在的，不强制要求。** 只有当设备确实存在多种技术路线变体（如火电锅炉的煤粉炉/CFB/HRSG、风电机组的双馈/直驱/半直驱）时才拆分子设备。如果设备没有明显的技术路线差异（如凝汽器、主变压器等），则**不设子设备层**，直接从设备目录进入子系统层（sub_system.md）。不可为了凑层级而强行拆分子设备。

已确认）

- **固定三层语义，不再开放自由"子部件"层级**。理由：自由子部件会让我们退回"任意深度树"的老问题，固定语义是本次改造的核心价值。
- **允许短链**：简单结构可提前终止（如某传感器："某子系统→该传感器(部件)"，无零件则零件列填"—"）。
- **优先拆到零件级**（鼓励拆深，因为故障天然挂零件级），但**禁止为填满三层而虚构零件**——真实结构到哪层就到哪层，不准注水（与故障层"少而准优于多而泛"同一纪律）。
- **遇到三层装不下的超复杂设备**：不是加第 4 层，而是重新审视子系统/部件的边界切分（通常是子系统切粗了），由三 AI 评审把关。

子系统 / 部件 / 零件是**真实的嵌套目录层级**，每个层级对应一个目录。

**新增文件**：每个子设备目录下新增 `sub_system.md`（与 `sub_equipment.md` 同格式），列出该子设备的功能子系统清单：

## 改造 3：属性挂载规则（多轮讨论已锁定）

三层各自承载的属性已确认，**一条规则统管所有"作业类"属性**：

| 结构层 | 名称+描述 | 易损标识 | 故障 / 故障类别 | 维护方法 | 报废方法 |
|--------|----------|---------|----------------|---------|---------|
| **子系统** | ✓ | — | ✗（纯结构归类/导航层） | ✗ | ✗ |
| **部件** | ✓ | ✓ | ✓（整体 / 总成级失效） | ✓ | ✓ |
| **零件** | ✓ | ✓ | ✓（具体失效 + 故障类别） | ✗（上挂到部件） | ✗（上挂到部件） |

**规则要点**：
1. **故障**挂在部件层（整体/总成级失效）和零件层（具体失效），沿用现有"父节点写整体失效、避免与子节点重复"的分工逻辑。**子系统层不挂故障、不加故障列**。
2. **跨部件耦合故障**（如齿轮箱-发电机对中不良、传动链扭振、共用油路串联污染）不单独建子系统故障，**归挂到耦合关系中最核心的可维护部件上**，并在故障描述中注明涉及的其他部件。
3. **维护方法、报废方法只挂部件层**。理由：日常保养与报废处置基本是总成级动作；零件级太琐碎。此规则顺带解决"齿轮箱整体换油"这类总成级保养的归属——直接挂齿轮箱部件行，不下放到零件。
4. 子系统层仅有"名称 + 描述"两个属性。

## 改造 4：子设备划分保障机制（生强意见3）

### 4.1 问题

当前子设备划分过细。实证：风电机组拆了 **9 个子设备**，其中 4 个标注"小众/试验性/极小众/市场份额不足1%"（高速永磁、异步双馈混合、电励磁直驱、液压传动、无刷双馈等）——这些几乎无现场存量、无人维护，展开完整知识纯属浪费且稀释主流机型质量。

### 4.2 改造目标：不是只改风电，而是建立通用保障机制

把"子设备该怎么划"做成 prompt 约束 + 三 AI 评审的通用机制。**子设备划分原则**：

1. **单一维度**：只按技术路线/型号变体切分，不混入功能模块（功能模块属于子系统层）。
2. **MECE**：主流路线互斥且穷尽，不重叠。
3. **按存量与可维护性裁剪**：覆盖主流机型，小众/试验性机型不展开下层。

### 4.3 风电试点

- **保留**：双馈（DFIG）、直驱（PMSG）、半直驱（中速永磁）——覆盖 95%+ 存量。

## 改造 5：物理属性重命名 + 新增故障类别列（文华意见4）

### 5.1 PHM 故障层级模型（设计依据）

```
物理属性（Mechanism）—— 物理化学原理层面（机械/电气/绝缘/热/化学/控制/环境）
    ↓
故障类别（Failure Mode）—— 监测系统直接报警的标签（不平衡/保持架/松动/轴承缺陷…）
    ↓
故障征兆（Symptom）—— 现场可观测现象（≈ 现 D4）
    ↓
故障原因（Root Cause）—— 根因分析（≈ 现 D3）
```

当前知识库**缺失"故障类别"这一层**，导致无法与监测平台（SCADA/CMS/DCS）的报警标签对接，只能做人工查询字典，无法接入自动化诊断。

### 5.2 改造内容

**(a) 原 D1「故障类别」重命名为「物理属性」**
- 取值不变：机械/电气/绝缘/热/化学/控制/环境。
- 文华原话："本质是物理属性类别，可以改名叫做物理属性"。
- 列名改为 `D1 物理属性`。

**(b) 新增「故障类别」列**
- 内容 = 公司监测平台已有的故障分类标签（不平衡、保持架、松动、轴承缺陷…）。
- **由静态文件维护，LLM 不自由生成**——只能从枚举中选择，避免同义异名（"轴承外圈剥落" vs "外圈点蚀"）和与监测标签对不上。
- 标签库**已有现成、由人工提供**。
- 列名定为 `故障类别`（与公司监测平台术语一致，不使用学术化的"故障模式"）。

### 5.3 静态标签文件设计

- 新建 `failure_categories.yaml`（人工维护）。
- 按**部件/零件类型**分组（旋转机械、轴承、齿轮、电气绕组、变压器、阀门、热交换器…），每组列出该类公认故障类别标签（对齐公司监测平台 + 参考 ISO 13373 / ISO 17359）。
- Collector 生成故障时，按当前部件/零件所属类型，**从对应分组枚举中选择**故障类别，禁止自创。
- 故障类别天然是**零件级**标签，零件层拆出来后归属最干净（呼应改造 2）。

### 5.4 执行要点

- 改 `construct_guide.md` 的 D1 定义（重命名为"物理属性"）+ 新增故障类别维度定义。
- 改 `collector.py` 故障层 prompt：注入对应部件类型的故障类别枚举，要求从中选择。
- 改 `validate_kb.py`：校验故障类别列的值必须在 `failure_categories.yaml` 白名单内。
- `failure_categories.yaml` 的部件类型分组，可在结构分解层评审时同步给部件/零件打类型标签。

## 改造 6：故障层新增检维修 5 列（文华意见3）

### 6.1 目标

把知识库从"故障诊断字典"升级为"完整运维工作流手册"，新增 5 个检维修维度。

### 6.2 5 列定义与生成策略

**已确认：5 列完全由 LLM 生成，但每条内容必须标注置信度（标准值 / 经验值），复用现有 D5 置信标注机制。**

| 新列 | 内容性质 | LLM 可靠性 | 生成要求 |
|------|---------|-----------|---------|
| 用工需求 | 工种 + 人数 + 预计工时（如"仪表检修高级工1名、工艺维护1名；工时4-6h"） | 低（经验估算） | 标"经验值"，作参考 |
| 工机具 | 通用工具类目（防爆工具套装、扭力扳手、数字万用表） | 中 | 通用项标"经验值"，规格依设备手册 |
| 备件用料 | 备件/耗材通用名（柔性石墨填料环、高温润滑脂） | 低（OEM 强相关） | 给通用名标"经验值"，具体型号现场补 |
| 安全注意事项 | HSE / 特种作业规程要求 | 较高（有标准依据） | 有标准依据的标"标准值"并引用（AQ 标准、化学品安全说明书等） |
| 验收标准 | 检验规范、量化验收指标 | 较高（有标准依据） | 有标准依据的标"标准值"并引用（ANSI/FCI、GB/T 等） |

### 6.3 Token 成本应对策略

故障表列数从 11 列（D1-D10 + 故障名称）增至 17 列（+ 物理属性重命名 + 故障类别 + 检维修5列），单条故障 token 消耗大幅增加。

**应对方案**：
- **分段生成**：将故障层 collector 拆分为两段调用。第一段生成核心诊断列（D1-D10 + 故障类别），第二段生成检维修 5 列（携带第一段输出作为上下文）。这样每次 LLM 调用的输出量可控，避免单次调用因 max_tokens 截断导致表格不完整。
- **后续 token 预算评估**：实施前先用 3-5 个零件试跑，测量实际 token 消耗，再确定 max_tokens 和分段策略。
- **语义分层告知下游**：原诊断维度是核心知识，检维修 5 列是补充参考（用工/备件 OEM 强相关，准确率天然低于前者）。建议 RAG 输出时对这 5 列注明"参考值，需对照现场实际"。

### 6.4 执行要点

- 这 5 项做成**独立维度列**（便于工单系统单独提取"用工需求"等），不塞进 D8。
- 沿用 D5 的置信标注体系（标准值/经验值），安全/验收这种有标准依据的鼓励标"标准值"并带标准号。
- **注意成本**：故障表列数大幅增加，Collector token 消耗显著上升，需评估 max_tokens 与分段生成（见 6.3）。
