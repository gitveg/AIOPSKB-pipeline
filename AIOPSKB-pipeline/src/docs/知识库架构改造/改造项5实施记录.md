## 1. 改造目标

### 1.1 改造项5(a)：D1 列重命名

原 D1 列名"故障类别"的取值为机械/电气/绝缘/热/化学/控制/环境——这些本质是物理化学失效机制（PHM 术语中的 Mechanism），不是监测系统直接报警的故障标签。

| 项目 | 改造前 | 改造后 |
|------|--------|--------|
| 列名 | D1 故障类别 | D1 物理属性 |
| 取值 | 机械/电气/绝缘/热/化学/控制/环境 | 不变 |

### 1.2 改造项5(b)：新增故障类别列

在 D1 之后插入新列"故障类别"，值从静态 YAML 文件枚举选取，LLM 禁止自创。

| 项目 | 说明 |
|------|------|
| 数据来源 | `failure_categories.yaml`（人工维护） |
| 组织方式 | 按部件类型分组（旋转机械、齿轮传动、电气绕组等12组） |
| 匹配方式 | 关键词自动匹配部件名，无匹配时使用"通用"分组 |
| 参考标准 | ISO 13373 / ISO 17359，对齐公司监测平台标签 |
| 表格变化 | 11列 → 12列 |


## 7. 平台标签对齐重构 + Phase 4 验证（2026-06-15）

> **背景**：初版 `failure_categories.yaml` 基于 ISO 标准（13373/17359）和领域知识编写，未与公司监测平台真实标签对齐。本次向公司技术人员取得 PHM 数据库访问脚本后，导出真实故障案例数据，将故障类别标签**从理论改为平台对齐**，并完成 Phase 4 实跑验证，正式关闭 §5.4"待验证"项。

### 7.1 数据来源：公司 PHM 数据库

新增脚本 `src/scripts/数据仓库外发.py`（基于技术人员提供的访问脚本改造），连接 PHM PostgreSQL 库（`alg_analysis`），导出 5 张关键表到 `src/scripts/db_export/`：

| 表 | 行数 | 用途 |
|----|------|------|
| `tools_enum_info` | 857 | 枚举字典（32 类，含 devicetype/alternatortype/alarmtype 等）|
| `diag_fault_case` | 1000 | **故障案例（核心）**，含 `fullfaulttypename` 层级故障分类 |
| `diag_fault_alarm` | 5000 | 故障报警记录 |
| `stat_device_info` | 5000 | 设备信息 |
| `business_device_condition_point` | 5000 | 工况测点清单 |

**关键发现**：平台**没有**预定义的"故障类别"枚举表；故障分类通过 `fullfaulttypename` 字段动态构建，格式为 `设备大类/部件/子部件/.../故障类型`，末段为失效模式（润滑不良/剥落/点蚀…）。

### 7.2 failure_categories.yaml 重构

**对齐方法**：故障类别 = `fullfaulttypename` 末段（失效模式）；位置信息（内圈/外圈）由知识库"零件"列承载，不进入故障类别——与平台层级一致。

**关键洞察**：平台故障类别是"跨部件通用的失效模式"（磨损/剥落/断裂…），同一模式出现在多个部件族。故采用"部件族分组（服务关键词匹配）+ 平台对齐叶子值"的设计。

| 项 | 初版（2026-06-08） | 本次重构（2026-06-15） |
|----|-------------------|----------------------|
| 数据来源 | ISO 标准理论 | PHM 平台 970 条真实案例 |
| 分组数 | 12 族 + 通用 | **13 族 + 通用** |
| 标签风格 | 含部件特征（轴承外圈缺陷）| 平台失效模式（剥落/点蚀）|
| 唯一标签数 | 96 | **59**（53 来自平台 + 6 标准补充）|
| 故意排除 | — | 排水孔堵塞（过细）、故障（无信息量）|

13 个部件族：滚动轴承、滑动轴承、齿轮传动、联轴器、转子叶轮、紧固基础、流体系统、密封、结构本体、电气绕组、控制元件、挠性传动、通用（兜底）。

### 7.3 select_failure_categories 改进

初版将"零件名+设备名"混合匹配，存在两类误判。本次改为**两层匹配 + 长度加权**：

| 改进点 | 说明 |
|--------|------|
| 零件名优先（权威）| 故障类别描述"零件"失效，不应被设备名干扰（齿轮箱里的轴承仍是轴承故障）|
| 设备名回退 | 仅当零件名匹配不到任何分组时，才用设备名+搜索文本 |
| 关键词长度加权 | 长关键词权重高，解决子串重叠（"石墨轴承"含"轴承"不再误判为滚动轴承）|

验证：28 个真实部件用例全部通过（含边界：石墨轴承→滑动轴承、轴承外圈+齿轮箱→滚动轴承、联轴器本体→联轴器）。

## 8. 修正：故障类别列移至第2列（2026-06-16）

### 8.1 背景
改造5 实施时把新增的"故障类别"列插在 D1 物理属性**之后**（第3列）。复盘发现：故障类别（失效模式，如结垢/泄漏/堵塞）是故障最核心的分类标签，应紧跟故障名称（第2列），比 D1 物理属性（机械/化学，次级归类）更靠前，便于一眼定位。新顺序：`故障名称 | 故障类别 | D1 物理属性 | D2 … | D10`。

### 8.2 改动
- **列顺序调整**（故障类别从第3列移到第2列）：`collector.py`、`orchestrator.py`（`_build_fault_table` + `_consolidate`）、`validate_kb.py`（SCHEMA + FAULT_REQUIRED_COLS）、`json_to_csv.py`、`construct_guide.md`。
- **按列索引同步**：`validate_kb.check_required_fields_fault` 改为**按表头名报告**（不再 `f"D{j}"` 按索引，更健壮、不受列顺序影响）；`check_phase4_output.py`、`fix_fault_categories.py` 同步列索引。
- **数据迁移**：凝汽器 **55 文件 / 321 行**（= 55 表头 + 266 数据，与 Phase4 规模吻合）机械互换第2、3列；跳过 `_archive` 与旧 11/10 列格式。迁移脚本用完已删。

### 8.3 连带修复改造5 遗漏 bug
探查发现 `md_to_json.py` 的 `FAULT_COLUMNS` 和 `DIM_MAP` 原本**不含"故障类别"**——解析时该列被丢弃、不进 JSON。本次顺带修复（`FAULT_COLUMNS` 补故障类别置第2列 + `DIM_MAP` 加精确映射）。修复后 JSON 含故障类别字段 282 条。

### 8.4 验证（零回归）
- 语法检查全过；`validate_kb --stage 4` 凝汽器通过。
- 全量回归 **643 ERROR / 3347 WARN**（与修正前完全一致，零回归）。
- `check_phase4_output`：12 列 100%、故障类别合规 266/266、分布正确（破裂/裂纹/结垢等 27 种，不再误显 D1 物理属性值）。
