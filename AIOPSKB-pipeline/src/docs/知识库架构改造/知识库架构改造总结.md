# 知识库架构改造 — 总结与成果

> **周期**：2026-06-05 ~ 2026-06-25
> **范围**：风电「风电机组」三机型（DFIG / 半直驱 / PMSG）知识库
> **状态**：✅ 架构改造完成，三机型数据落地并达标

---

## 一、背景与目标

基于**文华 + 生强**两位专家的架构改造意见（见 `知识库架构改造方案（文华+生强）.md`），对风电知识库进行系统性重构，目标：

1. 建立**三层结构**（子系统 → 部件 → 零件），替代旧的扁平部件表
2. 故障表从 11 列（D1故障类别…D10）升级为 **17 列**（独立故障类别 + D1物理属性 + D2-D10 + D11-D15 检维修）
3. 故障类别对齐公司 **PHM 监测平台真实标签**（静态枚举，禁止自创）
4. 段式编码全局唯一、可解析
5. 三机型子系统**统一骨架**，支持跨机型同位检索

---

## 二、最终架构

### 数据结构
```
行业 → (子行业) → 设备 → (子设备) → 子系统 → 部件 → 零件 → 故障
                              （三层）         （17列故障表）
```

### 17 列故障表
`故障名称 | 故障类别 | D1物理属性 | D2故障等级 | D3机理 | D4征兆 | D5特征参数 | D6监测手段 | D7诊断 | D8检修 | D9预防 | D10易混淆 | D11用工 | D12工机具 | D13备件 | D14安全 | D15验收`

### 统一的 10 子系统骨架（三机型共用）
风轮系统 / 变桨系统 / 传动系统 / 发电系统 / 变流与并网系统 / 偏航系统 / 控制系统 / 塔架与支撑系统 / 冷却与散热系统 / 润滑与液压系统

> 拓扑差异（齿轮箱级数、双馈/永磁、部分/全功率变流）仅在传动/发电/变流子系统的**描述**中体现，不破坏骨架。

### 段式编码（改造7）
`{行业2}-[子行业2]-{设备3}-[子设备3]-{子系统3}-{部件3}-{零件3}-[{故障3}]`

## 六、模型配置演进

### 早期（DeepSeek 全流程）
collector/judge/Phase C 全用 DeepSeek-V4-Pro，质量高但 API 配额消耗大。

### 当前（多模型分工）
| 环节 | agent | 模型 | 理由 |
|------|-------|------|------|
| Phase 3 结构生成 | structure | **DeepSeek** | token 少(~1%) + 质量关键 |
| Phase 4 故障生成 + judge | collector/judge_b | **GLM** | 量大省配额 |
| Phase C 标准核查 | verifier | Kimi/DeepSeek（待定）| 开关控制（当前关闭，Gemini 不可用）|

**GLM vs DeepSeek 质量对比**（PMSG vs DFIG/半直驱）：
- GLM **更听话**：故障类别自创少、D5置信更全、单置信0重复（PROMPT 约束下执行好）
- DeepSeek **更深**：D3机理链完整、D5多维参数、D8工艺方法具体
- 结论：DeepSeek 生结构（关键保深度）+ GLM 生故障（量大省配额）+ judge/治理兜底，分工合理

## 七、工具链增强

### validate_kb.py（多轮强化）
- D5 拆分改 `[标签]` 边界（原按 `；` 拆误判参数项内部分号）
- 故障类别：分隔符校验（禁半角`;`）+ 数量校验（限1-3个）+ 多值原子合规
- D2 严重度：梯度判断（关键部件同质合理分布不报）
- D5 标准号：放宽白名单（格式合法即允许，judge 把关真实性）
- parse_md_table：列数告警（消除静默丢弃）

### md_to_json.py
- 列数≠表头时告警（修复前静默跳过整行，导致数据丢失无感知）

### export_xlsx.py / json_to_csv.py
- **修复故障类别孤儿列 bug**：`_build_row` 漏填"故障类别"键，导致 JSON 有值但 xlsx 全空
- 新增 `_verify_xlsx` 自检：导出后读回，逐列对比非空数，不一致即报错（防字段遗漏）

### collector.py / judge.py / standard_checker.py（PROMPT 强化）
- D1 强制 7 枚举、单元格格式、故障类别多值全角分号+限1-3个、"其他"防滥用
- **单置信约束**：每参数恰好一个置信标注 + 重复标注反例（消除 D5 重复置信）
- judge 第21项 D2 分布均衡审查
- standard_checker：替换原置信非追加（防 Phase C 未来启用复发）

## 十、经验沉淀

### "表面通过"陷阱（本次重点攻克的反模式）
1. **validate 盲点**：递归遍历遗漏、参数项内部；误拆 → 抽样通过 ≠ 批量合规
2. **导出层丢字段**：JSON 有值但拍平时丢弃（孤儿列）→ 源正确 ≠ 产物正确
3. **JSON 静默丢弃**：列数不匹配行被跳过无告警 → 数据丢失无感知
4. **D5 重复置信**：Phase C 升级追加未清旧 → 标注矛盾

### 长远约束 > 临时手动修复
每个数据问题都配套：① 数据清理 ② PROMPT 强化（防再生）③ validate 校验（拦截）。例：故障类别多值规范 = 数据映射 + collector 单置信约束 + validate 分隔符/数量校验。

### 核心原则（贯穿全程）
**真实有效**：不接受表面通过 / 循环论证 / 数据污染。每次修复都 dry-run → apply → 复验，关键改动加自检兜底。
