## 1. 问题是怎么被发现的

### 1.1 validate --stage 4 递归遍历盲点（已修复）

`validate_stage4` 原实现只检查 `target/faults/*.md`（设备层 faults 目录），但新格式三层结构下故障文件在 `子系统/部件/faults/`。当 `--target` 指向设备层（如 `风电机组/双馈异步风电机组（DFIG）`）时，**遍历 0 个文件 → 0 WARNING（假阴性）**。

**修复**（`validate_kb.py` 1327-1366）：改为 `os.walk(target)` 递归收集所有 `faults/` 目录下的 `.md` 文件。修复后重新校验立即报出 384 WARNING。

> 此盲点意味着：**在此修复前，任何故障层数据问题（D1 取值、故障类别、置信标注、编码）在 `--stage 4` 都不会被检测**。凝汽器等已迁移设备若用 `--stage 4` 校验过，结论"通过"也是假阴性，需用修复后的 validate 重新校验。

## 2. 根因分析

### 2.1 validate 层（已修复）
`--stage 4` 不递归 → 假阴性。**已修复**。

### 2.2 collector/judge prompt 层（待修）
384 WARNING 中 194 处内容类问题，根因在故障生成 prompt：

- **D1 物理属性**：collector prompt 未强制"D1 只填纯物理属性枚举（机械/电气/绝缘/热/化学/控制/环境），失效机理（疲劳/磨损/老化）归 D3"，导致 LLM 把机理塞进 D1。
- **故障类别**：prompt 未禁止括号注释（如"变形（腐蚀诱发松动）"），未强制从 `failure_categories.yaml` 白名单精确匹配。
- **D5/D8/检维修置信标注**：prompt 对置信标注的"每条必带"约束不足，judge 的 1-20 项对抗审查未覆盖"置信标注完整性"维度。
- **D2 严重度偏置**：无分布均衡约束，LLM 倾向把多数故障标"严重"。

### 2.3 Judge 层（待评估）
轮毂总成空壳故障通过了 Judge（生成"无相关故障信息"占位符却未被拦截），说明 Judge 对"空壳/占位符"识别不足。

## 3. 逐个解决路线（按优先级）

> 修复顺序：**严重性 × 可修复性**。数据损坏 > 核心字段污染 > 内容质量 > 标准时效。
> 每项标注【状态】：🔴待决策 / 🟡进行中 / 🟢已完成

### 路线 1：必填字段空 —— 轮毂总成部件级空壳【🟢已完成】

- **问题**：`风能捕获子系统/轮毂总成/faults/轮毂总成.md` 唯一一行是占位符，故障名称="无相关故障信息…"，D1-D7 全 `—`，类别="其他"。
- **根因**：LLM 搜索轮毂总成**部件级**故障无果，生成空壳；Judge 未拦截。零件级（轮毂主体/导流罩）故障正常。
- **修复选项**：
  - A. 重生成 `--comp 轮毂总成 --force`（可能仍无果）
  - B. 手工编写部件级故障（铸造整体裂纹/螺栓群松动/动平衡失调）
  - C. 删除占位符行（部件级故障并入零件级）
- **决策**：✅ **选项 A 重生成成功**（2026-06-22，513s）。Judge 评分 **1→7**，第 2 轮补充 3 项缺失故障（铸件气孔/砂眼、导流罩支架断裂、变桨轴承连接螺栓断裂），最终生成 5 个真实部件级故障：轮毂主体疲劳裂纹（裂纹/危急）、轮毂与主轴连接螺栓松动（松动/严重）、轮毂变形（变形/危急）、导流罩结构老化开裂（老化/一般）、轮毂内变桨轴承安装面磨损（磨损/严重）。D1 全为纯枚举"机械"（无机理污染），D2 分布合理，D5+D11-D15 置信标注完整，D7 每条区分易混淆故障。**无需选项 B 手工编写**。
- **补充发现（2026-06-22 路线 2 扫描）**：又发现 4 处同类零件级空壳（D1/D2/D3 全空/无数据）：偏航/扭矩限制器、冷却/膨胀罐、功率变换/放电电阻、机械传动/主轴密封。建议同轮毂总成模式重生成（`--comp 各零件名 --force`）。**待用户确认是否批量重生成**。

### 路线 2：D1 物理属性非枚举（实测 77 处）【🟢已完成】

- **根因**：collector prompt 未隔离"物理属性枚举（机械/电气/绝缘/热/化学/控制/环境）"与"失效机理（疲劳/老化）/子系统类别（液压/电子）"。
- **决策**：✅ **选项 C 执行**（2026-06-22）：

## 5. 关键决策点（需用户拍板）

1. **修复策略总纲**：批量清洗当前数据 vs 修 prompt 重跑 vs 混合？
   - 批量清洗：快（1-2h），但内容类问题（置信标注）只能兜底补标，不准。
   - 修 prompt 重跑：根治，但又一晚（208 任务）。
   - **混合（推荐）**：格式类（D1/类别）批量清洗 + 修 judge prompt 加置信审查项后重跑。

2. **轮毂总成空壳**：手工编写 / 重生成 / 删除？

3. **白名单扩充**：IEC 61400-24 等合法标准是否加入白名单？

4. **是否同步修 collector/judge prompt**：防止 PMSG/半直驱/其他设备迁移时复发同类问题。
