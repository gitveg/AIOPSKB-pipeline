## 1. 改造目标

结构分解层从单层变三层（子系统/部件/零件）后，原段式编码（`PW-WD-001-002-001`）位段不够用。改造7 为「子设备/子系统/部件/零件」各定义独立位段，并让编码真正落地（生成 + 校验），而非仅停留在规范文档。

## 2. 关键发现（动手前的现状核查）

改造7 方案写「沿用现有阶段5交叉索引机制」，但核查代码后发现**该机制从未实现**：

| 检查点 | 实际情况 |
|--------|---------|
| `knowledge_base.json` | **无** code/编码字段 |
| CSV / XLSX（`json_to_csv.py`）| **无** 编码列 |
| `INDUSTRY_CODES`（`config.py`）| 仅 2 字符行业码；`orchestrator.py:35 self.code=` 赋值后**从未被读取**（死代码）|
| `validate_kb.py` | **无**编码格式/唯一性校验 |
| `阶段5 交叉索引` | `orchestrator.py run_validate()` 打印 **`(待实现)`** |

**结论**：编码此前只是 `construct_guide.md §1.2` 的纸面规范，无任何代码生成/存储/校验。这与「验证机制真实有效、不接受表面通过」的要求直接冲突——故改造7 决定**规范 + 落地生成 + 独立校验**一并做实。

## 3. 设计决策

### 3.1 编码格式

```
{行业2}-[子行业2]-{设备3}-[子设备3]-{子系统3}-{部件3}-{零件3}-{故障3}
         └省略        └省略     └000=旧格式      └000=部件级故障
```

| 段 | 长度 | 必现 | 000 含义 | 省略 |
|----|------|------|----------|------|
| 行业 | 2字母 | 是 | — | — |
| 子行业 | 2字母 | 否 | — | 无子行业时省略 |
| 设备 | 3数字 | 是 | — | — |
| 子设备 | 3数字 | 否 | — | 无子设备时省略 |
| 子系统 | 3数字 | 是 | 000=旧格式未做功能分解 | — |
| 部件 | 3数字 | 是 | — | — |
| 零件 | 3数字 | 是 | 000=部件级故障（无零件）| — |
| 故障 | 3数字 | 是 | — | — |

**正则**：`^[A-Z]{2}(-[A-Z]{2})?-\d{3}(-\d{3})?-\d{3}-\d{3}-\d{3}-\d{3}$`

### 3.2 为什么零件段用「000 占位」而非省略

若部件级故障省略零件段，会与「子设备可省略」产生段数歧义：5 个数字段既可能是`设备-子设备-子系统-部件-故障`（部件级+有子设备），也可能是`设备-子系统-部件-零件-故障`（零件级+无子设备），无法区分。

**零件段恒在（部件级填 000）→ 尾部段数固定 → 子设备存在性可由"尾部数字 5 vs 6"判定，子行业存在性可由"第2段是2字母还是3数字"判定 → 解析无歧义。**

### 3.3 编号规则（确定性）

各级在其父节点内按**生成顺序**（= 目录/文件行顺序）从 001 顺序编号。由于 `md_to_json` 建树阶段已按文件行顺序保序，编码生成放在建树后的后处理遍历中，直接 `enumerate` 即可确定性编号。子设备顺序以 `sub_equipment.md` 行顺序为准（非 listdir）。

### 3.4 独立校验避免循环论证

`validate_kb.py` 的编码校验**独立重新遍历目录**按规则重算码（不读 JSON、不 import `md_to_json` 的生成逻辑），校验格式正则 + 全局唯一性。生成端与校验端是两套独立实现，交叉验证一致性——这正是「非循环、非表面」的验证。

## 5. 过程中修复的 bug

`_assign_eq_codes` 旧格式分支最初未处理子设备段——当设备有子设备但子设备目录仍是旧格式时（如锅炉），`components` 是扁平合并的，子设备段被错误省略、部件号跨子设备全局递增。已修复为按 `sub_equipment` 字段分组编号子设备段、每子设备内部件号从 001 重启。validate 端本就按子设备 base_dir 分开传 `se_idx`，无需修。

## 7. 已知边界

1. **设备级 target 的 eq_idx**：`check_encoding` 对单设备目录无法从清单推断 eq_idx，用占位 1（仅校验设备内唯一性 + 格式）。全局唯一性校验需对子行业目录运行（`--target src/data/power/thermal`）。
2. **风电主流子设备仍是旧格式**：风电机组 3 子设备目录尚未迁移到三层结构，编码走旧格式分支（子系统段=000）。待后续「风电新格式全链路」迁移后自然变为真实子系统编号。
3. **`orchestrator.py:35 self.code`** 仍为死代码（改造7 不在 orchestrator 生成编码，留着无害）。

## 8. 如何使用

```bash
# 生成 JSON（含编码）
python src/scripts/md_to_json.py src/data/power

# 生成 CSV/XLSX（编码在首列）
python src/scripts/json_to_csv.py src/data/power/knowledge_base.json
# 或一键导出（重新生成 JSON + 版本化 XLSX）：
python src/data/power/export_xlsx.py

# 编码校验（独立，非循环）
python src/scripts/validate_kb.py --target src/data/power/thermal        # 全子行业（全局唯一性）
python src/scripts/validate_kb.py --target src/data/power/thermal/condenser  # 单设备
```

编码校验通过时静默（validate 只显示问题）；可调用 `check_encoding` 直接查看「共 N 个故障编码，格式合法且全局唯一」。
