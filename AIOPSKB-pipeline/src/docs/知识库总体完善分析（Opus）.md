很好的总结。从工业运维专家 + 多智能体系统两个视角，我把建议按你给的三个层面分别整理。**故障信息可靠性这一块最值得重点投入，所以放在最后展开**。

## 总体判断

当前知识库建设已经进入第二阶段：**框架不是主要矛盾，质量保障才是主要矛盾**。整体看：

- **框架层**：行业 → 子行业 → 设备 → 部件 → 故障 → D1-D9 属性的主结构基本成立，后续不宜频繁推翻列结构，而应补足工况边界、故障关联等工程诊断所需的关键信息。
- **逻辑性保障层**：三 AI 评审主要服务于设备层骨架，包括子行业划分、设备清单、主/辅/公用系统分类、子设备拆分和部件层级。这里的核心不是多找几个 AI 投票，而是让三 AI 依据同一套判定原则和行业编码锚点评审，最后由主智能体仲裁。
- **故障信息可靠性层**：这是当前最重要的战场。D5 阈值、D7 诊断逻辑、D8 检修步骤直接影响工程师和 LLM 的实际决策，必须继续强化置信标注、工况边界、鉴别诊断和安全审查。

## 一、框架层：补两个结构性缺口

### 1.1 工况边界（最关键缺口）

当前 D5 标注 `振动速度>7.1mm/s（ISO 10816-3，置信：标准值）`——但这个 7.1mm/s 来自 ISO 10816-3 中**轴中心高 ≥315mm、刚性安装、II 区上限**的具体条件。如果换成 75-315mm 的小机或柔性安装的机组，阈值完全不同。

**缺失字段**：阈值的适用条件（功率范围/电压等级/材质/安装方式）。

工程师查询时，没有工况边界的阈值等于没有阈值。建议两种实现：
- **轻量做法**：D5 单元格内直接嵌入，如 `振动速度>7.1mm/s（适用：轴中心高≥315mm，刚性安装；ISO 10816-3 表1）`
- **结构化做法**：新增 D10 "适用工况"，强制每条 D5 阈值对应一个工况描述

我倾向轻量做法——不改列结构，迁移成本低。

> **✅ 已落地（2026-05-21）**：采用轻量做法。collector.py D5 prompt 增加 `适用：xxx` 工况标注要求，每条阈值参数必须注明适用条件（电压等级/功率范围/材质/安装方式等），通用阈值可省略。judge.py 第11条审查维度同步增加 D5 工况适用性校验。

### 1.2 故障关联关系

当前是纯树状结构，但真实诊断中故障之间是**因果链**和**共现关系**：

- 因果：润滑油劣化 → 轴承磨损 → 振动超标（同一部件内的链式失效）
- 共现：联轴器对中不良 → 同时引发轴承振动 + 油温升高（跨部件耦合）
- 易混淆：电机绕组匝间短路 vs 转子断条，振动谱相似但治理方法完全不同

**建议在故障表内新增字段**（不必新建维度，可附在 D3 或新增 D10）：
- `诱发故障`：本故障未及时处理会演化为哪些故障
- `易混淆故障`：症状相似但需要区分的故障

这两个字段是 **RAG 场景下最有用的元信息**——工程师查询"振动超标"时，能直接得到"先排除以下3个相似故障"的指引。

> **✅ 易混淆故障已落地（2026-05-21）**：新增 D10 列（`D10 易混淆故障`），故障表格从 10 列扩展为 11 列。格式为"故障名：区分要点"，无则填"—"。collector.py、judge.py（第10+15条审查）、orchestrator.py（_build_fault_table/_parse_fault_table）、validate_kb.py、construct_guide.md v2.5 同步更新。导出链路（md_to_json.py + json_to_csv.py）已同步支持。
>
> **⬜ 诱发故障未实施**：当前未新增"诱发故障"字段。D10 已覆盖"易混淆"维度，"诱发"维度待评估是否值得增加第12列——需看 D10 落地后的实际使用效果再决定。

## 二、逻辑性保障层：强化设备层结构 + 补一个全库横向扫描

### 2.1 当前定位修正

三 AI 评审的主战场是**设备层结构**：
- 子行业划分是否合理
- 设备清单是否覆盖完整
- 设备分类（主设备/辅助设备/公用系统）是否正确
- 子设备拆分（技术路线）是否合理
- 部件层级是否清晰

这是知识库**骨架**的质量保障，方向对。但目前存在几个深层缺口三 AI 评审尚未触及。

### 2.2 缺口一：按子行业引入分类编码锚点

**问题**：三个 AI 各自基于训练数据判断"什么算主设备/辅助设备/公用系统"，但每个 AI 的训练侧重不同。同一台电除尘器，Claude 可能划为"辅助"，GLM 可能划为"公用"，DeepSeek 可能划为"环保系统下的主设备"——争议无锚点可仲裁。

虽然 `construct_guide.md` 0.2.1 节的"设备与部件判定原则"第 5 条已经提到 KKS 编码作为资产登记锚点，但**没有按子行业展开**，三 AI 评审时仍是各自归纳。

工程界对不同子行业有不同的成熟编码体系：

| 子行业 | 推荐编码体系 | 说明 |
|--------|------------|------|
| 火电、水电、核电等电站型场景 | **KKS**（DL/T 5448-2014）或同类电站标识体系 | 电站设备分类的事实标准之一，可作为火电、水电、核电设备归类锚点 |
| 风电 | **RDS-PP**（IEC 81346-10） | 风电场专用，覆盖整机、叶片、齿轮箱、变流器等 |
| 输电、变电、配电 | **GB/T 50064**、IEC 61850 设备模型 | 变电站设备分类与命名规范 |
| 光伏 | **IEC 62548** + 国内行业实践 | 光伏阵列、汇流箱、逆变器分类 |
| 储能 | 行业规范尚未统一，可参考 GB/T 36558、IEC 62933 | 处于演化期 |

**建议**：在 `construct_guide.md` 中按子行业明确"分类参考锚点"，三 AI 评审子行业的设备清单时统一引用对应的编码体系。这不是要把知识库强制改造成 KKS 或 RDS-PP 目录，而是为三 AI 提供设备归类的外部参照。比如评审火电设备清单时，三 AI 需要说明该设备是否能在 KKS 或电站资产体系中找到稳定归属；评审风电时，则优先对照 RDS-PP 的风电对象模型。

附加收益：生成的 KB 可以逐步补充行业编码映射，未来与 EAM/MES/资产台账系统集成时更顺畅。

> **✅ 已落地（2026-05-21）**：config.py 新增 `SUB_INDUSTRY_CODING_ANCHORS`（覆盖 11 个子行业的编码体系映射），construct_guide.md 0.2.1 节新增"子行业分类编码锚点"表，三 AI 评审时可引用。

### 2.3 缺口二：主设备 / 辅助设备 / 公用系统的判定原则明文化

**问题**：当前 `construct_guide.md` 0.2.1 节定义了"**设备 vs 部件**"的 5 条判定原则，但**主设备 / 辅助设备 / 公用系统**这三类之间的判定原则只有示例（line 49-51），没有明文规则。这正是用户提到的"划分的设备是否被归为了正确的分类"的争议根源。

举例：电除尘器在煤电是除尘环节的核心设备（环保子系统主设备？），但相对汽水循环系统又是辅助；循环水泵服务于多套机组时是"公用系统"，单机配套时算"辅助"。当前 LLM 凭直觉判断，三个 AI 答案常常不一致。

**建议**：在 0.2.1 节之后新增"三分类判定原则"，给出可机械执行的判定标准：

| # | 判定维度 | 主设备 | 辅助设备 | 公用系统 |
|---|---------|--------|---------|---------|
| 1 | 服务对象 | 服务生产主流程本身 | 服务某台或某类主设备 | 服务多个设备、多个系统或全厂 |
| 2 | 与能量转换核心的距离 | 直接参与主能量转换（如锅炉→蒸汽，汽轮机→机械能） | 服务于某台主设备的运行（如磨煤机服务锅炉） | 不绑定单一主设备，服务全厂或多台机组 |
| 3 | 故障的设备级影响 | 失效直接导致机组停运 | 失效导致对应主设备降负荷或停运 | 失效影响全厂运行，但不一定停机组 |
| 4 | 配置粒度 | 通常按机组一一对应 | 通常按主设备配套（1台主设备配 N 台辅助） | 按全厂或集中区域配置（1 套服务多机组） |

三 AI 评审时按这四条原则判定即可，争议大幅减少。这是和缺口一互补的——缺口一引入外部编码锚点，缺口二明文化内部判定原则。

最终仍由**主智能体仲裁**：三 AI 给出结构评审意见，主智能体基于 `construct_guide.md`、子行业编码锚点和三分类原则做最终裁决。这样保留三 AI 的多视角优势，也避免额外维护复杂的争议清单机制。

> **✅ 已落地（2026-05-21）**：construct_guide.md 0.2.1 节新增"主设备/辅助设备/公用系统 三分类判定原则"四维判定表 + 典型示例（锅炉/磨煤机/循环水泵/电除尘器/空压机站）+ 争议仲裁规则。config.py 新增 `EQUIP_TYPE_CRITERIA` 四维数据供程序化引用。

### 2.4 缺口三：故障层的横向一致性扫描（纯规则脚本）

设备层由三 AI 评审保障，**故障层**也需要横向一致性检查，但不应消耗 LLM 算力——纯规则脚本即可：

| 检查项 | 检查方法 |
|--------|---------|
| 故障命名规范化 | 跨部件扫描相似故障名（"绝缘老化" vs "绝缘劣化" vs "绝缘退化"），输出归并建议 |
| D1 分类一致性 | 同一种故障（如"绕组绝缘老化"）在不同部件下，D1 类别是否一致 |
| D2 严重度分布异常 | 若某部件 80% 故障被标"危急"，大概率是 LLM 偏置 |
| D5/D6 误填率 | 正则检测"参数+阈值"是否误写在 D6，"传感器名称"误写在 D5 |
| 标准号引用合法性 | 提取所有标准号，正则匹配格式 + 抽样校验真实性 |

零成本，但能发现 LLM 系统性偏置（最难自我发现的问题）。建议作为 `validate_kb.py` 的扩展模块。

> **✅ 已落地（2026-05-21）**：validate_kb.py 新增 5 项横向检查函数：
> - `check_d5_d6_crossfill()`：D5/D6 互填检测（传感器名误写在 D5，阈值误写在 D6）
> - `check_d2_severity_distribution()`：D2 严重度偏置检测（单等级占比≥80% 时告警）
> - `check_standard_version_age()`：标准版本时效检测（10 年以上标准引用告警）
> - `check_fault_name_consistency()`：跨部件故障命名一致性扫描（相似度≥85% 的故障名对输出归并建议）
> - 上述检查已集成到 `validate_stage4()` 和 `validate_full()` 中

## 三、故障信息可靠性（重点）— 五个建议

### 3.1 D7 诊断鉴别矩阵（最重要）

**当前 D7 的本质问题**：写的是"这个故障如何诊断"，但真正困扰工程师的是"这些症状下，是 A 故障还是 B 故障"。

举例对比：
> 当前 D7：通过 DGA 分析气体组分，若 H2 > 150μL/L 判定为绝缘故障
>
> 鉴别式 D7：H2 升高同时伴随 CH4 升高 → 局部过热（非放电）；H2 升高 + C2H2 出现 → 高能放电；仅 H2 升高 → 检查可能的进水或受潮（与放电鉴别）

**实现路径**：把 D7 的 prompt 要求从"列出判断逻辑"改为"列出鉴别逻辑"，强制要求至少回答"与哪个相似故障如何区分"。

这是整个知识库**走向工程实用**的最关键改造。诊断的核心是排除法，不是确认法。

> **✅ 已落地（2026-05-21）**：collector.py D7 prompt 从"判断逻辑"改为"鉴别诊断逻辑"，要求回答"与相似故障如何区分"并给出鉴别要点。judge.py 第4条（常规审查）改为"D7鉴别诊断充分性"，第13条（对抗审查）要求验证鉴别要点在工程上成立。允许写"无明显易混淆项"防止凑数。

### 3.2 FMEA 启发式枚举替代自由发挥

当前 Collector 用"列出常见故障"的开放式提示，结果就是"D5 永远是 3 条"那种凑数问题——LLM 在没有结构约束时倾向于产生固定数量的输出。

**改造**：用工程标准 FMEA 框架（IEC 60812）作为 Collector 的思考脚手架，而不是最终输出的硬性分类表：

```
按以下失效层级系统化枚举，不要凑数：
1. 功能失效（设备无法完成预期功能）
2. 性能退化（功能可完成但参数偏移）
3. 部件物理损伤（材料层面的损伤）
4. 结构失效（机械结构层面的破坏）
5. 接口失效（与其他设备的连接异常）
每个层级若有真实故障则列出，无则跳过。
```

这是一种"垂直工程脚手架"——给 LLM 一个工程界公认的思维框架，输出质量会比开放式提示稳定得多。但必须强调：FMEA 只用于启发枚举，**不能要求每个层级都强制产出故障**，否则会从"常见故障凑数"变成"FMEA 类别凑数"。

> **✅ 已落地（2026-05-21）**：collector.py 故障层 prompt 第一条要求改为 FMEA 六层级枚举框架（功能失效/性能退化/物理损伤/结构失效/接口失效/老化劣化），每层有则列、无则跳过。construct_guide.md 4.2 节同步更新。

### 3.2.1 防止过度结构化

工况边界、易混淆故障、诱发故障、FMEA 枚举都很有价值，但不能把它们变成新的强制填充任务。否则 LLM 会为了满足格式而虚构"易混淆故障"或"诱发故障"。

建议在 prompt 中明确：
- 有真实工程意义时填写，无则允许写"无明显易混淆项"或"未发现稳定诱发关系"
- 不以数量作为质量指标，少而准优于多而泛
- 对故障特征、鉴别关系、诱发关系均禁止凑数

> **✅ 已落地**：D10 易混淆故障允许填"—"，D7 鉴别诊断允许写"无明显易混淆项"，FMEA 框架明确"每个层级若有真实故障则列出，无则跳过"。三个措施均已在 collector.py prompt 中体现。

### 3.3 自我测试闭环（KB 反向校验）

最强的质量验证是 **KB-vs-现实**，但现实数据难以接入。次强的方案是 **KB-vs-自我**：让 Kimi 假装是工程师，根据 D4 症状描述反向问"这是什么故障"，再对比是否能命中 D3 的故障名。

具体做法：
- 抽样 10% 故障，提取 D4 症状 + D5 参数
- 把这些症状交给 Kimi（不告诉它故障名），让 Kimi 猜测可能的故障
- 命中率低的故障 → 说明 D4/D5 不够特征性 → 标记为"诊断特征不足"

这本质上是把 LLM 当成"模拟工程师"做盲测，**用同一个知识库去检测自己**，找出诊断盲区。零额外人工成本。

### 3.4 标准版本与失效时间

`置信：标准值（GB/T 7595）` 在 5 年后可能失效——GB/T 7595 升级了，阈值变了。建议：

- **D5 标注强制带版本**：`GB/T 7595-2017` 而不是 `GB/T 7595`
- **validate_kb.py 增加版本时效告警**：扫描所有标准号，标记 10 年以上的版本（高概率已更新）

这个改动很小，但能让 KB 具备"自我老化感知"能力——5 年后跑一次校验就知道哪些条目需要重新审视。

### 3.5 "经验值"的来源分层

当前 `经验值` 是一个笼统类别，但实际可信度差异很大：

| 当前 | 建议细分 | 含义 |
|------|---------|------|
| 经验值 | 经验值-行业共识 | 多个 OEM/电厂广泛采用 |
| | 经验值-OEM推荐 | 来自设备厂商手册 |
| | 经验值-单一来源 | 仅见于个别文献或案例 |

可以让 Kimi 在 Phase C 核查时同时做一次"经验值分层"。这层信息对 RAG 输出质量提升明显——回答时可注明"以下为多家厂商通用经验"vs"以下为单一来源数据，建议二次确认"。
