# 章节0: 元信息与前言

## 0.1 文档目的

本指南是工业设备智能运维知识库构建的**总蓝图**，定义了知识库的架构、数据模型、构建流程、质量标准和智能体协作方式。所有参与构建的智能体和人工审核者都应以本指南为准。

## 0.2 术语定义

| 术语 | 英文 | 定义 |
|------|------|------|
| 行业 | Industry | 最顶层分类，如电力、石化、冶金等 |
| 子行业 | Sub-Industry | 行业下的细分领域（按需，非必有）。如电力下的火电、水电、风电 |
| 设备 | Equipment | 具体的工业设备，如锅炉、汽轮机、变压器 |
| 子设备 | Sub-Equipment | 设备下的细分类型（按需，非必有）。如锅炉下的煤粉炉、循环流化床锅炉、余热锅炉。仅当设备是大类且包含多个技术路线时使用 |
| 子系统 | Sub-system | 设备（或子设备）的功能分解单元（v3.0新增）。如传动系统、发电系统、控制系统。注意：子系统≠子设备，子系统是功能分解维度，子设备是技术路线维度 |
| 部件 | Component | 子系统下的可独立更换/检修的总成单元（v3.0更新）。如齿轮箱、联轴器 |
| 零件 | Part | 部件下的更细粒度可拆卸件（v3.0新增）。如行星齿轮、太阳轮。允许短链（零件列填"—"） |
| 故障 | Fault | 部件或零件上发生的异常或失效模式，如水冷壁爆管、轴承磨损 |
| 故障类别 | Fault Category | 故障的**失效模式分类标签**（v3.0改造5新增，故障表第2列），取值来自 `failure_categories.yaml` 白名单（约61个标签，按部件系列分组），对齐 PHM 监测平台标签。区别于 D1 物理属性：类别是"怎么坏的"（磨损/腐蚀/泄漏），D1是"坏的物理机制"（机械/电气/化学）。LLM 不得自创类别 |
| 属性维度 | Attribute Dimension | 故障的知识描述维度（D1-D15：D1-D10诊断 + D11-D15检维修），涵盖机理、特征、监测、诊断、检修、预防 |

## 0.2.1 设备与部件判定原则 & 设备三分类标准

### 设备与部件判定

设备与部件的边界是知识库结构严谨性的核心。满足以下**多数条件**的归为"设备"，否则归为"部件"：

设备与部件的边界是知识库结构严谨性的核心。满足以下**多数条件**的归为"设备"，否则归为"部件"：

| # | 判定维度 | 设备特征 | 部件特征 |
|---|---------|---------|---------|
| 1 | 物理独立性 | 可独立运输、独立安装，拆出后仍是一个完整的物理实体 | 只能作为设备的组成部分存在，脱离设备无意义 |
| 2 | 采购独立性 | 独立采购单元，有独立型号、供应商和合同 | 随设备整体采购，通常不单独订购 |
| 3 | 运维独立性 | 有独立检修班组/团队、独立检修规程、独立备件管理体系 | 随设备检修一起维护，无独立检修规程 |
| 4 | 功能完整性 | 能完成一个独立的功能（即使需要与其他设备配合） | 只能完成设备功能的某个环节 |
| 5 | 资产登记 | 有独立的资产编号/KKS编码/设备台账条目 | 隶属于某设备的资产编码下 |

**典型判定示例**：
- 锅炉 → 设备（独立采购、独立班组、独立KKS）
- 给水泵 → 设备（独立采购、有泵班组、有独立KKS编码）
- 水冷壁 → 部件（锅炉的组成部分，不可独立运行）
- 风电机组 → 设备（整体采购、整体运维）
- 齿轮箱 → 部件（风电机组的组成部分，不可独立运行）

**常见错误警示**：
- 不可将独立辅机（如引风机、送风机、除尘器）归入主设备的"辅助设备"子部件，它们是独立设备
- 不可将同一事物同时作为独立设备目录和另一设备的部件（如凝汽器不应同时出现在凝汽器目录和汽轮机部件中）
- 不可将一台主设备的子系统（如风电机组的齿轮箱、叶片）拆为独立设备目录

### 主设备 / 辅助设备 / 公用系统 三分类判定原则

设备属性分为"主设备""辅助设备""公用系统"三类，按以下四维判定：

| # | 判定维度 | 主设备 | 辅助设备 | 公用系统 |
|---|---------|--------|---------|---------|
| 1 | 服务对象 | 服务生产主流程本身 | 服务某台或某类主设备 | 服务多个设备、多个系统或全厂 |
| 2 | 与能量转换核心的距离 | 直接参与主能量转换（如锅炉→蒸汽，汽轮机→机械能） | 服务于某台主设备的运行（如磨煤机服务锅炉） | 不绑定单一主设备，服务全厂或多台机组 |
| 3 | 故障的设备级影响 | 失效直接导致机组停运 | 失效导致对应主设备降负荷或停运 | 失效影响全厂运行，但不一定停机组 |
| 4 | 配置粒度 | 通常按机组一一对应 | 通常按主设备配套（1台主设备配N台辅助） | 按全厂或集中区域配置（1套服务多机组） |

**典型判定示例**：
- 锅炉 → 主设备（直接参与能量转换，一一对应机组）
- 磨煤机 → 辅助设备（服务锅炉运行，按锅炉配套）
- 循环水泵（多机共用）→ 公用系统（服务全厂冷却水）
- 电除尘器 → 辅助设备（服务锅炉烟气处理环节，按机组配套）
- 空压机站 → 公用系统（全厂仪用压缩空气，1套服务多机组）

**争议仲裁**：同设备在不同配置下分类可能不同（如循环水泵单机配套时为辅助、多机共用时为公用）。三 AI 评审时按上述四维逐条判定，争议由主智能体仲裁。

### 子行业分类编码锚点

三 AI 评审设备清单时，统一引用以下编码体系作为设备归类的外部参照。这不要求将知识库改造为编码目录，而是为评审提供可查验的锚点。评审脚本与流程详见 `ai_expert_review/README.md`。

| 子行业 | 参考编码体系 | 标准号 | 适用范围 |
|--------|------------|--------|---------|
| 火电、水电、核电、燃气轮机、抽水蓄能 | **KKS** | DL/T 5448-2014 | 电站设备分类标识，火/水/核/燃气电站的事实标准 |
| 风电 | **RDS-PP** | IEC 81346-10 | 风电场专用，覆盖整机/叶片/齿轮箱/变流器 |
| 光伏 | **IEC 62548** | IEC 62548 + 国内行业实践 | 光伏阵列/汇流箱/逆变器分类 |
| 输电、变电、配电 | **IEC 61850** | GB/T 50064 + IEC 61850 | 变电站/配电设备模型与命名 |
| 储能 | **GB/T 36558** | GB/T 36558 + IEC 62933 | 储能系统分类（行业规范演化中） |

**使用方式**：评审设备清单时，评审方需说明该设备能否在对应编码体系中找到稳定归属。若无法匹配，需给出合理说明。

## 0.4 数据仓库挖掘作为构建参考源

PHM 数据仓库（`alg_analysis`，近 5 年，23.4 万台设备 / 23 行业）是知识库构建的**第六个、且唯一「实证性」参考源**。前五种（Web 搜索、行业标准、厂商手册、FMEA、编码锚点）回答"应该有哪些设备"（规范性），数据仓库回答"现实中实际部署了哪些、各有多少"（描述性）。两者互补：数据为结构判定提供**现实存量校验**，但**不替代**结构判定本身——哪些设备存在、如何分层，仍由人工 / LLM / 专家评审按本指南完成。

**各层数据支撑度**（详细方法、阈值、行业案例见 `docs/数据辅助知识库构建/`）：

| 知识库层 | 支撑度 | 数据能做什么 |
|---|---|---|
| 子设备 | 🟡 中 | 验证某设备是否需按技术路线拆分（风电双馈/直驱/半直驱已实证吻合）；多数行业无技术路线维度，**不需拆子设备** |
| 子系统 | 🟠 弱 | 无结构树，仅从部件构成间接旁证功能域；划分以标准（KKS/RDS-PP）+ 功能分解为主 |
| 部件 | 🟡 中 | 部件级 `devicetype`（齿轮箱/叶片/辊/轴承座）提供候选清单；需去单企业特例 + 手册补全 |
| 零件 | 🔴 无 | 数据仓库无零件级数据，**不适用**，须靠手册/标准/LLM |

**关键认知**：监测平台的 `devicetype` **混合了「设备 / 子设备 / 部件 / 其他（部位/仪表）」四类**，并非纯"设备类型"。用数据做设备清单参照时，必须先过滤部件级与"其他"类条目，否则会把齿轮箱、叶片误列为设备。已用 `classify_devicetype.py` 给每个型号打 `kb_level` 标签（设备/子设备/部件/其他）。

**使用阶段**（详见各阶段正文指针）：
- 阶段2 设备枚举：`industry_devicetype_topN.csv`（取 `in_topn=True`，过滤 `single_ent` 与部件级条目）作为现实存量锚点
- 步骤2.5 子设备拆分：验证技术路线型代码聚类，取累计覆盖≥95% 的技术路线
- 阶段3 部件拆解：部件级 `devicetype` 作为部件候选补充

**数据质量分级（决定数据驱动 vs 标准驱动）**：

| 分级 | 行业 | 构建策略 |
|---|---|---|
| A 优 | 风电 | 集中度高、未分类低，数据可**直接驱动** |
| B 良 | 石化、化工、煤炭、煤化工 | 数据锚点 + 人工筛选主流程 |
| C 中 | 钢铁、水泥、有色、火电 | 分散/未分类高，数据仅**旁证**，以标准为主 |
| D 差 | 试验、汽车、隧道 | 数据稀疏，**不依赖**数据，纯人工 |

> **重要**：数据弱覆盖行业（火电/水电/核电）的主设备在数据中可能为 0（监测平台只覆盖旋转动设备，静设备/主机的振动测点缺位），**绝不能因"数据为 0"判定该设备不重要**——这类行业须**标准驱动**。详见 `docs/数据辅助知识库构建/火电数据参照分析.md`。

**局限**：①`devicetype` 四类混合，用前先识别级别；②单企业刷量须用 `single_ent` 过滤；③未分类占比参差（钢铁/水泥>30%慎用）；④无枚举代码的中文为推断值，个别需复核。建议**季度更新**（重跑 `industry_devicetype_topN.py` + `classify_devicetype.py`）。

# 章节1: 知识库架构与数据模型

## 1.1 层级架构

知识库采用灵活的层级树状结构：

```
行业 (Industry)
  └── [子行业 (Sub-Industry)]        ← 按需，大型行业才有
        └── 设备 (Equipment)
              └── [子设备 (Sub-Equipment)]   ← 按需，仅当设备是大类且包含多个技术路线时
                    └── 子系统 (Sub-system)    ← v3.0：功能分解，固定层级
                          └── 部件 (Component)   ← v3.0：可独立更换/检修的总成
                                └── 零件 (Part)      ← v3.0：更细粒度可拆卸件（允许短链）
                                      └── 故障 (Fault)
                                            └── 属性维度 (D1-D15)
```

**关键规则**:
- 子行业层**按需存在**：电力有子行业，水泥/煤炭等可能直接从行业进入设备层
- 子设备层**按需存在**：当设备是大类（如"锅炉"涵盖煤粉炉、CFB、余热锅炉等不同技术路线），需要细分时才加子设备层。不是所有设备都需要，简单设备直接进入子系统层
- 子系统层**始终存在**（v3.0新增）：按功能独立性划分（如传动系统、发电系统、控制系统），不是技术路线分类。子系统≠子设备
- **子系统数量限制**（v3.1新增）：按设备类型设上限，避免过细拆分增加维护负担：静设备（换热器/塔/容器）≤4；旋转机械（泵/风机/压缩机）≤6；大型主设备（锅炉/汽轮机/反应器）≤7（例外，须论证功能不可合并）；**硬上限7**。`validate_kb.py` 对 >6 发 WARNING（提示仅大型主设备允许），>7 阻断
- 部件→零件为**固定两层语义**，不再支持自由"子部件"嵌套。允许短链（零件列填"—"），禁止为填满三层而虚构零件
- 故障挂在**部件层**（总成级失效）和**零件层**（具体失效），子系统层不挂故障

## 1.2 编码系统

每条知识记录拥有唯一编码，结构如下：

```
{行业2字符}[-{子行业2字符}]-{设备3位}[-{子设备3位}]-{子系统3位}-{部件3位}-{零件3位}-{故障3位}

示例:
  PW-TH-001-001-001-000-001       →  电力-火电-凝汽器(无子设备)-凝汽器本体-冷却管-泄漏（部件级故障，零件段000）
  PW-TH-001-001-001-001-001       →  电力-火电-凝汽器-凝汽器本体-齿轮箱-行星齿轮-断齿（零件级故障）
  PW-TH-001-001-002-001-001       →  电力-火电-锅炉-煤粉炉-炉膛系统-水冷壁-高温腐蚀（有子设备：煤粉炉为第2个子设备）
  CM-001-001-001-000-001          →  水泥-回转窑-筒体系统-筒体-裂纹（无子行业，部件级故障）
  PW-WI-001-001-001-001-001       →  电力-风电-风电机组-双馈机组(第1个子设备)-传动系统-齿轮箱-行星齿轮-断齿（零件级故障）
  PE-002-001-001-005-000-001      →  石化-压缩机(第2设备，无子行业)-螺杆压缩机(第1子设备)-气体净化与分离系统-最小压力阀-泄漏（部件级故障，无子行业段）
```

**行业代码表**:
- PW=电力, PE=石化, MT=冶金, CM=水泥, CL=煤炭, RT=轨道交通, MF=制造业, AS=航空航天与船舶

**子行业代码**: 由阶段1调研后分配，如 TH=火电, HY=水电, WI=风电 等。可省略：当子行业层不存在时（行业直接展开到设备），省略该段。

**子设备编码**: 3位，在所属设备内按子设备清单（sub_equipment.md 行顺序）顺序编号。仅当该设备存在子设备时使用。

**子系统编码**: 3位，在所属子设备（或设备）内按子系统清单（sub_system.md 行顺序）顺序编号。

**部件编码**: 3位，在所属子系统的 components.md 中按行顺序编号（001, 002, ...）。

**零件编码**: 3位，在所属部件的零件列表（components.md 的零件列）中按行顺序编号（001, 002, ...）。部件级故障时零件段占位 000。旧格式无零件层，零件段固定填 000。

**故障编码**: 3位，在所属故障表（faults/*.md）内按行顺序编号（001, 002, ...）。部件级故障时其零件段占位 000。

**占位与省略约定（改造7）**:
- **省略段（按需层）**：子行业段、子设备段在层级不存在时省略（不占位）。子行业层、子设备层按需存在。
- **占位段（固定层）**：子系统段、零件段恒存在（层级固定），故障在该层级不使用时填 000。旧格式无子系统/零件层，子系统段固定填 000 标记"未做功能分解"（待迁移到三层结构后自然变更为真实编号）。

> 注：编码不存储在源 markdown 中（故障表为纯表格），由目录路径与故障名称唯一生成，在 JSON/CSV 导出时统一生成并校验唯一性。零件段恒存在（部件级故障填 000）保证尾部段数固定、解析无歧义。

## 1.3 故障属性维度 Schema

### 索引结构与知识维度的分离

知识库的查询定位由**构建目录层级**承载（不占用 D1–D9 知识维度字段）。路径中 `[子行业]`、`[子设备]` 按行业与实际设备按需存在：

```
行业 → [子行业] → 设备 → [子设备] → 部件 → 故障名称（见该部件对应 faults 文件表格首列）
```

其中：`faults/` 目录下每个 Markdown 文件的**文件名**与 `components.md` 中**部件名称**一致（中文名）。**所有部件均可生成故障文件**（叶节点优先，父节点在后）。父部件故障应聚焦整体宏观失效模式（整体退化、系统级失效、多子部件耦合故障），避免与单一子部件故障重复。**故障名称**由该文件内表格的「故障名称」列承载。故障**编码**格式遵循 1.2 节规则（如 `PW-TH-001-002-001`），供交叉引用。故障层 Markdown 须遵守 1.4.1「每个文件仅为一张表格、表格外无说明文字」，因此**不在表格外书写编码**；编码在阶段 5 构建交叉索引及后续转化为 JSON/CSV 时，由目录路径与「故障名称」统一生成并校验唯一性。

### 知识维度（D1-D15）

以下维度描述故障本身的**知识内容**，不含索引定位信息。覆盖完整的故障处理链：**分类→理解→发现→检测→诊断→处置→预防→鉴别**。

| 编号 | 维度名称 | 类型 | 必填 | 说明 |
|------|---------|------|------|------|
| D1 | 物理属性 | multi-enum | 是 | 机械/电气/绝缘/热/化学/控制/环境（表征失效的物理化学机制） |
| — | 故障类别 | yaml-enum | 是 | 从 failure_categories.yaml 按部件类型选取（对齐监测平台标签） |。多选用`;`分隔（如`机械;化学`）。选择最直接的失效机制，仅当确实无法单一归类时才多选 |
| D2 | 故障等级 | enum | 是 | 轻微/一般/严重/危急。判定标准见下方D2等级表 |
| D3 | 故障描述与机理 | text | 是 | 合并定义+机理+诱发因素：故障现象、根本原因分析（物理/化学/力学）、触发条件。要求因果关系完整 |
| D4 | 故障征兆 | array | 是 | 面向现场的可观测现象列表：声音、气味、仪表读数异常、外观变化等。简洁条目式，供工程师快速对照 |
| D5 | 故障特征参数 | array | 是 | 合并电气/物理/化学/状态量：所有可量化的诊断参数，每个参数标注类型标签和阈值，并追加**置信标注**。四级标注：（标准号+条款，置信：标准值）或（行业经验，置信：经验值）或（置信：经验值-未核实）或（置信：待核实）。标注规则收紧：**仅当同一参数出现来源冲突且无法裁断时**才标"待核实"，来源不足不是标"待核实"的理由——应标"经验值"。正确示例：[物理]振动速度>7.1mm/s（ISO 10816-3 表1 B/C级，置信：标准值）。错误示例：振动加速度传感器（这是监测手段，应填D6）。禁止伪造标准号。Collector生成时注入行业通用标准速查表（18参数域、~90标准），按部件类型预筛3-5个相关域以聚焦LLM注意力 |
| D6 | 监测与检测手段 | array | 是 | 合并在线/离线/带电：所有监测检测方法，每个方法标注类型标签。正确示例：[在线]振动加速度传感器、[离线]绝缘电阻测试。错误示例：振动速度>7.1mm/s（这是特征参数，应填D5） |
| D7 | 诊断方法 | text | 是 | 采用鉴别诊断逻辑（而非简单确认）。必须回答"与相似故障如何区分"。正确示例：DGA分析H2升高时：H2+CH4同时升高→局部过热；H2+C2H2出现→高能放电。错误示例：若H2>150μL/L判定为绝缘故障（仅确认，未鉴别） |
| D8 | 检修方法 | text | 是 | 合并根本检修和临时检修：彻底修复的具体步骤和所需工具，以及短期应急处理方案。按"根本处理：xxx；临时处理：xxx"格式组织。标注[规程级]/[经验级]。若无临时处理方案，填写"临时处理：无，须立即停机处理" |
| D9 | 预防措施 | array | 是 | 如何避免发生的措施列表 |
| D10 | 易混淆故障 | text | 条件必填 | 与本故障症状相似、容易混淆的其他故障名称及区分要点。格式：故障名：区分要点。若确实无易混淆故障，填"—"。禁止为凑数编造，少而准优于多而泛 |

### 检维修维度（v6.0新增，D11-D15，运维工作流补充）

以下5列（编号续接 D1-D10，即 D11-D15）支持从故障诊断延伸到运维执行，补充工单系统所需的检维修信息。由于用工/备件与OEM强相关，准确率天然低于诊断维度，RAG输出时应注明"参考值，需对照现场实际"。这5列做成独立维度列（便于工单系统单独提取"用工需求"等），不塞进D8。

| 维度 | 类型 | 必填 | 说明 |
|------|------|------|------|
| D11 用工需求 | text | 否 | 工种+人数+预计工时（如"钳工2名、管工1名；工时6-8h"）。标"经验值"作为参考 |
| D12 工机具 | text | 否 | 通用工具类目（如"扭力扳手、涡流探伤仪、堵管工具"）。标"经验值"，规格依设备手册 |
| D13 备件用料 | text | 否 | 备件/耗材通用名（如"冷凝管备件、堵头、密封胶"）。标"经验值"，具体型号需现场补充 |
| D14 安全注意事项 | text | 否 | HSE/特种作业规程要求。有标准依据标"标准值"并引用（如AQ标准、DL/T 869），否则标"经验值" |
| D15 验收标准 | text | 否 | 检验规范/量化验收指标。有标准依据标"标准值"并引用（如DL/T 869、GB/T 12145），否则标"经验值" |

**置信标注**：以上5列复用 D5 置信标注机制（标准值/经验值/待核实），每列内容末尾必须标注置信级别。D14 安全注意事项、D15 验收标准鼓励标"标准值"并带标准号。禁止伪造标准号——不确定来源就标"经验值"，不确定数值就标"待核实"。

> **D2 故障等级判定标准**：
>
> | 等级 | 判定标准 |
> |------|---------|
> | 危急 | 须立即停机，继续运行有人身安全风险或设备失效风险 |
> | 严重 | 应在72小时内安排处理，设备功能显著降级 |
> | 一般 | 可在下次计划检修前处理，设备功能轻微降级 |
> | 轻微 | 可在本检修周期内跟踪观察，不影响正常运行 |

### 属性挂载规则（v3.0）

三层结构各自承载的属性（改造3）：

| 结构层 | 名称+描述 | 易损标识 | 故障 | 维护方法 | 报废方法 |
|--------|----------|---------|------|---------|---------|
| **子系统** | ✓ | — | ✗（纯结构归类/导航层） | ✗ | ✗ |
| **部件** | ✓ | ✓ | ✓（整体/总成级失效） | ✓ | ✓ |
| **零件** | ✓ | ✓ | ✓（具体失效） | ✗（上挂到部件） | ✗（上挂到部件） |

**规则要点**：
1. 故障挂在部件层（整体/总成级失效）和零件层（具体失效）。子系统层不挂故障、不加故障列
2. 维护方法、报废方法只挂部件层（零件行这两列填"—"）。日常保养与报废处置基本是总成级动作
3. 子系统层仅有"名称 + 描述"两个属性

### 部件层扩展属性

部件（Component）除了名称、零件、描述、易损标识外，还有两个扩展属性：

| 属性 | 类型 | 说明 |
|------|------|------|
| 维护方法 | text | 日常保养规程：巡检周期、维护操作要点。与故障无关的通用例行维护。如"每3个月补充润滑脂、每6个月测量游隙"。**仅在零件列="—"的部件行填写** |
| 报废方法 | text | 部件不可修复时的处置：判定条件（定性为主）、拆除步骤、处置注意事项。**仅在零件列="—"的部件行填写** |

> **层级分工说明**：维护方法和报废方法是部件级属性，不是故障级属性。维护方法是"不管坏没坏都要做的日常保养"，区别于故障级D8检修方法（出了具体故障怎么修）和D9预防措施（怎么避免具体故障发生）。报废方法是"部件不行了怎么处理"，同一部件不管因何种故障报废，处置流程相同，因此放在部件层而非每个故障重复一遍。零件不单独填写维护/报废方法——它们上挂到所属部件行。

## 1.4 最终交付物与格式策略

### 构建阶段输出

构建过程中**统一输出结构化Markdown文档**。不同时生成多种格式，以节省token消耗。

Markdown文档需遵循**严格的格式规范**，确保后续可程序化解析转化为JSON和CSV：

#### 1.4.1 通用格式规则

1. **每个文件就是一张标准Markdown表格**，不允许在表格前后添加任何解释性文字、前言、总结
2. **列名固定不变**，不同文件的同一层级必须使用完全相同的列名
3. **不允许合并单元格、不允许嵌套表格**
4. **每行一个条目**，不允许在表格内使用换行符（`<br>`等）
5. **编码和字段值使用一致的格式**

> **v3.0 新格式**：新格式使用 `sub_system.md` + 子系统目录嵌套结构（子系统→部件→零件），是唯一模式。
> **无子行业行业的目录结构**：石化等无子行业行业，目录为 `data/{行业}/{设备}/{子设备}/sub_system.md`（省略子行业层），见 §0.3、§10.5。
> **三AI专家评审模块**：`ai_expert_review/` 是独立的结构评审模块（DeepSeek + Kimi + Claude 仲裁），详见 §2.8。

# 章节2: 多智能体系统设计

## 2.1 智能体角色总览

```
                    ┌─────────────────────────────────────────┐
                    │         主智能体(DeepSeek)                │
                    │    架构控制/结构验证/内容整合/最终批准       │
                    └──┬──────┬──────┬────────┬──────────┘
                       │      │      │        │
            ┌──────────┘      │      │        └──────────┐
            ▼                 ▼      ▼                    ▼
  ┌─────────────────┐ ┌──────────────┐ ┌──────────────────┐ ┌──────────────────┐
  │ 收集调研智能体    │ │ Judge智能体   │ │ 可用性判断智能体   │ │ 标准核查智能体    │
  │ (DeepSeek)      │ │ (DeepSeek V4) │ │ (DeepSeek)       │ │ (DeepSeek Pro)   │
  │                 │ │              │ │                  │ │                  │
  │ Web搜索调研     │ │ 独立审查      │ │ 工程师查询测试    │ │ D5置信二次审核   │
  │ 增量添加条目     │ │ 完整性评分    │ │ LLM诊断模拟测试   │ │ 消除待核实条目    │
  │ 引用来源        │ │ 缺失项指出    │ │ 级联路径验证      │ │ 标准引用去伪存真  │
  └─────────────────┘ └──────────────┘ └──────────────────┘ └──────────────────┘
```

## 2.2 主智能体（DeepSeek）

**职责**:
- 维护知识库整体Schema和编码规范
- 初始化每个行业的构建任务
- 接收收集调研智能体的输出，执行结构验证（编码合规、Schema校验、去重）
- 将验证后的内容提交给Judge智能体审查
- 整合Judge的反馈，判断是否通过、需要修订还是重做
- **整合与精炼**: 当某层内容积累到一定量后，负责合并重叠项、调整分类粒度、统一表述，最终敲定该层结构
- 管理交叉索引的构建
- 对每个层级做出**最终批准**决定
- 唯一有权修改Schema或目录结构

**决策权限**:
- 通过/驳回：基于Judge评分（≥7 通过）
- 终止：某层连续3轮未通过，暂停该层并向人类专家求助

## 2.3 收集调研智能体（DeepSeek）

**职责**:
- 严格按层级工作：当前层未通过前，绝不跨越到下一层
- 每轮通过Web搜索调研后**增量添加**新条目（设备/部件/故障）
- 每轮输出必须包含来源引用（URL、标准编号、文献名）
- 根据Judge反馈的缺失项进行定向补充调研
- 所有事实性信息必须通过搜索验证，不得凭空编造

**增量调研原则**:
- 每轮聚焦一个子行业/设备/部件，不贪多
- 每轮添加后立即提交审查，不积累
- Judge指出缺失项后，下一轮定向补充

## 2.4 Judge智能体（DeepSeek V4）

**配置**: 单审查者，使用DeepSeek V4。

**职责**:
- 审查每一轮新增内容，输出结构化评审结果
- **覆盖全面性**：是否遗漏了重要的条目
- **分类合理性**：分类方式是否符合实际工业环境；是否存在表述重合、边界模糊的条目；某些条目是否需要更细拆分或合并
- **粒度适当性**：设备/部件/故障的粒度是否合适（过粗导致信息丢失，过细导致冗余）
- **内容质量**：参数阈值是否合理、标准引用是否真实
- 评分 + 具体的缺失项/错误项/重合项列表

**输出格式**:
```json
{
  "verdict": "pass | revision_needed | reject",
  "score": 8,
  "completeness_issues": ["覆盖度定性问题，如'辅助设备覆盖不充分'"],
  "classification_issues": ["分类/粒度/边界问题"],
  "accuracy_issues": ["准确性问题"],
  "suggestions": ["改进建议"],
  "missing_items": ["具体缺失条目名称，如'引风机'、'送风机'"]
}
```

> **字段分工**: `completeness_issues` 描述覆盖度的定性问题，`missing_items` 列出具体缺失条目名称。
```

## 2.5 可用性判断智能体（DeepSeek）

**职责**:
- 以10年经验现场运维工程师的视角审查知识库
- 执行3类测试（详见阶段5）
- 评估索引查询的精准度
- 评估LLM借助知识库进行诊断的效果

## 2.6 标准核查智能体（DeepSeek Pro）

**职责**:
- 在故障知识 Phase B（整合）完成后对 D5 置信标注做二次审核（Phase C）
- 消除所有"待核实"条目（升级为"标准值"或降级为"经验值"）
- 尝试将"经验值"升级为"标准值"（当能确认对应标准时）
- 验证声称"标准值"的参数是否真实引用了正确标准（防止幻觉）
- 对所有含"待核实"的 D5 参数给出结论；无法确定的标"unknown"由 Post-Phase-C 正则兜底转为"经验值-未核实"

**与其他智能体的关系**: 标准核查智能体是故障知识生成流程的最后一道质量闸门，在 Judge 审查之后、写盘之前执行。与 Judge 互补——Judge 侧重覆盖度和逻辑合理性，标准核查侧重 D5 置信标注的真实性。

## 2.7 智能体协作流程

各智能体之间的协作遵循「先扩充后整合」的两阶段策略（详见章节3），交互流程如下：

```
主智能体 → 分配任务 → 收集调研智能体 → 搜索调研 → 增量输出 → 主智能体
主智能体 → 结构验证 → Judge智能体 → 审查评分 → 主智能体
主智能体 → 整理评审结果：
  a. 高分(≥8)无缺失 → 定稿
  b. 有缺失项 → 反馈收集调研智能体继续补充
  c. 覆盖度充分 → 主智能体整合精炼 → 定稿
```

## 2.8 三AI专家评审模块（ai_expert_review，独立于 pipeline）

除上述 pipeline 内的多智能体（主智能体 + Judge）外，项目还有一个**独立的结构评审模块** `src/ai_expert_review/`，用于对设备清单、子设备清单、结构树做**层无关的多AI辩论评审**。它在阶段2（设备）和阶段3（结构树）的人工审核环节调用，是 C方案复用与新生成设备的**必需把关机制**（§8.5、§10.4）。

**架构**：DeepSeek（行业资深工程师视角）+ Kimi（知识架构师视角）多轮辩论 → Claude/人工基于报告仲裁分歧（不自动改数据）。

**评审层级与命令**：

| 评审层级 | layer 参数 | 评审单元 | 典型用途 |
|---------|-----------|---------|---------|
| 设备清单 | `equipment` | 一个子行业的全部设备 | 阶段2 设备边界、主/辅/公用分类 |
| 子设备清单 | `sub_equipment` | 一个设备的全部子设备 | 阶段2.5 子设备维度纯度、MECE |
| 结构树 | `structure` | 一个设备的整棵结构树 | 阶段3 子系统/部件/零件，核心承载件检查（§8.5） |

**典型命令**：
```bash
# 火电设备层评审（有子行业）
python src/ai_expert_review/AI_Expert.py review --layer equipment --sub 火电

# 石化结构树评审（无子行业，设备类型作 --sub）
python src/ai_expert_review/AI_Expert.py review --layer structure --industry 石化 --sub 风机 --equip 离心风机
```

> 详见 `src/ai_expert_review/README.md`。**关键经验**：三AI评审能发现人工审查遗漏的问题（C方案继承的源行业缺陷、新生成设备漏核心承载件），是质量门控的重要补充。

# 章节3: 逐步构建工作流程

## 核心原则：先扩充后整合，增量迭代

每一层的构建遵循**两阶段策略**：

### 阶段A: 大量扩充（先广度）

收集调研智能体不受分类完美性约束，**尽量多地添加条目**。此时允许：
- 同一设备的不同叫法并存（如"磨煤机"和"煤磨"）
- 粒度不完全一致的拆分（有的设备拆到零件级，有的只到组件级）
- 可能有重合或交叉的条目

每轮扩充仍需经过Judge审查，但审查重点是**有没有遗漏**，而非分类是否完美。

### 阶段B: 整合精炼（后收敛）

当Judge评估覆盖度已基本达标时，进入整合阶段：
- 主智能体对积累的所有条目进行**去重、合并、拆分、统一表述**
- Judge审查整合后的结果，重点检查**分类合理性、粒度适当性、边界清晰性**
- 整合→审查→微调，直到Judge认可

```
┌──────────────────────────────────────────────────────┐
│              两阶段构建流程（每层）                      │
│                                                      │
│  阶段A: 扩充 (最多2轮)              阶段B: 整合        │
│  ┌─────────────────┐               ┌────────────┐    │
│  │ 调研智能体添加    │               │ 主智能体整合  │    │
│  │        │         │               │ - 去重合并   │    │
│  │        ▼         │               │ - 粒度调整   │    │
│  │ Judge审查(遗漏?) │               │ - 统一表述   │    │
│  │        │         │               │      │      │    │
│  │   还缺？→补充    │  覆盖度达标 →  │ 输出定稿     │    │
│  │        │         │    (触发整合)   │      │      │    │
│  │        ▼         │               └────────────┘    │
│  │  高分(≥8)无缺失?  │                                  │
│  │   ├─是→跳过整合   │  ← 节省1次LLM调用                 │
│  │   └─否→进入整合   │                                  │
│  └─────────────────┘                                  │
└──────────────────────────────────────────────────────┘
```

**为什么要两阶段**: 设备分类、部件拆分、故障维度的划分在初期不可能完美。先大量扩充保证覆盖面，再由主智能体在充足信息基础上做整合决策，比一开始就追求完美分类更可靠。

**每层都是独立循环**：子行业层、设备层、部件层、故障层各自独立迭代，上层通过后才展开下层。

## 分阶段执行机制

知识库构建采用**逐阶段独立执行**的方式，每个阶段是一个独立的命令，人工审核通过后再执行下一阶段。

### 执行命令

```bash
# 阶段1: 子行业划分
python src/pipeline/main.py 电力 --phase sub_industry

# 阶段2: 设备枚举（全部子行业）
python src/pipeline/main.py 电力 --phase equipment

# 阶段2: 设备枚举（仅火电）
python src/pipeline/main.py 电力 --phase equipment --sub 火电

# 阶段3: 部件拆解（火电全部设备）
python src/pipeline/main.py 电力 --phase component --sub 火电

# 阶段3: 部件拆解（仅锅炉）
python src/pipeline/main.py 电力 --phase component --sub 火电 --equip 锅炉

# 阶段3: 部件拆解（按设备属性筛选 — 仅主设备）
python src/pipeline/main.py 电力 --phase component --sub 火电 --equip-type 主设备

# 阶段3: 部件拆解（按设备属性筛选 — 辅助设备）
python src/pipeline/main.py 电力 --phase component --sub 火电 --equip-type 辅助设备

# 阶段3: 部件拆解（v3.0新三级结构：子系统→部件→零件）
python src/pipeline/main.py 电力 --phase component --sub 风电

# 阶段4: 故障知识（仅锅炉的水冷壁）
python src/pipeline/main.py 电力 --phase fault --sub 火电 --equip 锅炉 --comp 水冷壁

# 阶段4: 故障知识（按设备属性筛选）
python src/pipeline/main.py 电力 --phase fault --sub 火电 --equip-type 主设备

# 阶段4: 故障知识（强制覆盖已有数据 + 并行3线程）
python src/pipeline/main.py 电力 --phase fault --sub 火电 --equip-type 主设备 --force --workers 3

# 阶段4: 故障知识（v3.0新三级结构，风电试点）
python src/pipeline/main.py 电力 --phase fault --sub 风电 --force --workers 3

# 阶段4: 故障知识（水电子行业主设备）
python src/pipeline/main.py 电力 --phase fault --sub 水电 --equip-type 主设备 --force --workers 3

# 阶段5: 验证
python src/pipeline/main.py 电力 --phase validate
```

> **无子行业行业的命令差异（如石化）**：石化无子行业层，命令省略 `--sub`，直接从行业进入设备层：
> ```bash
> # 石化设备枚举（无 --sub）
> python src/pipeline/main.py 石化 --phase equipment
> # 石化结构层（无 --sub，直接 --equip）
> python src/pipeline/main.py 石化 --phase component --equip 压缩机
> # 石化故障层
> python src/pipeline/main.py 石化 --phase fault --equip 压缩机 --force --workers 3
> ```
> 跨行业复用（C方案）时，结构层用复制 + 评审替代生成，故障层用行业感知 prompt 生成，详见 §10。

### 增量构建与断点续跑

管道支持在已有数据基础上**增量构建**，适用于以下场景：

1. **按设备属性分批构建**: 设备清单包含主设备、辅助设备、公用系统，可以先只构建主设备的部件/故障，后续再补充辅助设备和公用系统。通过 `--equip-type` 参数实现。
2. **断点续跑**: 部件阶段（Phase 3）和故障阶段（Phase 4）会自动检测已存在输出文件的设备/部件并跳过，不会覆盖已有数据。中断后重新运行相同命令即可从断点继续。
3. **单设备修补**: 通过 `--equip` 指定单台设备进行重新生成（会覆盖该设备的已有数据）。

**跳过逻辑**: 当目标输出文件已存在且非空时，该条目自动跳过并在日志中标记 `跳过(已有数据)`。如需强制重新生成所有条目，使用 `--force` 参数（无需手动删除文件）。`--force` 与 `--workers N` 可组合使用以加速全量重跑。

### 执行流程

```
阶段1 → 人工审核子行业划分 → 通过？
                               ↓ 是
阶段2 → 人工审核设备清单 → 通过？
                           ↓ 是
阶段3 → 人工审核部件树 → 通过？
                          ↓ 是
阶段4 → 人工审核故障知识 → 通过？
                            ↓ 是
阶段5 → 验证通过 → 该行业完成
```

### 数据传递

每个阶段从磁盘读取上一阶段的输出，不依赖内存状态：

| 阶段 | 读取 | 输出 |
|------|------|------|
| 阶段1 | 无 | `index.md` |
| 阶段2 | `index.md` (子行业列表) | `*/equipment_registry.md`, `*/sub_equipment.md`, `*/equipment_classification.md` |
| 阶段3 | `equipment_registry.md` (设备列表) | `*/components.md`（旧格式）或 `*/sub_system.md` + `*/*/components.md`（v3.0新格式） |
| 阶段4 | `components.md` (部件列表) | `*/faults/*.md`（旧格式）或 `*/*/*/faults/*.md`（v3.0新格式） |
| 阶段5 | 全部数据 | 验证报告 |

> **注**: `--sub`、`--equip`、`--equip-type`、`--comp` 参数用于增量执行。`--equip-type` 按设备属性（主设备/辅助设备/公用系统）筛选，`--equip` 指定单台设备。Phase 3/4 自动跳过已有数据的设备/部件，支持断点续跑。

### 自动化校验脚本

每个阶段（2-4）的数据生成后，在主智能体验证之前，**必须**运行自动化校验脚本。校验脚本不依赖LLM，以程序化方式检查数据质量。

**校验项**:

| 校验项 | 适用阶段 | 检查逻辑 | 不通过时处理 |
|--------|---------|---------|-------------|
| 行级去重 | 2-4 | 数据行 `sort -u` 后行数与原始行数对比，不一致则报警 | 自动去重，输出警告日志 |
| 表头完整性 | 2-4 | 列名和列数与该阶段的Schema严格匹配 | 阻断，要求修正格式 |
| 父部件引用完整性 | 3 | components.md中parent列的值必须在部件名称列中存在（"—"除外） | 阻断，列出孤立节点 |
| 故障文件名对应 | 4 | faults/目录下的文件名必须与components.md中的部件名称对应（叶节点必须有，父节点可选） | 警告，列出缺失和多余的文件 |
| 必填字段非空 | 3-4 | 维护方法、报废方法（叶节点）、D1-D9（故障行）不得为空；D10允许"—"；检维修5列选填（允许"—"），但填写时须带置信标注 | 警告，列出空字段所在行 |

**集成方式**: 校验脚本位于 `src/scripts/validate_kb.py`，在阶段2/3/4的增量迭代循环中，每次生成新数据后、主智能体验证前调用。校验结果写入日志，去重类问题自动修复，格式类问题阻断并报告。

## 阶段1: 子行业/领域划分（按需执行）

首次运行时自动完成目录结构创建。当行业规模大、存在明确的生产细分领域时执行本阶段；当行业设备类型集中、无自然细分时跳过，直接进入阶段2。

**步骤**:

### 步骤1.1: 收集调研智能体进行行业调研

Web搜索策略：
- `"{行业名} 行业 子行业 分类 设备"`
- `"{行业名} industry sub-sectors classification"`
- `"{行业名} 行业标准 设备分类"`
- `"{行业名} 生产环节 工艺流程 主要设备"`

### 步骤1.2: 收集调研智能体输出子行业/领域清单

**输出格式**（严格两列，不允许添加其他列）：
```markdown
| 子行业名称 | 描述 |
|---|---|
| 火电 | 利用煤炭、天然气等燃料燃烧产生蒸汽驱动汽轮发电的发电方式 |
```

来源引用：每条描述末尾用括号注明来源（标准编号/URL/文献名），如`（来源：DL/T 5186）`。

### 步骤1.3: 主智能体结构验证

- 检查：子行业之间边界清晰，无重叠
- 检查：分类方式符合实际生产组织
- 检查：输出严格为两列格式，无多余文字

### 步骤1.4: Judge审查

- Judge审查重点：
  - 子行业划分是否覆盖了该行业所有主要生产环节
  - 是否与实际工业组织方式一致
  - 是否有遗漏的重要子行业
  - 是否存在重叠或分类不当

### 步骤1.5: 增量迭代

- Judge指出缺失项 → 收集调研智能体下一轮定向补充
- 重复直到Judge均评分≥7

**质量门控**:
- [ ] 子行业/领域覆盖该行业所有主要生产环节
- [ ] 各子行业边界清晰，无重叠
- [ ] 输出严格为两列格式，无多余文字
- [ ] Judge独立评分均≥7

## 阶段2: 设备枚举

**范围**: 在子行业层（如有子行业）或直接在行业层展开。

**策略**: 逐个子行业/领域依次完成，不并行。

**步骤**:

### 步骤2.1: 收集调研智能体调研设备

Web搜索策略：
- `"{子行业名} 主要设备 设备清单 设备种类"`
- `"{子行业名} 辅助设备 BOP系统 公用系统"`
- `"{子行业名} equipment list specification"`
- 搜索行业技术手册、设计规范中的设备清单

### 步骤2.2: 增量添加设备条目

**输出格式**（严格三列，不允许添加其他列）：
```markdown
| 设备类型名称 | 设备属性 | 描述 |
|---|---|---|
| 锅炉 | 主设备 | 通过燃料燃烧加热给水产生蒸汽用于发电或供热 |
```

**设备属性取值**: 主设备 / 辅助设备 / 公用系统

来源引用：每条描述末尾用括号注明来源。

### 步骤2.2a: 自动化校验

运行 `validate_kb.py --stage 2 --target {子行业目录}`，自动执行：
- 行级去重检查（equipment_registry.md、sub_equipment.md）
- 表头完整性检查（列名和列数匹配Schema）

### 步骤2.3: 主智能体验证

- 格式验证：严格三列，无多余文字，无多余列
- 设备边界检查（无重叠）
- 去重检查
- 判断是否需要子设备层：若某设备在实际现场存在≥3种不同技术实现方式（如"锅炉"涵盖煤粉炉、CFB、余热锅炉），且这些实现方式在部件结构和故障模式上有显著差异，标记为需要子设备拆分

### 步骤2.4: Judge审查

审查重点：
- 设备种类是否全面（主设备+辅助设备+公用系统）
- 是否符合实际工业现场的设备构成
- 是否遗漏了重要的辅助系统
- 哪些设备需要进一步拆分子设备

### 步骤2.5: 子设备拆分（按需）

对于步骤2.3中标记为需要子设备拆分的设备：

**输出格式**（严格两列）：
```markdown
| 子设备名称 | 描述 |
|---|---|
| 煤粉炉 | 煤粉悬浮燃烧的锅炉，适用于大型电站 |
```

**维度纯度要求**: 子设备拆分必须基于**单一分类维度**（通常是技术路线），不可混合多个维度。常见的正确维度选择：
- 按**技术路线/燃烧方式**：煤粉炉、CFB、余热锅炉
- 按**机组类型**：亚临界、超临界、超超临界
- 按**冷却方式**：湿冷、空冷

**维度纯度自检规则**: 任意两个子设备不应可能同时存在于同一台设备上（互斥性）。例如"电站锅炉"和"直流锅炉"可能同时存在于同一台设备上，说明维度混用了（前者是用途维度，后者是循环方式维度）。

**按存量与可维护性裁剪（改造4）**: 子设备清单只覆盖该设备的**主流技术路线（现场存量 95%+）**。市场份额极低、未规模化商用、试验性或已淘汰的机型**不单列**入正式知识库（可在归档目录备注，不展开下层知识）。判断标准：现场存量占比、是否规模化商用、运维知识能否独立成体系。通常 2-4 个主流子设备即可，宁缺毋滥。例如风电机组只列双馈(DFIG)/直驱(PMSG)/半直驱三个主流，高速永磁/液压传动/电励磁直驱(EESG)/无刷双馈/鼠笼异步(SCIG)等小众或已淘汰机型不列入。

**数据仓库验证（见 §0.4）**：当某设备大类下存在**≥3 个技术路线型 `devicetype`** 且各自有显著存量时，用 `industry_devicetype_topN.csv` 验证拆分必要性，并取累计覆盖≥95% 的技术路线作为子设备清单。风电三机型已实证（双馈 62% / 直驱 24% / 半直驱 13%）。多数行业无技术路线维度，对应设备**不拆子设备**。

子设备拆分也需经过Judge审查。

### 步骤2.5a: 编写设备分类决策文档

**目的**: 记录每台设备的分类判定依据和关键边界决策，作为后续阶段的锚点和跨行业复用参考。

**产出**: `equipment_classification.md`（与equipment_registry.md同级目录）

**格式**:
```markdown
# {行业名}子行业设备划分记录

## 1. {子行业名}

### 1.1 设备清单（N台）

| # | 设备 | 目录名 | 设备属性 | 判定依据 |
|---|------|--------|---------|---------|
| 1 | 锅炉 | boiler | 主设备 | 三大主机之一，独立采购（哈尔滨锅炉/东方锅炉/上海锅炉），独立锅炉班维护，独立KKS编码 |

### 1.2 关键边界决策

**{设备A}：独立设备 vs {设备B}的部件？**
- 决策：独立设备 / 归属部件
- 理由：对照5条判定原则的具体分析
- 历史问题：（如有）之前如何处理，为何修正
```

**编写要求**:
- 每台设备必须填写"判定依据"列，至少引用5条判定原则中的2条
- 任何"归属模糊"的设备（如凝汽器、励磁系统）必须在"关键边界决策"中专门论述
- 涉及跨设备边界的问题（如独立辅机是否归入主设备部件）必须记录决策
- Judge审查时同步审查此文档的分类合理性

### 步骤2.6: 增量迭代直到覆盖度达标

**质量门控**:
- [ ] 设备清单包含主设备、辅助设备、公用系统
- [ ] 每台设备有明确的功能描述
- [ ] 输出严格为三列格式，无多余列和多余文字
- [ ] 设备边界清晰，无重叠
- [ ] 无重大遗漏（参照行业标准和实际现场）
- [ ] Judge评估设备覆盖充分，无重大遗漏
- [ ] 需要子设备拆分的设备已完成拆分并通过审查

# 章节4: Prompt 设计准则

具体 prompt 文本以 pipeline 代码（collector.py、judge.py）为唯一真实来源，本节仅定义各层 prompt 必须满足的设计准则。

## 4.1 通用设计原则

1. **格式锚定**: 每个 prompt 必须明确输出格式（Markdown表格、列数、列名），禁止表格外添加解释性文字
2. **Schema 约束**: 故障层 prompt 必须在审查标准前包含 D1-D10 维度定义 + 检维修5列定义（Schema 锚定），确保 LLM 输出符合17列 Schema
3. **来源引用**: 收集智能体 prompt 必须要求在描述列（故障层为 D3 列）末尾注明信息来源（标准编号/URL/文献名）
4. **增量补充**: prompt 必须支持接收已有数据并在其基础上补充，不重复已有内容
5. **禁止事项**: prompt 应显式列出禁止行为（如禁止添加额外列、禁止编造阈值）
6. **变量约定**: `{变量}` 为必填替换参数，`{{条件块}}` 为按需包含（仅当条件满足时插入 prompt）

## 4.2 各层 Prompt 设计要点

### 收集调研智能体

| 层级 | 必含要素 | 固定列数 | 特殊约束 |
|------|---------|---------|---------|
| 子行业(L1) | 行业调研方向、格式要求、来源引用 | 2列 | 可建议不分子行业 |
| 设备(L2) | 子行业上下文、格式要求、已有设备清单、来源引用 | 3列 | 设备属性仅三种取值（主设备/辅助设备/公用系统）；禁止添加额外列 |
| 部件(L3) | 设备上下文、格式要求、已有部件清单、来源引用 | 6列 | 父部件列用"—"；易损标识"是/否"；维护/报废方法仅最底层部件（无子部件）填写 |

|------|------------|---------|
| 完整性审查(L1-L3) | 覆盖全面性、分类合理性、粒度适当性、边界清晰性、实际验证、子设备维度纯度 | 仅 sub_equipment 时适用维度纯度检查 |
| 故障知识审查(L4) | Schema合规（D1-D10锚定）、故障全面性（FMEA框架）、征兆实用性、参数准确性、D2等级一致性、D3因果完整性、D5/D6区分正确性、D7鉴别诊断充分性、D8检修实用性、D9预防可操作性、D10易混淆故障有效性；**对抗性审查**（挑剔工程师视角）：D5工况适用性、D5置信分布合理性（待核实>10%扣分、>20%不合格、零待核实正常）、D7鉴别诊断充分性、D8操作安全性、D8规程级标注真实性、D5假冒标准值核查（检查标准号真实性与阈值一致性）；**改造6新增**：检维修5列（D11-D15）完整性（用工需求/工机具/备件/验收量化、安全HSE匹配）、检维修置信标注合规性（D11-D15每条须带置信级别，"标准值"防伪造） | 审查标准前必须包含 Schema 约束块（D1-D10定义 + 检维修5列定义 + D2等级表）；对抗性审查以质疑姿态主动挑战，而非礼貌认可；Phase C后标准核查智能体（DeepSeek Pro）覆盖全部"待核实"条目，Post-Phase-C正则兜底保证零"待核实"落盘 |

# 章节5: 质量门控与审查标准

## 5.1 通用评分标准

| 分数 | 含义 | 处理方式 |
|------|------|---------|
| 9-10 | 优秀，无问题 | 直接通过 |
| 8 | 良好，有小建议 | 通过，记录建议供后续改进 |
| 7 | 可接受，有需关注的问题 | 通过，但需确认问题已知晓 |

**终止机制**:
- 某层连续3轮未通过：暂停该层，向人类专家请求协助

覆盖率由 Judge 综合评估，结合行业标准/厂商手册/FMEA文档对照判断覆盖度是否充分。可计算的客观指标（如"已生成故障的部件数/总部件数"）作为辅助参考。

# 章节6: 验证与测试方法

## 6.1 结构验证（自动化）

- 编码一致性：所有编码遵循命名规则，无重复
- 引用完整性：故障编码指向实际存在的记录
- 树完整性：部件树无孤立节点、无循环引用
- 格式验证：每个文件严格遵循该层级的表格格式

### 6.1.1 validate_kb.py 用法

自动化校验脚本 `src/scripts/validate_kb.py` 不依赖 LLM，以程序化方式检查数据质量。每个阶段生成数据后、主智能体评审前**必须**运行。

```bash
# 按阶段校验
python src/scripts/validate_kb.py --stage 2 --target src/data/power/thermal       # 设备/子设备层
python src/scripts/validate_kb.py --stage 3 --target src/data/power/thermal/boiler # 子系统/部件/零件层
python src/scripts/validate_kb.py --stage 4 --target src/data/power/thermal/boiler # 故障层（17列）

# 全量校验（扫描所有子阶段）
python src/scripts/validate_kb.py --target src/data/power
```

**阶段校验项**：

| 阶段 | 校验内容 | Schema |
|------|---------|--------|
| 2 | equipment_registry.md（3列）、sub_equipment.md（2列）：去重、表头完整 | 设备类型名称/设备属性/描述 |
| 3 | sub_system.md（2列）、components.md（6列）：去重、表头、部件-零件关系、属性挂载、必填 | 部件/零件/描述/易损标识/维护方法/报废方法 |
| 4 | faults/*.md（17列）：去重、表头、故障文件名↔部件名对应、必填非空、D1物理属性枚举 | 故障名称/故障类别/D1-D15 |

**子系统数量硬上限**（v3.1，阶段3检查）：
- 静设备（换热器/塔/容器）≤ 4
- 旋转机械（泵/风机/压缩机）≤ 6
- 大型主设备（锅炉/汽轮机/反应器）≤ 7（须论证功能不可合并）
- **硬上限 7**：`validate_kb.py` 对 >6 子系统发 WARNING（提示仅大型主设备允许），>7 阻断（error）

> **故障层目标**：阶段4 校验通过后，阻断错误数 = 0（警告可接受，如标准时效标注、D2 偏置、D5/D6 误判等非结构性问题）。故障层治理见 §9。

## 6.2 内容验证（Judge审查）

- D5数值阈值有来源（标准值/经验值/经验值-未核实 四级置信标注）；Post-hoc标准号白名单校验（validate_kb.py）
- D3故障机理符合物理/化学/力学原理

## 6.3 可用性验证（可用性智能体）

- 工程师查询测试（10个真实场景）→ 定位准确率≥80%
- LLM诊断测试（5个模拟场景）→ 诊断正确率≥80%
- 级联路径测试 → 故障相关引用链路可追踪、无死路

# 章节8: 设计哲学与粒度统一规则（v4.0 新增）

> **本章是石化三设备族（离心泵 / 风机 / 压缩机）经三AI评审 + 故障层治理后沉淀的跨设备粒度规则。**这些规则不是单点缺陷，而是 LLM 生成的系统性偏差。按照「第一性原理治理」原则，写入指南作为生成时的**硬约束**（而非事后修复），从根本上防止同类问题再次发生。适用于所有行业同类设备的结构层构建（阶段3）。

## 8.1 电气/控制元件粒度

LLM 生成控制系统时常出现两种偏差：
- **过度细分**：把 PLC 拆成 CPU模块 / 电源模块 / DI模块 / DO模块 / AI模块 / 通讯模块 6 个零件，使电控柜被模块淹没，与机械侧总成（齿轮箱/轴承）粒度失衡
- **层级错乱**：按钮/信号灯/接线端子等小元件被建为独立部件，与重型总成并列

**判定标尺：现场是否作为独立采购/更换单元。** 现场换 PLC 整机（不换单个 IO 模块），则 PLC = 部件，不拆模块。

| 元件类型 | 归属层级 | 说明 |
|---------|---------|------|
| PLC控制器 / 变频器 / 软启动器 | 部件 | 整体作为部件，**不拆分内部模块**为零件 |
| 接触器 / 断路器 / 热继电器 / 中间继电器 | 部件 | 独立可更换单元；触点/线圈可作其零件 |
| 传感器 / 变送器（压力/温度/液位/振动） | 部件 | 感测元件（芯体/膜片）可作其零件 |
| 电磁阀 / 气动执行器 | 部件 | 线圈/阀体可作其零件 |
| PLC 内部模块（CPU / IO / 电源） | 默认不单独建 | 仅当确实需现场单独更换时，最多保留 2-3 个关键模块作为零件，不全部展开 |
| 按钮 / 信号灯 / 接线端子 / 熔断器 / 柜内照明 | 零件 | 归入所属「控制柜」部件，不单独建部件节点 |

## 8.2 标准紧固件不单列

螺栓组 / 地脚螺栓 / 标准键 / 卡环 / 挡圈 / 弹簧垫圈等**标准紧固件不作为独立零件节点**。其失效（松动/断裂/锈蚀）的维护方法在父部件的「维护方法」或相关故障的 D8 中描述。

**理由**：紧固件是通用标准件，故障模式高度雷同，单列会产生大量冗余节点，且不提供独立诊断价值。**例外**：高强度螺栓/液压螺栓若作为关键承载件（如缸体连接螺栓），可作为关键零件保留。

## 8.3 易损标识判定

「易损标识」列按**失效周期可预测性 + 是否需备货更换**判定，不随意：

| 易损标识 | 判定标准 | 示例 |
|---------|---------|------|
| **是** | 有明确失效周期/模式的可更换件，运维周期内需主动更换或备货 | 轴承、密封、滤芯、传感器、温控阀、电磁线圈、O型圈、滤网、触点、膜片 |
| **否** | 长寿命结构件或随整机报废件 | 机壳、机身、轴承箱、柜体、叶轮（非易损）、管道 |

> **易损 ≠ 会坏**。是「是否需要在运维周期内主动更换/备货」。柜体再旧也是「否」（不备货、随整机报废）；传感器即使没坏也可能是「是」（要备货，按周期更换）。

## 8.4 执行机构与工艺阀门归属

执行机构（气动/电动执行器、阀门定位器）与工艺阀门（调节阀、安全阀、防喘振阀）的子系统归属：

| 对象 | 归属子系统 | 理由 |
|------|----------|------|
| 执行机构 + 工艺阀门 | **工艺机械侧**子系统 | 失效与工艺介质、阀位反馈强相关，归工艺侧便于故障定位 |
| 检测传感器 | 所属**工艺子系统** | 监测哪个工艺参数就归哪个子系统（温度传感器归工艺侧） |
| 纯电气控制元件（PLC/接触器/继电器） | **控制与监测系统** | 电气逻辑控制单元 |

**警示**：防喘振阀 / 进气导叶执行器若误归「电气控制系统」，会导致「控制故障」误判——其本质是工艺气路调节。归工艺机械侧。

## 8.5 核心承载件与安全附件必建

LLM（尤其 DeepSeek 新生成）倾向生成运动件/功能件，**遗漏基础静止承载件和安全附件**。这是三AI评审发现的**最高频致命缺陷**——缺失即标记「致命」级必须补齐。

**必建清单**（评审硬性检查）：

| 设备类型 | 必建核心承载件 | 必建安全附件 |
|---------|--------------|------------|
| 往复式压缩机 | 机身/机架(曲轴箱)、活塞杆、十字头、轴瓦、支撑环 | 安全阀、卸荷阀 |
| 离心压缩机 | 机壳/气缸、轴承箱、增速齿轮箱、高位油箱、进气导叶 | 防喘振阀、安全阀 |
| 液环压缩机/真空泵 | 机壳、叶轮、轴、轴封、气液分离器 | 安全阀、进气过滤器 |
| 离心泵 | 泵壳(蜗壳)、泵轴、轴承箱、密封腔、叶轮 | — |
| 风机 | 机壳、主轴、轴承箱、蜗壳、叶轮 | — |
| 螺杆压缩机 | 机壳、转子(阴阳)、轴承、同步齿轮 | 最小压力阀、安全阀 |

**判定原则**：任何承载压力/扭矩/介质的核心静止件、任何保护设备安全的安全附件，必须在结构树中存在。新生成设备的结构树必须经三AI评审（§10.5）验证核心承载件无遗漏。

## 8.6 规则的适用与例外

以上 5 条规则是**生成时硬约束**，写入阶段3的部件拆解 prompt（见 §4.2），并在三AI评审中检查。例外情况（如某设备确实需拆分 PLC 模块）须在评审中论证并记录。

> 这些规则沉淀自石化实践（离心泵 C方案 + 风机 + 压缩机新生成），已验证可推广到冶金 / 水泥 / 煤炭等行业的同类旋转设备。

# 章节9: 故障层治理机制（v4.0 新增）

> **故障层是 LLM 生成质量问题最集中的层。**经过火电 + 石化的治理实践，沉淀出一套**治理脚本链**，用于在 validate 之后、导出之前，批量修复 LLM 的系统性偏差。本章记录通病、治理工具与标准流程。

## 9.1 LLM 故障层生成通病

LLM（DeepSeek / GLM）生成故障层（17列）时存在以下系统性偏差：

| 通病 | 表现 | 根因 |
|------|------|------|
| **整列错位** | LLM 漏填「故障类别」列，整行左移，列数 <17 | 17列过多，LLM 偶发漏列 |
| **D1/故障类别对调** | D1 填了失效机理(磨损/老化)，故障类别填了物理属性(机械/化学) | 列含义混淆 |
| **类别白名单违规** | 自创类别（化学侵蚀/结构失效/跑圈/破损） | 未严格遵循 failure_categories.yaml |
| **D1 顿号分隔** | D1 用顿号（、）而非分号（;） | 分隔符不规范 |
| **D8 缺标注** | 漏 [规程级]/[经验级] | 标注规则未内化 |
| **D5 置信标注失当** | 滥标"待核实"或漏标注 | 来源判断不准 |
| **工况污染** | 跨行业术语混入（火电术语进石化） | C方案复制时未清洗 |
| **D5/D6 误填** | 特征参数填了监测手段，或反之 | 列含义混淆 |

## 9.2 治理脚本链

治理脚本位于 `src/scripts/`，统一遵循 **DRY-RUN → --apply 两阶段模式**（先预览确认，再写回执行）：

| 脚本 | 治理内容 | 检测逻辑 |
|------|---------|---------|
| `_fix_d1_cat_swap.py` | D1/故障类别对调 | D1 含非枚举值 且 故障类别 ∈ 物理属性七值 → 交换两列 |
| `fix_fault_categories.py` | 类别白名单违规 | 按预设 {文件:{旧类别:新类别}} 精确替换第2列 |
| `_fix_d8_level.py` | D8 缺标注 | 含标准号(GB/DL/T/API…)→[规程级]，否则→[经验级] |
| `_fix_d5_conf.py` | D5 置信标注 | 滥标"待核实"→ 升级"标准值"或降级"经验值" |
| `_fix_maint_conf.py` | 维护/报废方法冲突 | components.md 零件行误填维护/报废方法 → 改"—" |
| `_fix_d1_cat_thermal.py` | 火电专用 D1/类别修正 | 火电行业专用修正 |

> **使用方式**：所有脚本支持 `python src/scripts/<脚本名>.py <设备目录> [--apply]`，不带 `--apply` 为 DRY-RUN 预览。

## 9.3 标准治理流程

故障层生成后的标准治理链（石化 / 火电通用）：

```
1. validate_kb.py --stage 4 --target <设备目录>
       ↓ (查阻断错误，列数/必填/表头)
2. _fix_d1_cat_swap.py --apply      (D1/类别对调)
3. fix_fault_categories.py          (类别白名单违规)
       ↓
4. 重新生成整列错位文件
   (--force --comp <部件名>，列数<17的顽固文件手动Edit)
       ↓
5. _fix_d8_level.py --apply         (D8 [规程级]/[经验级] 标注)
6. _fix_d5_conf.py --apply          (D5 置信标注)
       ↓
7. D1 顿号(、)→分号(;) (脚本/正则)
       ↓
8. 工况污染核查 (跨行业术语扫描，C方案专用)
       ↓
9. validate_kb.py --stage 4 (再验证，目标：0 阻断错误)
```

## 9.4 整列错位的特殊处理

整列错位（LLM 漏填故障类别列致整行左移）是最棘手的问题——`_fix_d1_cat_swap` 无法修复（它仅交换2列，不能补缺列）。处理方式：
- **检测**：列数 < 17 的故障行
- **修复**：`python src/pipeline/main.py ... --phase fault --force --comp <部件名>` 强制重新生成该部件故障文件
- **顽固文件**：重生成后仍错位 → 手动 Edit 插入缺失列（导叶衬套等 C方案继承 bug 曾出现）

## 9.5 工况污染治理（C方案专用）

C方案跨行业复用时，源行业的工况术语会污染目标行业。**石化必须为 0 的火电术语**（典型映射）：

| 火电术语（污染） | 石化正确术语 |
|---------------|------------|
| DL/T 995-2016 等电力标准 | GB 50150-2016 / SH/T / API |
| 锅炉给水 / 送引风 / 工业锅炉水质 | 石化无此概念，删除或改工艺介质 |
| 吸入空气（轴承描述） | 油泵抽空 / 进油不畅 |
| 除氧器 / 凝结水 | 除氧处理 / 冷凝液 |

治理方式：扫描脚本逐文件检查 + 白名单映射清洗。详见 §10.5 工况污染治理。

## 9.6 治理原则：第一性原理

治理脚本是**事后补救**。**根本解决应回到生成源头**（这是本指南的核心方法论）：

| 问题类型 | 根本解决方式 |
|---------|------------|
| 通病频繁出现（D1 分号、D8 标注） | 写入 prompt 约束（§4.2），让 LLM 生成时就遵守 |
| 类别自创 | failure_categories.yaml 白名单在 prompt 中显式注入 |
| 核心承载件遗漏 | 三AI评审硬性检查（§8.5、§10.5） |
| 偶发偏差 | 治理脚本兜底（可接受） |

> **核心原则**：治理脚本只处理偶发偏差，**不处理系统性错误**（系统性错误必须改 prompt）。否则治理脚本会无限堆积，违背第一性原理。

# 章节10: 跨行业复用与多行业构建（v4.0 新增）

> **同类型设备（泵/风机/压缩机/电机）在不同行业的部件结构高度相似。**跨行业复用可大幅节省生成成本、保证同类设备结构一致性、快速扩展到新行业。本章定义「C方案」（跨行业复用）的流程、行业感知与把关机制。

## 10.1 C方案定义

**C方案 = 跨行业结构复用**，分两步：

```
步骤1: 结构层复制（直接拷贝目录）
  源行业/{设备}/{子设备}/  →  目标行业/{设备}/{子设备}/
  （子系统/部件/零件层，sub_system.md + components.md 等直接复制）

步骤2: 故障层重新生成（industry-aware prompt）
  基于复制的结构层，用【目标行业】的 prompt 重新生成故障层
  （prompt 注入目标行业的工况锚点、标准体系、术语）
```

> **关键**：结构层可复制，故障层**必须用目标行业 prompt 重新生成**（直接复制故障层会引入工况污染）。这是 C方案与"全量复制"的本质区别。

## 10.2 何时用 C方案 vs 新生成

| 场景 | 策略 |
|------|------|
| 同类设备跨行业（石化离心泵 ← 火电离心泵/给水泵） | ✅ **C方案** |
| 同类设备行业内（石化离心泵 ← 石化风机） | ❌ 新生成（结构不同） |
| 新行业首设备（无源可复用） | ❌ 新生成 |
| 工况差异大的同类设备 | ⚠️ 慎用，需大量特化 |

## 10.3 C方案的行业感知（industry-aware）

C方案复用时，目标行业故障层 prompt 必须注入**行业锚点**，否则产生工况污染：

| 行业 | 工况锚点 | 标准体系 |
|------|---------|---------|
| 石化 | 介质（油/气/酸碱）、易燃易爆、GB 30871 特殊作业 | API / SH/T / GB |
| 火电 | 蒸汽/水、高温高压、DL/T 规程 | DL/T / GB |
| 冶金 | 高温、粉尘、重载 | YB/T / GB |
| 水泥 | 粉尘、磨损、大扭矩 | JC/T / GB |

锚点注入故障层 prompt，确保生成的 D3/D5/D8/D14 符合目标行业工况（如石化必须引 GB 30871 受限空间作业、DL/T 标准必须清除）。

## 10.4 C方案的把关：三AI评审（必需）

**C方案会继承源行业的缺陷**——火电原版漏的部件，复制到石化后依然漏。因此 C方案的结构层**必须**经三AI评审：

| 评审发现 | 案例（石化实践） |
|---------|---------------|
| 继承的缺陷 | 离心风机继承火电"减速机油冷却器混淆"→ 删除 |
| 缺失核心承载件 | 离心风机缺轴承箱 → 补；螺杆缺最小压力阀/安全阀 → 补 |
| 易损标识错误 | 差压开关易损标识 否→是 |
| 零件补全 | 电动机补电机轴承/接线盒/冷却风扇 |

> **规则**：C方案复用的设备，**结构层评审通过后才生成故障层**。新生成设备同样必须评审（§8.5 核心承载件缺失在新生成中更严重）。

## 10.5 石化无子行业的处理

石化无子行业层（§0.3），但 C方案源（火电）有子行业层。复用 + 评审时的路径处理：

- `ai_expert_review` 的 `review` 命令路径模型是 `industry/sub/equip`
- 石化无子行业，故将**设备类型**（如"风机"）作为 `--sub` 参数
- 评审命令示例：
  ```bash
  python src/ai_expert_review/AI_Expert.py review --layer structure --industry 石化 --sub 风机 --equip 离心风机
  ```

## 10.6 工况污染治理（C方案专用）

C方案故障层重新生成后，仍需核查工况污染（源行业术语残留）：

1. **扫描**：脚本扫描目标行业库中的源行业术语（如石化库中的 DL/T、锅炉给水）
2. **白名单映射**：按 §9.5 映射表清洗
3. **核查**：目标行业的源行业术语计数必须为 0

> 石化库工况污染已治理至 0（火电专用术语在石化库中 0 出现）。

## 10.7 C方案实践案例（石化）

**C方案成功案例**（结构层从火电复用）：
- 石化离心泵 ← 火电给水泵/离心泵（110 故障，0 错，工况污染 0）
- 石化风机-离心风机 ← 火电风机（经三AI评审修复继承缺陷）
- 石化压缩机-螺杆压缩机 ← 火电双螺杆（经评审补最小压力阀/安全阀）

**新生成案例**（无源可复用，DeepSeek 新生成）：
- 石化风机-罗茨风机（DeepSeek 新生成，6 子系统 42 部件）
- 石化压缩机-往复式 / 离心 / 液环（DeepSeek 新生成，均经评审补核心承载件）

> **经验**：新生成设备比 C方案复用更易漏核心承载件（DeepSeek 倾向生成运动件，遗漏静止承载件）。新生成设备**必须**经三AI评审（§8.5）。
